# closed-remediation-review

> 评审整改完了，谁来验收？一个只读子线程逐条核对，主线程逐条裁决——**清单冻结、不许扩张**，让评审真正收得了口。

## 这是什么

对抗评审的收口工序。一次开放式对抗评审跑完、意见回补之后，用它来核验：原本采纳的意见和用户裁决，是不是被完整、无误、无越界地落实了。

它调用**一个**全新上下文的只读子线程做机械比对，再由主线程对每条结论逐条裁决。

和开放式评审的分工：

| 环节 | 目的 | 形态 |
|---|---|---|
| 开放式对抗评审 | 找未知漏洞、暴露不同视角 | 多模型独立评审 + 主线程裁决 |
| 封闭式整改验收（本 skill） | 核对已知整改是否正确关闭 | 单个只读子线程 + 主线程裁决 |

- **管**：采纳项是否落实、用户裁决是否按原义物化、整改 diff 有没有夹带清单外的语义变化、追溯链有没有断。
- **不管**：发现新的设计问题、重开已决策事项、再跑一轮多模型对抗评审——这三件在本 skill 里都是**判失败**。

## 解决什么问题

评审这件事最容易死在两个相反的方向上：

**一是收不了口（评审棘轮）**。每一轮评审都能发明新要求，而新要求几乎总是"更严"的方向——因为漏一条是事故、多加一条叫严谨。于是 R2 发现 R1 没提的问题，R3 又发现 R2 没提的，永远有下一轮，评审从质量手段退化成无限循环，最后停在半改状态。

**二是整改根本没人验**。评审报告写完、意见"已回补"，但：

- 采纳项漏了一条，没人发现；
- 回补了，但改写了原意，或者落到了错误的层；
- 顺手改了清单之外的东西，业务语义被悄悄动了；
- 报告里写着"用户已批准"，但找不到任何原始裁决证据；
- 整改把评审报告、正式规格、测试用例之间的追溯链改断了。

这两件事看着相反，根子是同一个：**没有一个"只准核对已知项、不准发明新项"的封闭工序。**

## 为什么这么设计

- **验收清单冻结后不得扩张**，这是全 skill 的核心。运行前主线程冻结输入并记录范围哈希，清单只包含五项已知内容。验收中看到别的设计问题——不记录、不顺手改、不升级。它不属于本次验收。**这就是往回拧棘轮的那颗螺丝。**
- **子线程只检，不裁**：它只能输出状态和事实证据，禁止给新方案或优化建议。因为"给建议"就是发明新项的入口。
- **失败状态分成五种而不是一个 FAIL**：遗漏 / 回补了但改变原意 / 清单外语义变化 / 缺可审计裁决来源，各自的处置完全不同。合成一种就没法处置。
- **主线程逐条裁决，且驳回必须留证据**：子线程意见不是自动修改指令。照单全改是判失败项——那等于把裁决权交给了一个只看局部证据的检查器。
- **能自己解的不打扰用户**：发现语义变化不等于自动升级。若既有裁决或正式规格已给出唯一答案，主线程直接恢复原义；只有确实需要**新的**业务选择时才停机，且要合并成一张表一次性问。
- **复验只允许失败集合缩小**：范围哈希不变、检查项集合不变，不得借复验发起新一轮开放式评审。这条堵死了"用复验绕过单轮限制"的后门。
- **不新建第二份真值**：结论追加到原评审报告里，且报告只是过程证据，不取得正式规格地位。避免评审产物自己长成一套影子规范。

## 怎么用

**触发场景**：评审整改验收、评审回补检查、关闭对抗评审、确认整改没有改变设计语义。

**四个前提，缺一不许运行**：

1. 同一评审对象、同一真值基线下的开放式对抗评审已经且**只**跑过一次。
2. 原报告每条意见有稳定编号、处置结论和整改要求。
3. 需要用户拍板的项已写入裁决记录，每条有稳定编号与原始证据。
4. 整改前对象、整改后对象、允许改动范围都可定位。

缺前提就退回去补，**不要用本 skill 补做设计**。

**流程**：

1. **冻结输入**：评审对象路径、整改前后哈希、原报告全文与全部裁决、用户裁决记录、上游正式真值与"已决策不得重开"清单、允许修改范围、整改 diff。记录范围哈希。
2. **起一个只读子线程**：全新上下文，只给冻结证据包，不灌主线程的预设结论；只读不写，不调其他模型，不再起子线程。
3. **子线程逐条输出**：每行含检查项编号、关联的原意见或裁决编号、状态、对象位置、事实证据、是否疑似改变业务语义。
4. **主线程逐条裁决**：驳回（写明反驳证据）/ 采纳（唯一修法且不产生新业务选择时自行修正）/ 停机（合并成一张表请用户一次拍板）。
5. **留痕**：追加到原评审报告，写明范围哈希、检查结论表、最终状态。

**终态只有三种**：全部关闭且无未决语义 = `PASS`；仍有确定性整改未完成 = `FAIL`（继续修同一清单）；需要用户做新的业务裁决 = `STOP`。

**`PASS` 之前，被评审的产物不得进入下游冻结或交给自主执行。**

**常见坑**：

- **把它当第二轮评审用**：一旦开始找新问题，棘轮就重新转起来了，本 skill 存在的意义归零。
- **给子线程灌入期望答案**：证据包必须干净，否则它只会复述主线程的判断。
- **照单全改**：跳过逐条裁决 = 判失败。
- **疑似语义变化一律升级用户**：先查既有裁决和正式规格有没有唯一答案，有就直接恢复原义。
- **驳回不留证据**：凭直觉否决和照单全改是同一类错误的两面。
- **死亡线规则没有有效裁决记录却写"用户已批准"**：必须停机，这条没有例外。
