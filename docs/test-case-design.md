# test-case-design

> 把设计条目写成**施工前就冻结**的用例规格：每条断言有稳定编号、能对账、改不动——让"改断言让测试变绿"这条捷径彻底关闭。

## 这是什么

测试三件套的第二层——**用例层**。它把设计规范条目和正式规格转成可冻结的测试用例规格：定义断言、数据策略、自动化方式，并建立「设计条目 → 正式规格 → 断言编号 → 执行落点」的完整追溯链。

它的产出不是验收资产，而是**施工规格**：用例先于施工冻结，施工阶段不许因为代码跑不过就地改断言。

- **管**：用例规格字段、断言的原子化与编号、可对账判据、白盒/黑盒双视角、金标准用例的额外要求、冻结与变更留痕。
- **不管**：要不要测这个面（归 `test-standards`）、具体命令与脚本写法（归 `test-execution-router` 与项目执行 skill）。

## 解决什么问题

在 AI 写代码、AI 写测试、AI 自己判定"通过"的循环里，测试环节有一条几乎无法察觉的捷径：**代码跑不过 → 把断言改松 → 测试变绿 → 交付**。

它之所以难防，是因为改断言这个动作本身是合法的——脚本写错了本来就该改。区别只在于改完之后脚本是更接近规格还是更接近代码，而如果规格本身也能改，这两者就再也分不开了：

| 场景 | 规格说 | 代码实际 | 脚本原来 | 改成 | 这是什么 |
|---|---|---|---|---|---|
| A | 400 | 400 | 404（写错了） | **400** | ✅ 忠实化 |
| B | 400 | **404（有 bug）** | 400 | **404** | ❌ 作弊 |

除此之外还有几类反复出现的失效：

- **空壳用例**："测试新增接口是否正常"、"验证页面能打开"——写了等于没写。
- **断言写虚，对不了账**："应该失败"、"返回成功"、"数据落库了"——两个人照着它写脚本会写出完全不同的东西。
- **漏测无法机器判定**：断言没有稳定编号，就没法用检查器逐条去测试资产里找落点，"哪条被 skip 了"只能靠人肉读。
- **串行重放冒充并发验证**：涉及余额、限额、计数的写路径，顺序重放全绿、真并发才暴露不变量被破坏。
- **金标准形同虚设**：保护业务不变量的用例没有执行落点，等于没有。

## 为什么这么设计

- **用例先于施工冻结，且产自施工之外**：这是整套机制的地基。规格必须是施工够不着的裁判席——它一旦可变，作弊者就能"先改规格再理直气壮地改脚本"。
- **哈希锚在规格上，不锚在脚本上**：脚本有 bug 就得改，改了哈希就变，锚脚本必然死锁。所以冻结 `spec_hash`（规格全文）而不是脚本。计算时把 `spec_hash:` 那行替换成占位符再算，避免自引用。
- **粗锚 + 细锚两层**：`spec_hash` 是全文粒度，只能回答"动没动过"；`assertion_index` 冻结编号全集，才能回答"动了哪一条"。
- **断言必须有稳定编号 `AC-x`**：三层防线全部依赖它——编号覆盖检查器（机器判漏测）、`change_log`（点名追溯"AC-7 从 X 改成 Y，依据是…"）、红→绿翻转审计（定位是改代码还是改脚本变绿的）。编号删除后留空号、永不复用，否则历史链指向错误对象。
- **一条 AC = 一个可独立证伪的结果**：平台、入口、快/慢路径、成功/失败分支、边界前中后、并发/串行是不同的证明义务，必须拆开。一个用例可以编排多个 AC，反过来不行。
- **可对账用一句试金石判定**：*两个人拿着这条断言分别去写脚本，会写出行为相同的断言吗？* 不会就是写虚了。比任何"断言要充分"的形容词都可执行。
- **`required_test_shape` 把"怎么才算真证明了"写进规格**：并发语义必须真并发竞争、超时语义必须拆三个时间点、双路径必须各自取证并证明只派发一次。否则"测了"和"证明了"永远有缝。
- **字面编号只证明有落点，不证明覆盖**：所以终审必须打开测试落点核对语义与测试形状，不得仅凭检查器放行。这条是防止编号机制自己退化成走过场。
- **认为用例写错了 → 回炉，不是就地改**：带证据终止本次执行、退回设计步重来。把"改规格让测试变绿"明确定义成任务失败。

## 怎么用

**触发场景**：编写或审查正式测试用例层、补齐覆盖、施工前冻结用例规格。

**流程**：

1. **收集输入真值**：需求 → 交互 → 契约 → 数据库 → 客户端方案 → 服务端方案 → 轻量设计的规范条目与决策表 → 用户裁决记录 → 本次 diff。
2. **双视角推导**：白盒（分支、状态机、数据不变量、事务补偿、并发竞态）+ 黑盒（正向闭环、反向路径、空态错误态、多角色、真实链路组合）。
3. **写用例规格**：每条用例填齐字段，重点是 `assertions` 那张编号表。
4. **判定金标准**：保护死亡线区域业务不变量的用例升级为金标准，额外满足四条——不可删除、必须有执行落点、断言落到不变量本身而非某次调用返回值、至少含一条反例断言。
5. **冻结**：写冻结头（`frozen_at` / `design_refs` / `formal_spec_refs` / `spec_hash` / `assertion_index` / `change_log`），正式副本只留一份在正式用例层路径。

**断言表长这样**：

| id | verifies | assertion_kind | given | when | then | boundary | required_test_shape |
|---|---|---|---|---|---|---|---|
| AC-1 | SD-3 | contract | 请求缺必填项 | 提交请求 | 响应错误码 71001 | C 端接口 | 真实契约测试 |
| AC-2 | SD-3 | contract | 请求缺必填项 | 提交请求 | `retryable=false` | C 端接口 | 真实契约测试 |

注意 AC-1 和 AC-2 是同一次请求的两个结果——**拆开，不合并**。

**常见坑**：

- **想冻结测试脚本的哈希**：脚本必须可改，锚在脚本上会死锁。锚只能锚在规格上。
- **断言引用了上游不存在的东西**：AC 新增了设计里没有的状态分支、错误码或时点口径 = 测试层越权造规则，退回设计或用户裁决，不得冻结。
- **把"设计没说"当成冲突上报**：设计**选错了**是翻案（不许，走上游评审）；设计**没说**是缺陷（必须放行并回填）。这两者处置完全相反。
- **金标准没有执行落点**：无 `execution_ref` 的金标准视为未生效，等于没写。
- **模拟绿不标保真度**：用替身替代真实外部依赖必须标 `simulated`，并写明真实链路在哪里收口。
- **冻结后改了断言却不写 `change_log`**：哈希变了而变更记录为空 = 违规改判。
