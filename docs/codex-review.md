# codex-review

> 施工完成后的低成本符合性核验。它最危险的失败模式不是"漏看 bug"，而是**把已拍板的正确做法当成 bug 报上来、又被照着改掉**——整个 skill 都在堵这个口子。

## 这是什么

施工链路的**收尾核验层**：代码写完之后，由外部单模型对照已冻结的正式规格、规格物化覆盖报告、执行契约与工程红线，查"实现有没有偏离已拍板的东西"。

标准答案是冻结的规格本身。轻量设计只用来解释设计条目的由来，不能覆盖正式规格——两者不一致说明物化环节失效，应该返闸，不由评审者选边。

- **管**：已写完代码的低中风险符合性核验、意见的三级分类与分流台账。
- **不管**：还在定方案时的探索（→ `adversarial-review`）、执行契约的开工前红队（→ `adversarial-review` 章程口径）、高风险或逻辑密集代码的正交审查（→ 升档）。
- **不是门禁**：不卡开工、不卡交付，只在用户主动要求时跑。

## 解决什么问题

事后代码评审有一个反直觉的主要风险：**评审者缺乏前面多轮讨论的背景，会把刻意的取舍误判成缺陷**。最隐蔽的一种是——评审者根本不知道某个做法是已拍板的决策，于是理直气壮地把它标成"违反规范"，然后被照着改掉，把正确的实现改坏。

具体形态：

- **把已批准的合法偏离报成范围蔓延**：自主执行期间按契约授权做的自愈，如果不把留痕清单交给评审者，会被整片报成"违反规格"。
- **拿过期规格评新代码**：覆盖报告里的哈希和当前冻结件对不上，于是"按新决策改对的地方"被报成"违反旧决策"。
- **打包者主观挑上下文**：作者觉得"这些周边不重要"就不给，而作者盲区恰恰就是漏给的那部分。
- **只给代码 diff**：漏掉暂存区、未跟踪文件和新增文件——而新增文件正是范围蔓延最该看的对象。
- **自由心证**：既没有冻结规格也没有决策表，评审失去标准答案，退化成"评审者觉得应该怎么写"。

## 为什么这么设计

- **默认方向是「不改除非已证实是缺陷」**：证据责任压在"改"这一侧，不是压在"不改"这一侧。这一条是全 skill 的地基。
- **有标准答案的核验，单模型够用**：符合性核验是对照答案查偏差，硬上多方对抗既贵，又会把已拍板的取舍翻出来重吵——那正是要堵的风险。
- **但明确不宣称"单模型够全部代码审查"**：代码评审里最高价值的发现常常是"答案没覆盖到的地方出了 bug"——并发竞态、边界态、错误处理、性能。规格通常不下沉到逻辑级（实现细节属代码自由范围），这类问题需要正交视角，单模型会系统性漏检。所以设**升档硬门**。
- **升档是运行前的强制筛查，不是事后自觉**：这个 skill 便宜、能高频跑，定位本身就诱导"默认都走它"。所以筛查结果要写进评审记录，否则等于没筛。两条维度正交：命中死亡线/钱权数据/不可逆/对外契约/上线安全 → 升档；实现含并发、状态机或边界密集逻辑而冻结规格未下沉到逻辑级 → 也升档。
- **三个角色必须拆清**：施工者（写代码的）、评审者（外部模型）、分流责任人（主线程编排者）。分流责任人**没有独立模型，且常常就是或紧邻施工者**——"作者裁自己代码的评审"这个护短风险是真实存在的，所以证据纪律全部为对冲它而设。
- **前置门先验明答案本身**：规格已冻结、覆盖报告全绿、**输入新鲜度**（哈希与当前冻结件一致）、**自主执行的留痕清单**（这是"已批准的合法偏离"清单，不给它评审必然误报）。答案不可靠时评审建在沙上。
- **承重上下文用触发式，不靠主观裁剪**：被改文件命中承重面、跨域入口、数据结构、配置、迁移或外部契约时，用类型系统与调用图把直接调用方与被调方拉全。这与设计阶段防"伪全集"是同一个道理。
- **它在自主执行之外，这是有意的**：执行内部的审核只能是闭环内的自审与机器检查器，引入循环外观点会带来场景与上下文不同的噪音。本 skill 是**事后的、用户主动要的第二双眼睛**，不是执行工序。
- **缺决策表不等于拒评**：有一类合法施工经风险筛查证明无事故级决策，因而没走轻量设计。这恰恰是评审者最没背景、最易误判的一类，走退化基线（正式规格 + 覆盖报告 + 执行契约）照常评。

## 怎么用

**触发**：用户手动说"跑一遍代码评审"。不挂门禁、不自动触发。

**什么时候用**：一段代码写完、决策已冻结，想要一道独立的实现核验。

**什么时候改用别的**：

| 场景 | 改用 |
|---|---|
| 还在定方案、设计待探索 | `adversarial-review` |
| 执行契约的开工前评审 | `adversarial-review` 章程口径 |
| 既无冻结规格也无决策表、也无退化基线 | 先补设计，否则评审退化为自由心证 |
| 命中升档硬门 | `adversarial-review` 代码模式（复用同一份冻结真值） |

**流程**：

1. **过前置门**：规格冻结状态、物化报告全绿、输入新鲜度、自主执行留痕清单、升档筛查——逐项确认并记录。
2. **打包输入**：代码 diff（原样内嵌带路径行号）+ 工作区真实状态（含暂存/未跟踪/新增文件）+ 触发式承重上下文 + 已冻结真值 + 验证转录（已跑的命令与结果、未跑项及原因）+ 验收条件 + 工程红线原文（内嵌，不写"参考某文档"）+ 射程切分声明。
3. **跑评审**：单模型，意见带严重度与证据类型（实测失败 / 文本违反 / 逻辑反例 / 推断风险）。
4. **分流**：三级分类——确证缺陷改掉 / 待裁定的留着 / 需要上浮的上报。默认方向是不改。
5. **判断是否返闸上游**：如果触及承重面或证明上游规格错了，默认热修（附修改方案经业务决策负责人按项目治理批准后修订上游并回原执行续跑），热修不可靠且获相应批准才回炉退回设计步；两条路都不在评审这层硬改。

**常见坑**：

- **不给自主执行的留痕清单**：合法自愈会被整片报成违规，这是最高频的误报来源。
- **只给 `git diff`**：新增文件和未跟踪文件看不到，范围蔓延正好藏在那里。
- **红线写成"参考某文档"**：必须摘出适用条款内嵌原文，外部模型读不到你的项目文档。
- **拿它当门禁**：它不卡开工也不卡交付，做成门禁就会变成新的评审棘轮。
- **该升档不升**：便宜好跑是它的优点，也是它最容易被滥用的地方。筛查依据不写进记录 = 没筛。
- **只指轻量设计就判"缺陷"**：判定必须同时指向正式规格或红线，否则不成立。
