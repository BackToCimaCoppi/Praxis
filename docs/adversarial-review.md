# adversarial-review

> 同一份内容，让 Claude(Opus) 和 GPT(5.5) 各出一份独立评审，再由 Opus 当裁判逐条裁决采纳/驳回，产出一份经得起挑战的报告。给"定稿前要做高规格交叉审查"的人用。

## 这是什么

adversarial-review 是 ask-claude / ask-opus 的**上层编排**。主线程把待评审内容（设计文档 / 代码 / 任意方案）打成证据包，并行起两个独立评审者，最后跑裁判轮收口：

- **评审者 A**：Claude（默认 Opus），用 Agent 工具。
- **评审者 B**：GPT（gpt-5.5，超强思考），用 codex 调用。
- **裁判**：Claude（默认 Opus），用 Agent 工具，逐条裁决并写报告。

它管：打证据包、并行发起双评审、跑裁判轮、验收并报告路径。流程只有一条，没有模式分支。

它**不管**：身份隐瞒（不藏方案出处，只做清晰角色设定）；也不替方案辩护——裁判只判"批判有没有道理"。证据包方法论复用 ask-* 的 `dispatch.md`（RAM 框架），本 skill 只补对抗评审专属规则。

## 解决什么问题

单份评审、或自己审自己，会遇到：

1. **盲区重叠**：一个评审者有固定的关注点和盲区，漏掉的地方没人补。
2. **生成语境惯性**：方案出自某个模型，让它自己复查时仍带着"让方案自洽"的目标，发现不了设计时忽视的边界。
3. **噪声无人收口**：两份评审难免有相互矛盾、有凑数的批判，没人裁决就只能囫囵全收或全弃。
4. **并发串台**：多个评审任务同时跑，临时文件用固定名会互相覆盖，A 读到 B 的 prompt。

## 为什么这么设计

1. **视角正交**：Claude 和 GPT 是两套不同模型，关注点、盲区、偏好都不同，合起来覆盖面远大于任一单审。
2. **评审 ≠ 生成语境**：哪怕同型号模型，切到"评审者"角色（目标是找漏洞、找边界、找过度设计）也能发现设计时的盲区——认知工具不同。
3. **裁判收口**：Opus 裁判把两份评审合并去重、逐条裁决，收敛成一份内聚结论；对初判驳回的意见做"自我反驳复核"（成立需要哪些前提 + 前提有无证据），有证据才翻转。
4. **抵消同源亲和**：裁判与评审者 A 同为 Opus（Claude 占两席），裁判 prompt 内置抵消指令——对 A 侧批判不接受"无证据采纳"，并如实标注采纳来源分布，防止系统性偏向同源一侧。
5. **mktemp 隔离**：临时文件用 `mktemp -d` 的唯一后缀按"运行实例"隔离，而非路径哈希——哈希挡不住两个并发 agent 写同一报告路径，唯一后缀能。

## 怎么用

1. **触发词**："克劳德评审"、"对抗评审"。

2. **流程**
   1. **打证据包**：评审对象**逐字内嵌、不压缩**（它是评审的宾语，压了就没法评）；周围的约束 / 判断标准 / 背景按 dispatch 最小化压缩。对象超大撑爆上下文时才改用"同一份最小必读清单"钉死对象。
   2. **要输出路径**：用户没给就开口问"评审报告写到哪个文件？"，不允许 Claude/GPT 自己决定。
   3. **派生 scratch**：跑一次 `mktemp -d` 生成本轮专属临时目录，记住 echo 出的 `ABS_REPORT` 和 `SCRATCH` 两个字面值，后续 Bash 调用直接粘字面值，不要重跑 mktemp。
   4. **并行双评审**：同一份对象 + 同一套批判者角色，分别发给评审者 A（Agent/Opus，`run_in_background`）和评审者 B（codex/gpt-5.5，`run_in_background`）。两者互不等待。
   5. **收齐结果**：A 的输出存为 C_claude；B 的输出经文件中转——codex 后台退出后再起一次 Bash `cat "$SCRATCH/gpt-out.txt"` 取 C_gpt（不在退出通知里）。
   6. **裁判轮**：把"评审对象 + C_claude + C_gpt"发给裁判（Agent/Opus），逐条裁决采纳/驳回，写报告到指定路径。
   7. **验收**：报告非空、每条意见有 ✅/⚠️/❌ 标签 + 来源、驳回项留有复核痕迹、无越界写入 → 向用户报告路径 + 采纳 N 条 / 驳回 M 条。

3. **最小示例**

   输入：用户说"对抗评审这份设计文档，报告写到 review.md"。
   主线程内部跑：
   ```
   ① 证据包：设计文档全文内嵌 + 适用约束原文 + 输出路径 review.md
   ② 派生 scratch：mktemp -d → 记住 ABS_REPORT / SCRATCH
   ③ 并行：Agent(opus, 批判 prompt)  ‖  codex exec(gpt-5.5, 同一份批判 prompt)
   ④ 收齐 C_claude + C_gpt
   ⑤ Agent(opus, 裁判 prompt) → 写 review.md
   ```
   产出（review.md）：含"意见逐条裁决"（每条带来源 Claude/GPT/两者、裁决标签、理由、驳回复核）、"修正后的最终结论"、"驳回意见汇总"、"双方共识与分歧 + 采纳来源分布"。

4. **常见坑**
   - **把评审对象也压缩了**：对象必须逐字内嵌，压缩的只是它周围的约束和背景。
   - **重跑 mktemp**：mktemp 是随机的，后续 Bash 重跑会建新空目录、丢掉已写的 prompt——只能粘记住的字面值。
   - **以为 codex 结果在退出通知里**：codex 的 stdout 被重定向到 log，C_gpt 只能从 `gpt-out.txt` 文件取，必须再起一次 Bash 读。
   - **用前台长 timeout 跑 GPT**：Bash 前台单次上限 10 分钟，容不下最长 30 分钟的评审，codex 必须走后台。

---

> 配合使用：日常单方问答 / 派活用 ask-sonnet 或 ask-opus；需要 Claude + GPT 双评审才用本 skill。证据包方法论与这两个 skill 共用 dispatch 的 RAM 框架。
