# adversarial-review

> 同一份内容，默认两个不同模型（用户点名时最多五个）**独立**找问题，主线程逐条裁决。同一对象**只开放一次**——评审是用来发现问题的，不是用来无限加码的。

## 这是什么

一次开放式的多模型评审。主线程把待评审内容（设计 / 用例 / 执行契约 / 高风险代码 / 任意方案）冻结成证据包，并行发给默认两个不同模型（用户明确点名时可再加入最多三个可选模型）；每名评审者必须先在授权的项目根内**亲自做一次独立只读勘察**，再各出一份独立意见；然后**由主线程自己**合并、去重、编号并逐条裁决，裁决完成后再对实际参与的模型逐个点评、排名。

它是"发现"环节；"验收整改是否落实"是下一道工序（`closed-remediation-review`）。

角色分工：

| 角色 | 谁 | 权限 |
|---|---|---|
| 评审者 A（默认） | 本工具的原生子代理，Fable 5（`model: "fable"`） | 项目根内只读发现 |
| 评审者 B（默认） | 外部模型 codex GPT-5.6-Sol，reasoning max | 项目根内只读发现 |
| 评审者 C（可选） | Cursor Grok 4.6 Extra High（`cursor-grok-4.6-xhigh`），经 `scripts/cursor-review-runner.sh` 只读 ask 模式 | 项目根内只读发现；仅用户明确点选时加入 |
| 评审者 D（可选） | Cursor GLM 5.2 Max（`glm-5.2-max`），同上 | 同上 |
| 评审者 E（可选） | Cursor Kimi K3 Max（`kimi-k3-max`），同上 | 同上 |
| 裁决者 | **当前主线程本人** | 只裁决，不发明新设计 |
| 整改验收 | `closed-remediation-review` | 固定范围只读检查（单个 Opus 5 子线程） |

**可选评审者的点选规则**：C/D/E 默认全部关闭、各自独立点选——只有用户明确写出"加入 Grok / GLM / Kimi"，或对带该模型名称的选项答"是"才加入；"全部模型 / 五模型"表示三者都加；只说"三模型""多加一个"无法确定是谁，必须先让用户点名。AI 不得因模型可用、任务复杂或死亡线命中而自动加入，也不得为了询问 C/D/E 而阻塞常规评审。

**全员禁 Fast**：任何评审者的模型 ID 不得以 `-fast` 结尾，也不得开启 Claude Code fast mode 或等价的速度模式。Fast 不是思考强度——用户要"快 / 省"时只能在非 Fast 思考档内降档（A 固定 Fable 5 不换模型，B 把 reasoning 降到 high）。需要把 A 钉死在 xhigh 推理档时，改走只读 CLI 路线：`claude -p --model claude-fable-5 --effort xhigh`，工具面只给读取与检索。

- **管**：冻结评审身份与证据包（含授权项目根与读取/动作禁区）、并行取得全部已选评审者带调查账的独立意见、逐条裁决、裁决后点评并排名参与模型、交接给封闭验收。
- **不管**：替用户选择业务语义（评审只能暴露缺口）、身份隐瞒（不藏方案出处）、替方案辩护。

## 解决什么问题

**第一类是单份评审固有的**：

1. **盲区重叠**：一个评审者有固定的关注点和盲区，漏掉的地方没人补。
2. **生成语境惯性**：方案出自某个模型，让它自己复查时仍带着"让方案自洽"的目标，发现不了设计时就忽视的边界。
3. **噪声无人收口**：两份评审难免相互矛盾、夹带凑数意见，没人裁决就只能囫囵全收或全弃。
4. **并发串台**：多个评审同时跑，临时文件用固定名会互相覆盖。

**第二类更致命，是评审机制自身的退化**：

- **评审棘轮**：R1 提一批意见，改完跑 R2 又提一批新的，R3 还有。每一轮都能发明新要求，而新要求几乎总是"更严"的方向——漏一条是事故、多加一条叫严谨。评审于是从质量手段变成无限循环，最后停在半改状态。
- **评审者给下游加门禁**：意见里写"建议此处增加人工审批"、"应设为硬门"——评审结论本是信息，一旦被当成门禁写进下游，就永久地多了一道闸。
- **评审越权定义业务语义**：评审者提出一个"更合理"的业务规则，被当成结论采纳，而用户从没拍过这个板。
- **凑数的阻断项**：评审者觉得"一条问题都没有显得我没干活"，于是把可选优化升级成阻断级。

## 为什么这么设计

- **视角正交**：不同模型的关注点、盲区、偏好都不同，合起来覆盖面远大于任一单审；默认两套已足够正交，第三方模型只在用户点名时加入，避免"多模型"本身变成新的堆料棘轮。
- **评审 ≠ 生成语境**：哪怕同型号模型，切到"评审者"角色（目标是找漏洞、找边界、找过度设计）也能发现设计时的盲区——认知工具不同。
- **取消独立裁判轮，改由主线程裁决**：主线程本来就持有这次任务的全部上下文和真值基线，另起一个裁判线程既多一次模型调用，又要把上下文重新喂一遍——上下文越传越薄，裁判反而比主线程更容易判错。
- **评审身份用哈希锁定，同一身份只开一次**：用评审编号 + 对象哈希 + 真值基线哈希标识身份，同一阶段、同一基线、同一对象不得开第二轮。**这是反棘轮的核心机制。** 只有用户裁决、上游正式真值或对象发生根本重写时旧身份才失效，且必须登记失效原因和新哈希——措辞修订、补引用、落实上一轮整改都不构成新对象。
- **评审意见不是真值**：会改变业务结果、接口契约、持久化语义或死亡线规则的选择，必须追溯到正式上游规格或由业务决策负责人作出的可审计裁决记录。**没有来源只能升级到对应授权角色，不能自己定。**
- **给评审者写死禁令**：不许批判有正式来源的"已决策·不得重开"项、不许把候选方案写成已批准、不许因理论上可能而升级阻断、**不许建议给下游新增无依据的审批或人工门**。
- **严重度预算 + "没有阻断是有效结论"**：阻断级原则上 0–3 条，超出必须逐条证明不是同一根因；每条要回答具体失败场景、违反哪份冻结真值、为什么不能在施工中确定性自愈。明写"不得凑数"，是因为凑数是评审者的默认倾向。
- **钉对象，不钉视野；读得宽，评得窄**：全部已选评审者必须评同一对象、同一真值基线和同一口径，但**必须**各自在授权项目根（默认取被评审对象所在的 Git 工作树根，不得为了省上下文缩成对象所在目录）内做独立只读勘察——证据包只是冻结核心与调查种子，不是穷举白名单；两边发现路径可以不同，补读结论要给精确位置。调查得到的背景只能用来判断冻结对象，不能借此重开已决策项或改评整个项目。**禁止用摘要替代被评审对象**。
- **勘察是义务，不是许可**：只写"可自行补读"，评审者往往直接基于种子材料作答。所以要求每份意见先交一份精简调查账（冻结核心已读项 / 自主发现的关键文件与检索主题 / 反证与覆盖边界 / 未能访问或缺失的信息），用它区分"独立调查后无问题"和"只读了证据包后无问题"；授权范围内的材料因通道能力读不到，登记为信息缺口（INFO-GAP），不许猜。
- **证据包本身也受审**：评审者要核验起始材料是否漏了冲突真值、关键生产者/消费者或已失效的内容，发现缺口按事实报告——不能默认制包方天然完整。
- **开放的只是项目内只读发现，不是所有工具**：禁止读本地环境文件、私钥、凭据存储、认证缓存和主线程的裁决草稿；禁止执行测试/构建/迁移、联网、访问外部系统、派生子代理。触碰禁区立即判该方失败。
- **先裁决、后评分**：全部意见裁决完成后，主线程再按"模型 + 通道"对实际参与者做任务内点评和不并列排名，只看最终确认成立的贡献和误报成本，不按原始问题数量。排名不得反向改动任何裁决，也不能当作再开一轮的依据；通道工具面的限制要与模型能力分开记，不把信息缺口评成模型漏报。
- **评审者之间不得互读输出**：一旦能看见对方的意见，独立性当场消失，多份评审会退化成一份。
- **禁 Fast 是硬约束而非偏好**：Fast 档牺牲的是推理深度，而评审的全部价值就在推理深度；"快 / 省"只允许在非 Fast 思考档内降档，且不得换掉模型后仍宣称完成了多模型对抗。

## 怎么用

**触发词**："克劳德评审"、"对抗评审"。

**流程**：

1. **冻结评审身份与证据包**：评审编号、对象哈希、真值基线哈希；评审对象——短小、临时或评审通道读不到的内嵌全文，同一工作区内的大对象给绝对路径 + 哈希 + 精确范围，**禁止摘要替代**（它是评审的宾语，摘了就没法评）；正式真值基线；"已决策·不得重开"区（每项须引用正式规格或裁决记录）；本次口径卡；授权项目根、起始导航、禁止读取项与禁止动作；输出格式与严重度预算。
2. **要输出路径**：解析成绝对路径且位于用户授权的任务目录。临时目录每轮独立生成，不用全局固定名。
3. **并行发起全部已选评审**：默认 A（Fable 5）+ B（GPT-5.6-Sol max），用户点名的 C/D/E 一并启动；同一对象、同一真值基线、同一套评审者指令，互不等待、互不可见。启动前核对每个模型 ID 均非 Fast；Cursor 评审者要先确认已登录且模型清单里有精确 ID，未登录走远程登录或终止，缺 ID 直接终止，禁止用 Auto 或其他档位顶替。任一已选评审者启动失败重试一次仍失败就终止，不把缺席阵容冒充完成。每位评审者先在项目根内独立勘察，输出调查账，再列发现。没做勘察或缺调查账的，用同一证据包重试一次，仍缺就判该方失败。
4. **主线程逐条裁决**：合并去重、分配意见编号、逐条判采纳或驳回。需要业务决策负责人批准的合并成一张表集中询问；项目要求会签时照常执行，并逐项记录实际授权角色与裁决。
5. **点评并排名参与模型**：裁决全部完成后，主线程对全部实际参与者（A–E 中实际启动的每一个"模型 + 通道"）写一句优势、一句短板和本次任务适配结论，给出不并列的名次，并记录各通道实际工具面与信息缺口。
6. **整改并冻结整改清单**，然后转 `closed-remediation-review` 做封闭验收。
7. **验收通过才允许下游继续**。

**口径卡**：设计评审 / 用例评审 / 章程评审各有一张，放在 `references/profiles/`。章程口径卡的四问里有一问专门找"边界太紧"——因为其余三问都在找"太松"，缺了它红队本身就是棘轮。

**常见坑**：

- **把评审对象也压缩了**：对象要么逐字内嵌，要么给精确路径 + 哈希 + 范围让评审者自己读原文；能压缩的只是它周围的约束和背景。
- **用证据包清单封顶视野**：把项目根缩到对象所在目录、或用文件白名单代替项目根，跨文件影响面会被人为截断。证据包是准入下限，不是调查上限。
- **接受没有调查账的"无问题"**：没有证据表明做过证据包外的独立发现，就分不清是真没问题还是没看。
- **把通道读不到评成模型漏报**：先修通道或重制可访问的证据包；信息缺口和模型能力要分开记账。
- **想再跑一轮 R2**：同一身份只开一次。整改验收走封闭工序，不是重新开放找问题。
- **换掉模型后仍宣称完成了多模型对抗**：要求"快/省"时只能在非 Fast 思考档内降档，不能换模型还说做了对抗评审；报告首部"评审模型"默认写 `Fable 5 + GPT-5.6-Sol max`，按实际点选追加，记录实际模型 ID。
- **任何一处出现 Fast**：模型 ID 以 `-fast` 结尾或开了 fast mode，启动前就终止并改回非 Fast 精确 ID，不以低延迟为由继续。
- **自作主张加第三方评审者**：任务复杂、死亡线命中都不是理由；C/D/E 只认用户明确点名，而且不能为了问"要不要加"而卡住常规评审。
- **Cursor 模型缺席就拿别的顶替**：所选精确 ID 不在账户模型清单里，或未登录，只能远程登录或终止；Auto、High、Low 档位都不是等价替身。
- **让评审者互相看输出**：独立性是这个机制的全部价值来源。
- **把评审报告当规格**：正式规格层才是长期真值，评审报告只是发现与裁决的过程证据。
- **对无来源的意见照单全改**：涉及业务语义的必须先有业务决策负责人的可审计裁决，否则只能升级询问。
