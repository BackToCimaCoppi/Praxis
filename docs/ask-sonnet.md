# ask-sonnet

> 让主线程把活儿"派给"一个干净的 Sonnet 子线程：主线程负责收集弹药，Sonnet 负责深度推理或动手干活。给需要省 token、又想保证推理质量的人用。

## 这是什么

ask-sonnet 用 Agent 工具起一个 Sonnet 子线程，把"深度推理 / 方案设计 / 代码生成"外包出去。它定义了一套分层协作：

- **主线程（你）= L1 信息收集者**：读文件、定位事实、把上下文压缩成一个"最小充分包"。
- **子线程（Sonnet）= L2 推理者**：在干净的上下文里只处理你精炼好的包，做判断、出方案、写代码。

它管两件事：**问模式**（Sonnet 只读不改，输出分析结论）和**派模式**（Sonnet 在授权范围内动手改文件）。

它**不管**：自动判断该不该调子线程——这是用户的分工权，不说触发词主线程就自己处理；也不替子线程做结论——结论永远是子线程的职责。

## 解决什么问题

不用它，直接把所有上下文丢给强模型，会遇到：

1. **token 浪费**：读几百行文件的成本也由强模型承担，账单飙升。读文件本不需要深度推理。
2. **注意力稀释**：把几百行原始代码原样喂给模型，它的注意力被无关内容分散，真正该判断的地方反而没力气抠。
3. **越俎代庖**：你把"这段代码符合规范"当结论写进 prompt，子线程没法独立验证约束是否真的满足——你替它思考了，它只能照单全收。
4. **派活失控**：让模型直接改代码，它可能改了一堆你没授权的文件，事后无法纠正。

## 为什么这么设计

1. **L1/L2 分层**：信息收集（廉价、机械）和深度推理（昂贵、需要算力）拆开，各用各的成本档位。主线程做"找到什么、整理成什么格式"，子线程做"判断"。
2. **传原文，不传结论**：约束条件一律内嵌**原文**（如"for/stream 中不得调 Dao/Service"），不写成"代码符合 N+1 规范"。原文让子线程自己验证，结论剥夺了它验证的能力。
3. **给清单，不设路障**：文件清单是"最小必读"（保证不漏关键信息），不是"只准读这些"。子线程是更强的模型，它判断要补读就放手让它读。但放开的只是**读**——派模式能写哪些文件仍被授权边界死死限定。
4. **来源声明**：子线程不知道你读了什么、漏了什么。必须显式写"L1 信息来源声明"，否则它会基于错误假设作答。

## 怎么用

1. **触发词**
   - 问模式："问一下sonnet"、"问一下claude"
   - 派模式："让sonnet去做"、"让claude去做"
   - 不说触发词 → 主线程自己处理，不调子线程。触发词模糊 → 先问"问模式还是派模式？"

2. **流程**
   - **问模式**：
     1. 判断问题类型，按槽位（具体问题 / 文件引用 / 背景事实 / 约束条件 / 判断标准 / 外部信息）选填上下文
     2. 每项过 RAM 检验句：「Sonnet 需要 [这项]，才能 [回答问题]，否则卡在 [具体卡点]」，填不完整就删
     3. 写"L1 信息来源声明"（交付形式、已读文件清单、未纳入的已知信息）
     4. 用 Agent 工具（model: sonnet）发出，prompt 末尾声明"不要改任何文件"
     5. 消化结论，用自己的话回答用户，附上独立判断
   - **派模式**：
     1. 发任务 + 验收标准 + 禁止区 + 约束（不预设文件清单）
     2. Sonnet 探索代码，先回"改动范围计划"
     3. 主线程确认/调整范围 → Sonnet 施工
     4. 主线程按验收清单（范围 / 编译 / 约束 / 验收标准 / 越界）逐项检查 → 报告用户

3. **最小示例**（问模式）

   输入（主线程发给子线程的 prompt）：
   ```
   这个分表方案在百万级数据下会不会有性能问题？

   L1 信息来源声明：
   - 交付形式：直接回复，不写文件
   - 已读文件清单（最小必读，可自行补读）：
     - .../FollowBiz.java（只读：getFollowerList）
   - 未纳入本包的已知信息：无

   背景事实：
   - 分表策略：表名按 hash(uid) % 32
   - 当前数据量小，暂无性能问题

   约束条件：
   - 禁止 N+1 查询：循环内不许调 Dao，必须批量查询 + Map 关联
   判断标准：百万级场景单次请求 < 500ms

   输出要求：直接输出结论，不要改任何文件。
   ```

   产出（子线程返回 stdout，主线程消化后转述给用户）：一份结论，指出哪些查询会随数据量退化、是否触碰 N+1 红线、能否满足 500ms。

4. **常见坑**
   - **把原始代码整段贴进包**：200 行代码要先压成 3 行"这个方法做了什么"，否则稀释注意力。
   - **约束写成结论**："代码符合规范"是错的，要贴规则原文让子线程自己验。
   - **一次调用反复追问**：每次追问都开新的 Agent 调用，不要在同一个子线程里来回聊。
