# doc-layer-system

> 一套可执行的「七层文档体系」规则引擎：在 AI 驱动开发里，把每一类设计信息钉到固定的一层，并用人工裁决和死亡线机制兜住关键决策，防止文档与代码一起腐烂。

## 这是什么

doc-layer-system 是一个用户级通用 skill，描述一套贯穿「需求 → 交互 → 接口 → 数据库 → 前端实现 → 后端实现 → 测试」的七层文档体系。它规定了：

- 每一类信息该放在哪一层（分层规则）
- 文档和代码、或两层文档之间打架时怎么办（冲突分级 + 人工裁决）
- 改了某层之后，必须连带检查哪些下游层（变更钩子）
- 哪些代码区域 AI 不许自己拍板（死亡线审查）
- 开发任务从头到尾的文档同步流程

**管什么**：
- 信息的「归属层」裁决——"这个东西该放哪一层"
- 跨层 / 文档与代码冲突的处理纪律——"这几个文档矛盾了听谁的"
- 代码 / 文档改动后的同步与扫描流程
- 高保真决策（契约、数据库结构、核心业务链路、核心算法）的人工把关

**不管什么**：
- 不硬编码任何项目特定值（目录路径、业务域列表、死亡线区域清单、金标准领域清单、命名规范等）——这些全部交给**项目级补丁**填充
- 不替代具体的文档撰写工作（如 L5/L6 怎么落笔，由配套写作指南管；L1 反推由其他 skill 管）
- 不是任务管理工具，也不直接改代码

一句话边界：它是「规则」，不是「内容」。规则在这个 skill 里通用且开源；内容（你项目的真实路径和清单）由你自己的项目级补丁写。

## 解决什么问题

不用这套体系，AI 驱动开发里反复出现这些痛点：

1. **文档腐烂，越写越没人信**
   传统做法让文档「镜像代码」，代码一改文档就过时。久而久之，没人相信文档，验收只能去读代码——而读代码恰恰是 AI 协作里最该被替代的环节。

2. **AI 自作主张「对齐」，悄悄改坏关键逻辑**
   AI 发现接口文档和代码不一致，就自己按文档改了代码（或反过来按代码改了文档）。如果不一致的恰好是支付金额、鉴权方式、核心算法，这种「自动对齐」就是事故现场。

3. **改了一处，忘了连带的下游，联调时才爆炸**
   改了一个接口字段，忘了同步前端调用链路、后端处理链路、接口测试用例；改了一张表，忘了后端 ORM 和数据完整性测试。问题攒到联调或上线才暴露。

4. **信息无家可归，到处乱塞**
   业务规则被写进了接口文档，数据库约束被写进了后端代码注释，UI 颜色和业务逻辑混在一份文档里。问"这条规则在哪"，没人答得上来。

5. **关键决策被 AI 在施工时悄悄换掉**
   人明明拍板了「用复合游标翻页」「这一步要放在同一个事务里」，但这些决策没被锁在任何地方，AI 下次施工时换成了「页码翻页」「拆成两个事务」，看起来合理，实则违背了已定的结论。

## 为什么这么设计

### 核心机制一：七层定位，每层只回答一个核心问题

| 层 | 核心问题 | 与代码的关系 | 审核强度 |
|---|---|---|---|
| L1 需求 | 产品是什么形态、有哪些功能、业务规则如何 | 描述型 | 🔴 逐字审 |
| L2 交互规格（可选） | 交互流程、界面状态、视觉规格长什么样 | 描述型 | 🟡 方向性确认 |
| L3 契约（接口） | 系统对外约定什么字段契约 | 契约型 | 🔴 逐字审 |
| L4 数据库 | 数据如何存储（表/字段/索引/约束） | 契约型 | 🔴 逐字审 |
| L5 客户端实现规约（可选） | 前端用什么技术、走什么主要链路、守什么架构规范 | 设计型 | 🔴/🟠 |
| L6 服务端实现规约 | 后端用什么技术、走什么主要链路、守什么架构规范 | 设计型 | 🔴/🟠 |
| L7 测试用例 | 怎样验证上面各层的设计意图被正确实现 | 验收型 | 🟠/🟡 |

L2、L5 是**可选层**：纯后端、CLI 工具、数据管道这类没有独立客户端 / 无 UI 的项目，可在项目补丁里声明省略，直接从 L1 接入 L3/L4/L6/L7。

关键取舍：**L5/L6 是「设计型」层，不是代码镜像层。** 它们只锁三件事——架构骨架与禁止模式、跨模块红线、核心业务链路与关键技术选型。纯实现细节（私有方法、SQL、DTO 转换、标准 CRUD）以代码为准、不进文档。正因为不追代码细节，L5/L6 才**不会腐烂**。这是整套体系敢于「文档 > 代码」的根基。

### 核心机制二：冲突分级 + 人工裁决（推翻「AI 自动对齐」）

这是本体系相对旧式文档法最大的改动：**禁止 AI 用「裁决链」自动修正它认为低优先级的那一层。** 发现不一致一律分级：

| 级别 | 典型情形 | AI 动作 |
|---|---|---|
| L0 表面冲突 | 措辞 / 排版 / 同义词差异 | 可直接按上游对齐，无需停机 |
| L1a 局部语义冲突 | 单一未发布功能内的规则不一致 | 标注延后，当轮可继续，但合并前必须裁决 |
| L1b 跨域语义冲突 | 跨已发布功能 / 跨域 / 命中死亡线 | 立即停止，报告，等人裁决 |
| L2 契约破坏冲突 | 接口签名 / 字段类型 / 表字段名 / 枚举 / 鉴权方式不一致 | 立即停机标红，默认拒绝继续，必须人裁决解锁 |

裁决链（L1→L2→…→L7）的唯一用途，是告诉**人**"理论上谁优先"，供人决策时参考——绝不允许 AI 拿它当自动执行的依据。

### 核心机制三：变更钩子，改一处自动扫下游

每类改动都对应一张「必须扫描的下游层」清单。例如改 L3 接口 → 必扫 L5/L6/L7；改 L4 表 → 必扫 L6 和实现验证测试；改了 Service 业务规则的代码 → 必扫 L1 业务规则、L6 状态机、L7 金标准。钩子分三层落地：AI 主动扫描、可选的 `post-change-check` 脚本、评审拦截。

### 核心机制四：死亡线审查（AI 不许独自拍板的区域）

死亡线 = 用户必须亲自审查、AI 不能独自决定逻辑的代码区域。体系自带一份**通用最小兜底清单**，无需任何项目补丁即时生效：

- 支付 / 计费 / 退款 / 优惠权益
- 鉴权 / Token / 密码 / 密钥
- 用户数据删除 / 批量更新 / 数据迁移脚本
- 第三方平台回调（支付 / 认证 / OAuth）
- 涉及金额、用户身份、隐私字段的 SQL / 批处理脚本

AI 一旦触碰，必须标记死亡线变更、通知项目补丁声明的真实审查人、确认对应金标准测试，并通过「死亡线最小准入四件套」（命名审查人 / 列出审查对象 / 关联验证证据 / 留下可追溯记录）才能继续。即便 AI 有 99% 信心逻辑正确，也必须人审。项目补丁只能在这份兜底清单上**叠加**自己的核心算法区域，不能删减。

### 核心机制五：用户级通用引擎 + 项目级补丁挂载点（这是它能开源的关键）

整套规则被切成两半：

- **通用引擎（在本 skill 里，开源共享）**：七层划分、冲突分级、变更钩子、死亡线兜底清单、审核强度、同步流程——这些跨项目通用，不含任何一个项目的私有信息。
- **项目特定值（不写进本 skill，由使用者自己的项目级补丁填充）**：真实目录路径、业务域 / 模块列表、本项目额外的死亡线区域、金标准领域清单、命名规范、HTTP/鉴权约定、审核角色绑定、单文档行数上限、`execution_ref` 格式等。

skill 正文里凡是出现 `{docs_root}`、`{NN}-{domain_name}`、`示例（MyApp）` 的地方，都是**补丁挂载点**——通用规则给出占位模板，真实值由你项目的补丁来填。这样同一份引擎可以被任何团队拿去用，私有信息留在各自仓库，互不污染。这正是它能作为开源方法论库招牌的原因。

## 怎么用

### 1. 触发词

下列场景会触发本 skill：

- 写 / 改了代码或文档后需要**同步**
- 新增接口 / 数据库 / 页面功能
- 执行代码审查（如 `/review`）、编写测试用例
- 处理「文档和代码矛盾了」「这几个文档矛盾了听谁的」
- 询问「这个东西该放哪一层」

### 2. 流程：一步步走查

**第一步——先建项目级补丁（首次接入时一次性完成）。**
通用引擎不知道你的路径和清单，必须先有补丁。在你项目自己的项目级补丁 skill（见 `templates/项目级补丁模板/`）里声明：

- 项目形态（全栈 / 纯后端 / 纯前端），据此裁掉不适用的层
- 业务域 / 模块列表、各层 `docs_root` 真实路径
- 本项目额外的死亡线区域、金标准领域清单
- 命名规范、单文档行数上限、审核角色绑定等

> 项目特定值不写进 doc-layer-system 本体，而是按**项目级补丁模板**写成你自己项目的补丁来填充。本 skill 永远保持通用、可开源。

**第二步——开发时按工作模式走同步流程。**

- 新增功能：确认 L1 → 更新 L2（如适用）→ 更新 L3+L4 并经用户确认 → 编码 → 核对 L5/L6 链路 → 更新 L7 → 评审。
- 改现有功能：先判断改动范围（仅实现优化 / 改接口数据库 / 改功能设计），从对应层起步，先改文档经确认再改代码，最后更新 L7。
- 任何一步发现两层不一致 → **停下，按冲突分级走人工裁决**，不自行修正。

**第三步——改动后跑变更钩子自检。**
对照改动来源查「必扫下游」清单，逐项确认；命中死亡线区域则走死亡线四件套；涉及业务不变量则确认金标准用例。

### 3. 最小示例：输入 → 产出

**输入**：给后端某域新增一个「订单列表」接口，按时间倒序分页。

**产出（按层落位）**：

```
L3 接口契约（🔴 逐字审，先于代码）
  GET /orders
  请求：cursor（选填，上次响应返回的 cursor 值）、limit（选填，默认 10）
  响应：列表 + 下一页 cursor
  → 用户确认后置为「已审核」，契约冻结

L6 后端实现规约（设计型，只锁决策点，不贴代码）
  3.x 订单列表翻页
  | 决策点 | 选定 | 放弃 | 为什么 |
  |--------|------|------|--------|
  | 翻页方式 | 复合游标（创建时间+id） | page/pageSize | 偏移翻页并发写入下会重复/漏行 |
  🔑 施工红线：游标必须带 id，只带时间戳会在同时间戳跨页时静默漏数
  代码锚点：OrderQueryService

L7 测试用例
  契约测试：验证 cursor 翻页字段与错误码
  金标准（若涉及业务不变量）：标注守护的 L1 不变量 + execution_ref
```

注意 L6 那条**没有一行代码、没有 `文件:行号`、没有置信度尾注**——它只把「为什么是复合游标」这个决策锁死。AI 拿到它，就不可能擅自改回页码翻页。这正是设计型层该有的样子。

### 4. 常见坑

- **把 L5/L6 写成代码法证报告**：逐方法复述「A 类调 B 类、B 类调 C 类」，满篇方法签名和证据尾注。这是反推时最容易犯的错——代码一改全错，必然腐烂。L5/L6 只写「做了什么决策、为什么、放弃了什么」，每条至多留一个类名锚点。
- **AI 看到不一致就自动「对齐」**：尤其是 L2 / L2b 级冲突（契约 / 死亡线），必须停机等人裁决，绝不能自己改代码或反写文档。
- **信息塞错层**：业务规则写进接口文档、表约束写进后端注释、UI 颜色和业务逻辑混在一处。拿不准时用「该放哪一层」决策树：做什么/为什么→L1，UI 视觉→L2，对外接口字段→L3，数据存储→L4，前/后端架构与链路→L5/L6，如何验证→L7。
- **进度状态词混进正式文档**：`已完成`、`开发中`、`已上线`等属于任务总控，不进 L1~L7。正式文档用「版本归属」+「生命周期状态（草稿/已审核/已废弃/过时待修订）」。
- **以为通用引擎能直接跑**：没写项目级补丁就用，路径、域、死亡线清单全是空占位。补丁是前置条件，不是可选项。
- **死亡线想图省事**：「AI 自审」「以后再审」「只说改了死亡线区域不给 diff」都不通过准入，必须凑齐四件套。
