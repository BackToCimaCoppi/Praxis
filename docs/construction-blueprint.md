# construction-blueprint

> 开工前把"动哪些文件、按什么顺序、关键处长什么样"钉死，让对抗评审打在图纸上，而不是已成型的代码上。

## 这是什么

施工蓝图是**任务级详细设计的施工层**：在真正写代码之前，先产出一份"代码镜像 + 施工指南"。它把一次任务要动的施工面摊开成逐文件变更清单、关键实现点、施工切片和验收映射，目的是限制施工范围、把评审前移到图纸阶段。

> **定位说明**：本库的结果管控闭环（`lightweight-design` → 用例冻结 → `goal-charter` 自主执行）已**不再产出**施工蓝图——它的影响面勘察与验收映射并入轻量设计，施工切片并入 goal 章程里程碑，逐文件施工指令书被取消。本 skill 保留给**仍由人逐工序把关**的传统流程可选使用。

它是一次性消耗品——施工完成即归档，**来不及腐烂**。正因为生命周期极短，文件清单、方法签名、伪代码在这一层全部合法（这是它和长期真值文档的本质区别）。

边界划分：

```
轻量设计方案 ── 决策海拔 ── 人看的，用户审核拍板
      ↓
施工蓝图 ────── 代码海拔 ── AI 看的，开工前对抗评审（本 skill）
      ↓
   施工 → 回补七层文档
```

- **管**：开工前的施工面规划、范围锁定、图纸级对抗评审。
- **不管**：业务决策（归轻量设计方案，用户在那一层拍板）、长期正式真值（归七层文档）。蓝图无裁决权，与七层冲突时听七层。

## 解决什么问题

不写蓝图、直接从设计跳到代码，会反复踩这些坑：

- **评审来得太晚**：评审只能发生在代码写完之后，错误已经扩散进几十个文件，回退成本极高。
- **大 diff 评审疲劳**：面对几百行 diff，评审者有疲劳和沉没成本，越大越容易"算了就这样吧"。
- **范围蔓延看不出来**：代码里偷偷多动了一个不该动的模块，混在大改动里根本发现不了。
- **漏改最难抓**：接口改了但某个消费方没跟着改，这种"少了一处"在代码评审里几乎查不出来。

## 为什么这么设计

- **两道闸缺一不可**：蓝图评审拦"方向错"（范围、遗漏、方案性错误），代码后检查拦"手抖错"。把这两类问题分到两道闸，每道闸只盯自己最擅长抓的。
- **粒度铁律防"代码写两遍"**：变更清单卡死在**文件级**（一文件一行）；只有歧义点/风险点才下沉到逻辑级（允许签名、伪代码）；纯透传/CRUD 只列文件不展开。判定句：蓝图字数接近预估代码量 = 写过头了，砍。
- **一次性消耗品换来合法性**：长期真值文档禁止代码镜像，是因为代码一改它就腐烂；蓝图施工完即归档，根本来不及腐烂，所以才允许写到代码海拔。
- **验收映射是对抗评审的主靶面**：每个已拍板决策点都要映射到具体变更条目——有决策无落点 = 漏，有落点无决策 = 越权加戏。评审不是泛泛"看看好不好"，而是拿决策当裁判逐条对。

## 怎么用

1. **触发词**：中大任务施工前；凡写了轻量设计方案的任务默认接一份蓝图。可跳过的情况：小改动（计划模式足够）、纯文档任务、变更面只有一两个文件时。

2. **流程**：
   - **定输入**：按优先级取上游——已拍板的轻量设计方案（首选，它是蓝图的裁判标准）> 现存七层文档 > 需求 + 当轮聊天确认（后者必须在蓝图里显式登记为"真值来源"）。
   - **写边界**：先写负面清单（明确不改什么），这是限制范围的主力。
   - **列变更清单**：逐文件三分类（新增/修改/删除），覆盖代码、DB migration、配置、脚本全部施工面，一文件一行 + 一句"改成什么样"。
   - **下沉关键实现点**：只对有歧义/风险的少数点写到逻辑级，允许签名和伪代码。
   - **切片**：拆成独立可编译/可验证的施工切片，每片写**可执行的完成判定**（不写"完成即完成"）。
   - **重构类补历史资产退出**：旧表/旧代码/旧接口删什么、何时删、是否留兼容层——不留双轨。
   - **填验收映射**：把每个轻量设计决策点映射到具体变更条目，双向核对。
   - **对抗评审**：拿蓝图 + 轻量设计方案 + 契约文档，过三个靶面（范围越界 / 遗漏 / 方案性错误）。常规任务单评审；高风险或命中项目死亡线时升级到多方对抗评审。
   - **冻结开工**：评审发现的问题改在**蓝图上**，改完可再评一轮；通过后冻结进入施工。
   - **施工纪律**：只能按蓝图执行；必须偏离先回改蓝图；偏离触及已拍板决策则退回轻量设计层重新拍板。
   - **归档**：完工后按轻量设计方案的"回补清单"回补七层，蓝图本身归档即终结。

3. **最小示例**：

   ```
   输入：已拍板的轻量设计方案（给订单列表加状态筛选）

   产出（施工蓝图骨架）：
   # 施工蓝图：订单列表加状态筛选
   ## 1. 任务边界
      改：列表查询接口 + 前端筛选栏
      不改：订单状态机本身、其它列表页
   ## 2. 变更清单
      修改 OrderQueryController：查询入参加 status 字段
      修改 OrderMapper：where 拼接 status 条件
      修改 order-list.vue：顶部加状态下拉
   ## 7. 验收映射
      决策"筛选走后端不走前端" → 落在 OrderMapper 那条
   ## 10. 可开工性结论：可以
   ```

4. **常见坑**：
   - **写过头**：把伪代码铺满全文 = 把代码写两遍，又慢又没增益。只让歧义点下沉。
   - **负面清单写软**："尽量不动其它模块"是无效的——必须硬，点名不改什么。
   - **验收映射只做单向**：只检查"决策有没有落点"，漏了反向的"落点有没有对应决策"，越权加戏就漏过去了。
   - **把蓝图当正式真值**：不得混入七层文档目录冒充 L3/L4/L6，它是任务资产不是长期真值。
   - **施工中偷偷扩张**：完工后实际 diff 与变更清单的差异，就是验收时要逐条解释的清单。

> 项目特定值（蓝图存放路径、红线自检清单、死亡线升级规则、编译/测试/检查脚本命令）不在本 skill 硬编码，由你自己项目的项目级补丁声明并注入模板第 6 节。
