# lightweight-design

> 为单次局部修改写一份"任务级 L5/L6"：用决策海拔锁死本次要改什么、怎么改，让用户在这一层拍板。

## 这是什么

轻量设计方案是**任务级详细设计的决策层**：为一次局部修改任务，写清本次修改的业务逻辑与关键技术取舍。它是 L5/L6 的"任务切片版"——人和 AI 都看得懂，用户在这一层审核拍板，施工期它就是局部临时真值，完工后回补七层正式文档。

边界划分：

```
轻量设计方案 ── 决策海拔 ── 人看的，用户审核拍板（本 skill）
      ↓
施工蓝图 ────── 代码海拔 ── AI 看的，开工前对抗评审
      ↓
   施工 → 回补七层文档
```

- **管**：本次任务的决策（选什么/弃什么/为什么）、负面清单、影响面与回补清单。这是**唯一必经的人工拍板闸**。
- **不管**：代码海拔的施工细节（归施工蓝图）；整域级长期真值（归七层正式文档）。它也**不得越权推翻** L1/L2/L3 正式真值。

## 解决什么问题

实际开发里大量任务是局部修改，两头都难受，中间这层正好补上：

- **重写整域文档太重**：为了改一条链路而重写整域 L5/L6，成本高到没人愿意做。
- **只拿需求直接开工会跑偏**：AI 干着干着就会在某个没人拍板的决策点上自作主张，做出"看起来合理但不是你要的"选择。
- **范围蔓延**：任务跨多个文件/模块时，没有负面清单兜底，改着改着越界。
- **用户无处拍板**：用户不读代码，需要一个能看懂、能拍板、能验收的层，而不是事后看一堆 diff。

## 为什么这么设计

- **决策锁死三件套**：每个决策点必须写清 选了什么 / 放弃了什么 / 为什么。精炼 ≠ 含糊——禁止"采用合适的策略"式模糊措辞，每点锁死到唯一选择。
- **试金石定取舍**：判断一条要不要写进文档，问"不写下来的话，一个有能力的 AI 施工时会不会做出一个看起来合理、但和已拍板结果不同的选择？"会 → 进文档；不会 → 不写。这条避免文档既不漏关键决策、也不堆废话。
- **只写到决策海拔**：禁止代码、伪代码、逐方法调用链复述——这些是代码海拔，归施工蓝图。判定句："这句话删掉、读者直接看代码反而更准，它就超标了。"
- **决策留「为什么」，规格进正式层（零遗漏物化）**：轻量设计**不是施工期的第二套真值**。任务里所有会约束施工或验收的有效语义——选定决策、业务规则、数值口径、状态与失败语义、负面约束、兼容策略、架构归属、跨域边界、验证义务——都要原子化成带**稳定编号的规范条目**，并在冻结前逐条物化到职责正确的七层文档里；轻量设计自己只保存"为什么这么选"（候选方案、放弃理由、调查证据）。
  > 早期做法是"施工期以设计文档为准、完工后再回补七层"。那等于让两套真值并行一整个施工周期，回补一旦拖延或走样，七层就永久落后于现实——而这正是文档腐烂的主要来源。现在改成**先物化再施工**：施工者只看正式规格就够，不必依赖轻量设计才能补全语义。
- **决策来源必须可审计**：会改变业务结果、死亡线规则、对外契约或持久化语义的条目，必须追溯到上游正式真值或一条**用户裁决记录**（保存原话或明确选项、日期、来源、适用范围）。评审建议、AI 偏好、代码现状都不能伪装成"用户已批准"。多项独立选择要逐项编号，不许捆成一句"用户总体同意"。
- **同一问题只能有一个答案**：除了条目索引，还要建一本**业务主题账**——把切片内每个会改变可观察结果的问题登记为一个主题，逐个打开它涉及的全部正式落点交叉核对。"每条设计都已回写"不等于"回写后只有一个答案"。
- **评审只开放一次**：同一阶段、同一真值基线、同一设计对象只允许一轮开放式对抗评审，整改后转封闭验收，禁止自动第二轮。

## 怎么用

1. **触发词**：局部功能开发/重构/单链路改造且存在需人拍板的决策点；任务跨多文件易蔓延；用户说"先出设计方案再动手"。不用的情况见下表。

   | 场景 | 改用 |
   |---|---|
   | 小改动（修 bug、加字段、单文件小改） | 计划模式，零文档成本 |
   | 小任务（有决策点或测试义务，但单会话可完成） | 轻量任务流程 [`plan-goal`](plan-goal.md)：一份全包计划 → 用户批准 → 自主执行 |
   | 整域级设计 / 新域立项 | 直接写七层正式文档 |
   | 纯执行、无决策点的机械任务 | 直接做 |
   | 跨会话、多 agent 的超大任务 | 任务总控 + 每专题各自走「轻量设计 → 用例冻结 → 规格物化 → 执行契约」 |

2. **流程**（六态生命周期）：
   - **① 起草**：输入 = 需求 / 聊天确认 / 现存七层文档 / 代码摸底。
   - **② 冲突检查**：起草时必须与现存七层文档核对；发现不一致走**人工裁决**，禁止 AI 自行选边，更不得越权推翻 L1/L2/L3。
   - **③ 用户拍板**：唯一必经的人工闸。决策表 + 负面清单是审核主靶面；用户确认即冻结，后续不得自行重裁。
   - **④ 建索引**：把全部有效语义原子化成带稳定编号的规范条目（不能只索引高风险决策点），建立业务主题账，定稿后记录设计哈希——后续只能补正式落点，不能静默改写语义。
   - **⑤ 冻结前物化**：每个条目落到职责正确的正式层（接口→契约层、表→持久化层、核心决策→设计层、验收→用例层），并建立「条目 → 正式规格 → 验收断言」的双向追溯。覆盖报告全绿才算冻结完成。
   - **⑥ 降级为决策留痕**：物化完成后，正式七层是唯一规范真值，轻量设计降为"为什么这么选"的留痕。施工者不应依赖它才能补全规格。
   - **施工中决策要改** → 退回本层重新拍板，不允许在代码或执行记录里悄悄改。若只是"规格有洞但现有真值给出唯一方向"，走有界重新冻结补齐条目与追溯，不必惊动用户。

3. **最小示例**：

   ```
   输入：需求"订单列表要能按状态筛选" + 现存订单域七层文档

   产出（轻量设计方案骨架）：
   # 轻量设计方案：订单列表加状态筛选
   ## 1. 背景与意图：客服要按"待发货"快速捞单，列表加状态筛选
   ## 2. 范围与非范围
      改：列表查询业务逻辑、筛选交互
      不改：订单状态机定义、其它列表页
   ## 3. 决策表
      | 决策点 | 选定 | 放弃 | 为什么 |
      | 筛选在哪做 | 后端过滤 | 前端过滤 | 分页下前端过滤会漏数据 |
   ## 6. 影响面与回补清单
      回补 L3 接口文档、L5 订单域设计
   ```

4. **常见坑**：
   - **决策表写模糊**："采用合适的缓存策略"不算决策，必须锁死到唯一选择。
   - **负面清单写软**：不点名"不改什么"，范围就守不住。
   - **混入代码**：贴伪代码、逐方法复述调用链——越到代码海拔，应该挪到施工蓝图。
   - **阻塞级待确认没清零**：阻塞级（必须先决策的点）未决就进蓝图/施工，等于把坑往下游埋。
   - **忘了回补或忘了标失效**：回补完不在头部标"已失效"，就会和七层形成两套真值打架。
   - **试金石没过**：写了一堆"删掉直接看代码更准"的话，文档变臃肿。
