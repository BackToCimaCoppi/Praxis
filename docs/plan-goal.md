# plan-goal

> 把「调查 → 设计 → 用例 → 章程 → 自主执行 → 验收」整条研发流水线压进**一份计划文件**，人只出面两次：批准一次、验收一次。

## 这是什么

plan-goal 是**轻量任务流程**：为一个单会话就能做完、但又带着决策点或测试义务的小任务，写一份九节全包式计划——决策点、验收断言表、文档同步清单、执行章程全在里面——交给你批准，然后转自主执行模式（`/goal`）一口气跑到底，最后你在终点验收一次。

它是 `lightweight-design`（轻量设计）+ `goal-charter`（执行章程）+ 任务总控那条重流程的**微缩档**。重流程把设计、用例冻结、章程、总控编排拆成多份文件、多道人工闸；本档把这些压成一份文件、一次批准。

三档分级（判据按「碰了什么」，**不按改动量**——三行 diff 改掉一条优惠券核销规则也不是小任务）：

| 档位 | 判据 | 模式 |
|---|---|---|
| 直接做 | 无业务语义决策、无新增测试义务（排版 / 注释 / 配置微调） | 计划模式，不出文档 |
| **plan-goal** | 有决策点或测试义务，单会话可完成，未命中升级触发 | 一份全包计划 → 批准 → goal |
| 升级 | 命中任一升级触发 | `lightweight-design` 或任务总控 |

**升级触发（命中任一就不许硬塞轻量档）**：跨 ≥2 个业务域写入 · 不可逆数据迁移 · 钱 / 权 / 数据整链路重构 · 阻塞级决策互相耦合、无法一次拍板收敛 · 预计跨会话。

死亡线区域（项目里改错即事故的业务规则清单）的**局部小改**允许进本档，但计划开场必须声明命中，是否加一道对抗评审由你在批准时决定——不升档、升评审强度。

- **管**：计划怎么写、批准意味着什么、执行期什么情况才准停下来问人、怎么把计划交接给 `/goal`、终点怎么验收。
- **不管**：重流程本身（设计清算归 `lightweight-design`，用例冻结管线归 `test-case-design`，多会话编排归 `task-control-doc`）；对抗评审的编排（归 `adversarial-review`，且本档只由你手动触发，AI 永不主动提议）；任何项目特定规则（死亡线清单、域边界、钩子命令由项目级补丁注入）。

## 解决什么问题

小任务夹在两个坏选项中间：

**套重流程**：为了给优惠券加一条核销校验，要写设计方案、建规范条目索引、跑冻结管线、写章程、建总控目录——五份文件、三道人工闸，流程比活本身还重。结果是没人愿意走，或者走到一半就"先干了再说"。

**跳过流程**：直接开工看似省事，实际会漏掉四样东西——

- **决策没留痕**：AI 在某个没人拍板的点上自作主张（"优惠券退回时过期的要不要一起退？"），做出看起来合理但不是你要的选择，事后从 diff 里根本看不出这是个决策。
- **断言被改弱**：先写代码再补测试，测试天然向代码靠拢；跑红了改断言比改代码容易得多，验证器就这样被悄悄搞绿。
- **人被反复打断**：凭据在哪、runner 起不来、测试夹具过期、实现细节二选一——每件事都停下来问一句，"让 AI 自己跑完"变成"每十分钟被叫一次"。
- **文档掉队**：改完代码没人同步接口文档、表结构快照，七层文档从此永久落后于现实。

本档要的是：**砍过程，不砍验收**。把重流程里防「不可逆风险 / 真值分叉 / 工具机制事实」的规则保留下来，把防「跨会话交接 / 脚本可解析 / 弱模型防呆」的脚手架全部废弃——那些失败模式在单文件、单会话的形态下根本不存在。

## 为什么这么设计

- **一份文件九节，每节有写「无」的权利，但不许整节省略**：目标终态 / 开场声明 / 事实基线 / 决策点清单 / 改动清单 / 测试计划 / 文档同步清单 / 执行章程 / 执行记录。省略和「无」是两回事——前者没扫过，后者扫过没命中。简单任务半屏写完。内核只有三问：**选了什么 / 为什么 / 怎么验**。
- **用户批准 = 本档的评审等价物 + 冻结**：重流程里"决策生效"靠逐条裁决记录，"计划冻结"靠评审通过。本档把两者合并成一次批准：第 4 节决策点逐条生效，计划取得冻结件资格。前提是决策点必须**单列一行、逐条拍**——禁止把多项打包成一句"总体同意"，否则批准就没有裁决含量。
- **批准后文件分区**：§1–§8 冻结，改动决策点或断言表必须显式声明并重新获批，禁止静默改写；§9 执行记录只许追加，是执行期唯一可写的区域。
- **「计划赢」有边界**：执行中撞见"计划 ↔ 代码 / 现实"不一致，计划**明写**的语义按计划改、不停机；计划没写但可由正式文档唯一推出的，在执行内对齐；只有两份冻结真值形成改变业务结果的矛盾才停机。**不许拿冻结件资格给计划没写的东西背书**——冻结的是写下来的字，不是执行体的推测。
- **停机出口白名单只有三条**：① 两份冻结真值存在改变业务结果的矛盾；② 死亡线业务规则要变；③ 需要计划未预授权的不可逆 / 外发动作。凭据定位、实现取舍、测试 / runner / 环境 / 证据工具缺陷、重复失败，全部在同一次执行里自愈，不升级成用户裁决。**打断你的成本远高于一次可回滚的自愈。**
- **断言不许削弱**：验收断言表批准后即是裁判席。施工中改测试脚本前先问一句——改完更接近断言表 = 忠实化，可以；更接近代码 = 作弊，不行。如果证明断言表本身错了（`SPEC_STALE`），停机附修改方案（改哪些计划节/AC、影响面、恢复点），你批一次后改好计划、断点续跑；只有计划骨架不成立才终止执行重批整份计划——两条路都不许在执行中就地改断言。
- **测试只保留五件本质**：命中面判定 / 断言可对账 / 断言先于代码冻结且不许削弱 / 写链路必验数据库终态 / 失败分类且取证形态不升格（替身绿只证明代码路径被走到，不证明功能对用户可用）。不走 `test-case-design` 的哈希冻结管线——断言表就是本档的冻结载体。
- **可预见的用户停机在批准后、建 goal 前清算掉**：密钥、登录、第三方后台、真实设备这类事分四类——AI 能自己做的留给执行体；不依赖候选件的当场做完；依赖候选件的合并成一次用户窗口；跨天的外部审批升为上游任务。默认目标是零次窗口。
- **`/goal` 交接照机制事实办，不凭印象**：完成条件只有一个参数、有字符上限 → 条件指针化指向计划文件，不复制内容；判定器不跑命令不读文件 → 每条终态必须带举证义务（"`git status --porcelain` 输出已贴出且为空"，而非"工作树干净"）；条件不成立就自动续轮 → **停机出口必须写进完成条件**，漏写哪个哪个形同虚设。执行体终态只能是 `CANDIDATE_READY`，无权宣布任务完成。
- **反棘轮**：禁止给本档单向加闸门、加审批、加必跑评审；评审结论是信息不是门禁；给本档新增任何规则必须经用户裁决。事故后的正确动作是「审计 → 用户拍板 → 靶向修」，不是往模板里塞新必填节——漏一条是事故、多加一条叫严谨，这种激励不对称会让轻量档在三次复盘后变回重流程。

## 怎么用

**触发词**：`plan-goal`、「轻量流程」、「小任务」；或任务本身满足「有决策点 / 测试义务 + 单会话可完成 + 未命中升级触发」。

**流程**：

1. （可选）调查：亲自读代码，或把已枚举的叶子任务有界并行派出去；（可选）和你对齐方向。
2. 按九节模板写一份全包计划；落盘路径按项目补丁约定，没有约定就先向你确认。
3. 你可选触发对抗评审（AI 不会主动提议）。
4. **你批准** → 决策点逐条生效、计划冻结。
5. 清算启动服务表：能当场做完的用户动作当场做完。
6. AI 生成一条四段式 `/goal` 条件：开工指令（指向计划文件 + 从磁盘重读纪律 + 中途不汇报）/ 完成条件（每条带举证）/ 约束（章程里最致命的 3–6 条）/ 出口（停机白名单三条 + `SPEC_STALE` 停机出方案 + 限轮）。
7. goal 自主跑到底：启动检查并修执行基础设施 → 施工 → 测试 → 文档同步 → 项目钩子 → 提交 → 追加执行记录 → 报出 `CANDIDATE_READY`。
8. **你终点验收一次**：打开计划文件，§1 终态 vs §9 执行记录，一屏对完。

**最小示例**（虚构域：订单取消后退回已用优惠券）：

```
# 计划：订单取消自动退回优惠券
## 1. 目标终态
   取消订单后该单占用的优惠券状态回到「未使用」；已提交、工作树干净。
## 2. 开场声明
   命中 L3 接口 / L4 表结构 / L7 用例；死亡线：优惠券状态机（命中，局部小改）；
   域：订单、优惠券；跨域写入：否（优惠券域通过已有内部事件回写）；环境：测试库。
## 3. 事实基线
   优惠券表已有 status 字段与 used_order_id；取消链路已发「订单已取消」事件（读过）。
## 4. 决策点
   | 决策 | 选定 | 放弃 | 为什么 |
   | 已过期的券要不要退 | 退回但状态置「已过期」 | 不退 | 用户视角"券没用上"，过期与否是另一条规则 |
   | 部分退款单要不要退 | 不退 | 按比例 | 券不可拆分；比例规则无上游真值（死亡线标记） |
## 5. 改动清单
   订单域取消事件消费者；优惠券状态回写；L3 事件契约补一个字段。
## 6. 测试计划
   命中面：接口 ✓ / DB 终态 ✓ / UI ✗（无页面改动）/ 权限 ✗（无新入口）
   | AC | 断言 | 取证 | 执行 | 出处 |
   | AC-1 | given 有效券已用于订单 when 取消 then 券 status=未使用 且 used_order_id 为空 | 实测 | 自动化 | 决策1 |
   | AC-2 | given 券已过期 when 取消 then 券 status=已过期 | 实测 | 自动化 | 决策1 |
   | AC-3 | given 部分退款 when 完成 then 券状态不变 | 实测 | 自动化 | 决策2 |
## 7. 文档同步清单
   L3 事件契约 / L4 优惠券表 DDL 快照 / L7 追加 AC-1~3；L1 L2 L5 L6 不涉及。
## 8. 执行章程
   可达性：只碰测试库；预授权：允许 commit；禁推送。停机白名单三条。限轮 8。
   有界并行：接口测试与 DB 断言可并行。启动服务表：无用户窗口。
## 9. 执行记录
   （goal 期间追加）
```

对应的 `/goal` 条件只有一条，几百字：指向这份计划 → 完成条件逐项带"输出已贴出" → 三条最致命约束 → 出口三类"命中即视为条件满足"。

**常见坑**：

- **按改动量判档**：改一行核销规则也是决策点，不能因为 diff 小就"直接做"。
- **决策点打包**：把三个选择写成一段话让你"总体同意"——批准就失去了裁决含量，事后无法追溯哪条是你拍的。
- **整节省略**：跳过第 7 节文档同步清单而不是写"逐层不涉及"，等于没扫过。
- **执行中改断言**：跑红了顺手改测试让它绿——那是作弊；断言表真错了走 `SPEC_STALE`：出修改方案获批后续跑，计划骨架不成立才重批。
- **把环境故障当停机理由**：runner 起不来、夹具过期、凭据找不到，都是执行体自己修，不是来问你的理由。
- **`/goal` 条件抄计划**：条件明显偏长基本就是在复制计划正文；正确做法是指针化 + 举证义务 + 出口写全。
- **执行体自己宣布完成**：终态只能报 `CANDIDATE_READY`，任务完成与否由你终点验收说了算。
- **复盘后往模板里加必填节**：这是棘轮的入口；要加规则先经你裁决，且一个病灶一处靶向修。

> 项目特定值（计划落盘路径、死亡线清单、域边界、变更后钩子命令）不在本 skill 硬编码，由你自己项目的项目级补丁声明；项目强制加载的 skill 照常加载，本档不豁免。
