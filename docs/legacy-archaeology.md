# legacy-archaeology

> 把一个黑盒老项目反推成「树形下钻、业务/库/接口讲清」的知识库，给后续重构的 AI 注入背景。

## 这是什么

一个**代码考古编排器**。你有一个年久失修、没人讲得清的老项目（典型是老 Java 微服务），
它指挥一支 AI agent team 去逐模块调查，把代码翻译成一棵 **README 层层索引、逐层下钻**的知识库树：
顶层讲项目概况和模块切分，每个模块下钻到三个叶子文档——**业务逻辑 / 数据库 / 接口**。
多个项目还共享一张**平台层服务调用图**。

**管什么**：把「系统做什么业务决策、存什么数据、暴露什么接口契约」讲清楚，每条挂源码锚点，
可被重构 AI 按需检索下钻。

**不管什么**：不写需求文档、不描述代码实现、不碰测试。也**不承诺「零遗漏」**——它只承诺
「边界内可审计覆盖 + 残余风险显式登记」（漏的地方都给你标出来，而不是假装查全了）。

## 解决什么问题

要重构一个大平台，让 AI 设计新系统替代旧系统，但 AI 完全不懂老项目背景。直接把代码喂给它，
会遇到三个死结：

- **喂不进**：几十个微服务、几百万行代码，上下文窗口装不下；就算装得下，AI 也会遗忘、忽略。
- **不敢信**：让 AI「自己读一遍代码总结」，它会自信地把没读到的业务规则**脑补**成看似合理的样子——
  错的文档比没文档更毒，会把错误前提直接设计进新系统。
- **抓不住细节**：老代码最脏、最隐蔽的业务规则（超时补偿、状态机暗分支、magic number 阈值），
  恰恰是重构最容易打碎、最该被记下来的，也是最容易被一句话总结漏掉的。

这个 skill 把「调查」做成一套有纪律的流程：分层下钻省上下文、源码锚点防脑补、双台账 + 外部真值源
差集**把漏掉的地方显式标出来**。重构 AI 平时只读 L1，遇到要深究的点再钉下去读叶子，既省上下文又
不丢细节，而且每一处「没查到」都写在明面上。

## 为什么这么设计

- **为什么只三层（业务/库/接口）**：重构要的是「契约和规则」，不是旧实现。需求会重写、代码会替换、
  测试会重做——把它们写进来只会增重、过期、抢上下文。三层是「重构背景」的最小充分集。

- **为什么不承诺零遗漏**：白盒静态扫描在不预设技术栈时，**逻辑上无法证明「我枚举出的 = 系统全部」**。
  把无法证明的东西写成承诺就是自欺，还会制造「已经查全了」的假绿灯，让重构 AI 在漏掉且不知道漏了的
  地方踩雷。所以承诺降级为「可审计覆盖 + 盲区显式登记」——这是这个 skill 经对抗评审后最关键的一处。

- **为什么要双台账 + 外部真值源**：单本台账由枚举生成，又拿它给枚举对账，是**循环论证**——枚举漏的项
  台账里根本没那一行，对账永远绿灯。所以拆「发现来源台账（记边界与盲区）」+「对象覆盖台账（记认领）」，
  再叠一层不依赖技术栈的外部真值源（网关路由表、`information_schema`、broker topic…）做**差集**，
  差集就是白盒漏掉的盲区。拿不到真值源就标低置信、不给绿灯。

- **为什么子 agent 不在源头丢弃内容**：判断一条逻辑「是业务规则还是碰巧这么写」需要业务意图，而这是
  无业务背景的子 agent 最判不准的。所以子 agent 只「发现 + 保全候选 + 标证据强度」，二分留给有业务
  输入的回合。源头丢弃的东西，下游再也找不回来。

- **为什么编排要有预算和落盘**：主 agent 自由调度但「持续到无未决点」没有终止保证（老代码的不确定会
  发散），且把所有回报堆进主 agent 上下文必然爆掉、丢失全局未决点。所以状态全落盘、单模块设轮次上限、
  按风险优先级下钻、每轮可停机。

- **为什么文件名用 ASCII、内容用中文**：文件名是机器导航锚点，中文文件名在不同系统/工具链上会被转义成
  乱码、断链。骨架用 ASCII（`business-logic.md`/`database.md`/`api.md`），正文全中文。

## 怎么用

### 1. 触发词
「老代码考古」「反推知识库」「重构前背景」「把老项目翻译成文档」「legacy 调查」。

### 2. 流程

```
开工：问用户 → 输出根目录 / 查哪个项目 / 快照批次号
  ↓
步骤0 认栈 → 批量索要 DB schema + 外部真值源（提到派 team 之前，因为子 agent 中途停不下来）
  ↓
步骤1 搭双台账（发现来源台账 + 对象覆盖台账）→ 外部真值源差集找盲区
  ↓
步骤2 主 agent 切模块 → 派 agent team（子 agent：只产三层、挂锚点、保全候选、阻塞高优返回）
  ↓
步骤3 主 agent 消化回报（自由轮次有上限）→ 攒一批问用户 → 补派 → DB 拿不到则推测模式
  ↓
步骤4 台账对账（每行收敛到 已记录/推测/失传/待人工；盲区显式登记，不给绿灯）
  ↓
步骤5 残缺性审计关卡（adversarial-review 审覆盖边界/枚举策略，不宣称完整）
  ↓
步骤6 回填平台层调用图（稳定标识做主键、悬空边、冲突不静默覆盖）
```

每查完一个项目得到一棵树；查下一个项目时往平台层调用图增量补一笔。

### 3. 最小示例

**输入**：「调查 order-service 这个老项目，输出到 ~/kb，批次 2026-06-23」。

**产出**（节选）：
```
~/kb/order-center/
  README.md            # L1：订单中心概况 + 模块清单 + 残余风险摘要
  discovery-ledger.md  # 枚举来源 + 已知未覆盖（反射RPC盲区）+ 真值源比对状态
  coverage-ledger.md   # t_order[已记录] / order_paid[推测] / closeExpiredOrder[待人工]
  下单/
    README.md
    business-logic.md  # 规则：订单超时关闭—触发每5分钟扫【事实|OrderJob:30】…
    database.md  api.md
~/kb/_platform/call-graph.md   # order-center → inventory（悬空边·被调方未建库）
```

### 4. 常见坑

- **坑：把它当「文档完整性保证工具」用**。它**不保证**查全，只保证把漏的标出来。看产物时务必读
  「残余风险摘要」和发现来源台账的「已知未覆盖」——那才是它最诚实、最有用的部分。
- **坑：不给 DB schema 还指望数据库层准**。schema 要在派 team 之前给；不给则整层是代码推断、低置信，
  应用层推断的隐式外键经常推错，别当事实信。
- **坑：以为子 agent 能边查边问你**。不能。子 agent 派出去跑完才返回，所有「问用户」都在主 agent 层
  分轮次集中进行。
- **坑：跨服务调用方当成查全了**。一次只查一个项目，看不到别的服务谁调你的接口；接口文档里跨服务
  调用方标的是「未知/待补」，要靠平台层调用图逐步收敛，别据此判断「这个接口可以放心改」。
