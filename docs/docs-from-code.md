# docs-from-code

> 代码早就写好了，需求文档却从来没写过？这个 skill 教你从代码反推出一份能让人看懂「这功能在干嘛」的 L1 需求文档。

## 这是什么

它是一套**从代码反推需求文档（L1 层）的通用方法论**。给一个已有功能的代码库，它提供 7 步操作流程、前后端代码阅读重点、归档使用规则、不确定信息的处理办法，以及一份需求文档模板，帮你把「代码事实」翻译成「业务语言写的需求」。

**它管什么**：

- 怎么定模块边界、从前端读什么、从后端读什么、怎么用枚举和模型补边界条件
- 怎么用业务语言把代码事实重写成需求文档（不是把代码翻译一遍，而是讲清楚「这功能为用户解决什么」）
- 不确定的信息怎么处理（写「待确认」，不虚构）

**它不管什么**：

- 不管项目特定的目录结构、版本制、命名规则——那些去看各项目自己的 `docs-writing-guide`
- 不是七层冷启动总控（那是 `code-to-7layer`），不产出 AI 导览文档（那是 `code-to-guide`）。它只聚焦一件事：**反推 L1 需求**。

## 解决什么问题

代码先行、文档缺失的项目里，不用它你会遇到：

1. **新人接手看不懂业务**。代码能跑，但「这个功能给谁用、解决什么问题、有哪些业务规则」全在程序员脑子里，一离职就失传。
2. **需求文档写成了代码说明书**。直接照着代码翻译，写出一堆「调用了 XxxService.create 方法」这种实现细节，读者还是不知道业务在干嘛。
3. **状态和边界条件漏写**。枚举里藏着的状态值域、Service 里藏着的限制规则，不系统地翻一遍就会漏，文档不完整。
4. **拿旧方案当现状**。归档目录里有历史方案文档，不小心当成当前事实写进去，文档和代码对不上。

## 为什么这么设计

- **前端定「做什么」，后端定「规则」**。前端代码给出页面、入口、交互动作（用户能看到什么）；后端代码给出接口能力、枚举状态、Service 里的规则与限制（系统怎么约束）。两边都读才完整。
- **代码事实优先，归档只做补充**。归档（历史文档）只能用来补充模块命名、业务意图、代码里不明显的边界规则；**绝不能用归档覆盖代码事实，也不能把旧方案当现状**。代码在跑，代码才是真相。
- **不确定就写「待确认」，绝不虚构**。三步兜底：回代码再验证 → 用归档交叉核对 → 还确认不了就老实写「待确认」。宁可留白，不编结论。
- **最后一道清理：是否写进了实现细节**。第 7 步专门回头检查——需求文档里如果出现了实现细节，删掉。需求是业务语言，不是代码说明。

## 怎么用

### 1. 触发词

「补写需求文档」「从代码反推」「L1 补写」「反推 L1」。

### 2. 流程（7 步）

```
1. 确定模块边界
2. 从前端找：页面、入口、交互动作
3. 从后端找：接口、业务能力、规则与状态
4. 从枚举和模型补充：状态、类型、边界条件
5. 查归档目录，只做补充和交叉核对（不能覆盖代码事实）
6. 用业务语言重写成需求文档
7. 最后清理：「是否写进了实现细节？」
```

代码阅读重点：

- **前端**：页面名称与层级、tab 与分包结构、服务调用名称、按钮文案、空状态/错误状态处理、页面跳转关系。
- **后端**：Controller 对外能力、枚举体现的状态和值域、Biz/Service 中的规则与限制、权限校验、状态流转、外部依赖。

### 3. 最小示例

```
输入：一个已有「优惠券」功能的代码库，无需求文档。

按流程走：
  前端 → 发现「我的优惠券」页面、领取按钮、已过期空状态
  后端 → CouponController 提供领取/核销接口
         CouponStatus 枚举：未使用 / 已使用 / 已过期
         Service 规则：每人每券限领 1 张、过期不可核销
  归档 → 交叉核对，补上「优惠券用于拉新」的业务意图

产出：docs/01-需求/ 下一份需求文档，按模板章节组织：
  1. 模块目标：通过优惠券提升新用户转化
  2. 用户价值：新用户领券享立减
  4. 功能列表：领取、查看、核销
  5. 业务规则：每人每券限领 1 张
  6. 状态流转：未使用 → 已使用 / 已过期
  8. 异常与边界：过期券不可核销
  （全程用业务语言，不写「调用了哪个方法」）
```

需求文档推荐模板章节：

```
0. 版本归属 / 适用版本      6. 状态流转
1. 模块目标                 7. 系统支撑能力
2. 用户价值                 8. 异常与边界场景
3. 页面与入口               9. 与其他模块的关系
4. 功能列表                 10. 验收标准
5. 业务规则
```

### 4. 常见坑

- **把代码翻译成文档**。需求要用业务语言讲「为用户解决什么」，不是逐方法复述实现。第 7 步专门清这个。
- **拿归档覆盖代码**。归档只能补充、交叉核对，代码事实永远优先。把旧方案当现状是大忌。
- **漏掉枚举和 Service 里的隐藏规则**。状态值域藏在枚举里、限制规则藏在 Service 里，第 3、4 步必须系统翻一遍。
- **不确定就硬编结论**。确认不了就写「待确认」，别虚构。
- **找项目特定规则**。目录结构、版本制、命名这些本 skill 不管，去看项目自己的 `docs-writing-guide`。
