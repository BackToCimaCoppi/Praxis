# ask-claude

> 一个统一入口，按触发词把活儿派给 Sonnet 或 Opus 子线程：主线程收集弹药，Claude 子线程做深度推理或动手干活。给"想用一句话同时覆盖两档模型"的人用。

## 这是什么

ask-claude 与 ask-sonnet / ask-opus 是同一套"派活问询"机制，区别在于它把 **Sonnet 和 Opus 两档** 收在一个 skill 里，靠触发词选模型档位。它定义了分层协作：

- **主线程（你）= L1 信息收集者**：读文件、提取事实、压成"最小充分包"。
- **子线程（Sonnet / Opus）= L2/L3 推理者**：在干净上下文里做深度推理、方案设计、代码生成。

它管 **问模式**（Claude 只读不改，输出结论）和 **派模式**（Claude 在授权范围内动手改文件）；并管 **模型映射**——默认 Sonnet，触发词点名 opus 时升 Opus。

它**不管**：自动路由（不说触发词就不调子线程）；也不替子线程下结论。

## 解决什么问题

不用它，直接把所有上下文丢给强模型，会遇到：

1. **token 浪费**：读文件这种廉价机械活也用强模型承担，账单飙升。
2. **注意力稀释**：原始上下文越杂，强模型越分心，真正需要算力的判断点被埋没。
3. **越俎代庖**：把"已符合规范"当结论写进去，剥夺了子线程独立验证约束的能力。
4. **派活失控**：让模型自由改代码，可能动了一堆没授权的文件，事后无法纠正。

## 为什么这么设计

1. **L1 / L2-L3 分层**：信息收集和深度推理拆开，各用各的成本档；主线程只做"找到什么、整理成什么格式"。
2. **一个入口覆盖两档**：默认 Sonnet（性价比），需要更强推理时一句"问一下opus"即升档，不必记两套 skill 名。
3. **传原文，不传结论**：约束条件内嵌原文，让子线程自己验证，而非接受主线程预判。
4. **给清单，不设路障**：文件清单是"最小必读"而非"只准读这些"——但放开的只是**读**，派模式能写哪些文件仍由授权边界严格限定。
5. **来源声明**：主线程必须显式声明读了什么、漏了什么，否则子线程会基于错误假设作答。

## 怎么用

1. **触发词**（按模式 × 模型组合）
   - 问 Sonnet（默认）："问一下克劳德"、"问一下claude"、"问一下sonnet"
   - 派 Sonnet："让克劳德去做XX"、"让claude直接XX"
   - 问 Opus："问一下opus"
   - 派 Opus："让opus去做XX"、"让opus直接XX"
   - 不说触发词 → 主线程自己处理。触发词模糊 → 先问"问模式还是派模式？"

2. **流程**
   - **问模式**：
     1. 按问题类型选填槽位（具体问题 / 文件引用 / 背景事实 / 约束条件 / 判断标准 / 外部信息）
     2. 每项过 RAM 检验句：「Claude 需要 [这项]，才能 [回答问题]，否则卡在 [具体卡点]」，填不完整就删
     3. 写"L1 信息来源声明"（交付形式、已读文件白名单、未纳入的已知信息）
     4. 用 Agent 工具（model 按触发词取 sonnet / opus）发出，prompt 末尾声明"不要改任何文件"
     5. 消化结论，用自己的话回答用户，附独立判断
   - **派模式**：
     1. 发任务 + 验收标准 + 禁止区 + 约束（不预设文件清单）
     2. Claude 探索代码，先回"改动范围计划"
     3. 主线程确认/调整范围 → Claude 施工
     4. 主线程按验收清单（范围 / 编译 / 约束 / 验收标准 / 越界）检查 → 报告用户

3. **最小示例**（问模式，默认 Sonnet）

   输入：
   ```
   这个分表方案在百万级数据下会不会有性能问题？

   L1 信息来源声明：
   - 交付形式：直接回复，不写文件
   - 已读文件白名单：
     - .../FollowBiz.java（只读：getFollowerList）
   - 未纳入本包的已知信息：无

   背景事实：分表按 hash(uid) % 32；当前数据量小，暂无性能问题
   约束条件：禁止 N+1，循环内不许调 Dao，必须批量查询 + Map 关联
   判断标准：百万级场景单次请求 < 500ms

   输出要求：直接在 stdout 输出结论，不要改任何文件。
   ```

   产出：一份结论，指出哪些查询会退化、是否触碰红线、能否满足 500ms。

4. **常见坑**
   - **把原始代码整段贴进包**：先压成关键事实（200 行 → 3 行），别稀释注意力。
   - **约束写成结论**：贴规则原文，别替子线程下"已符合规范"的判断。
   - **一次调用反复追问**：每次追问都开新的 Agent 调用，别在同一子线程里来回聊。
