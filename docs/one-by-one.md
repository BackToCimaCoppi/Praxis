# one-by-one

> 用户要一口气裁决多件事时，不弹窗、不批量抛问题：用通俗汉语一次只讲一题，裁一题、落盘一题，再进下一题——**只固定「怎么问、怎么记」，不改变原流程要问什么、问几个**。

## 这是什么

一种**逐题裁决模式**。触发后，本会话余下全程禁用弹窗式提问（如 Claude Code 的 `AskUserQuestion`），改为纯文本：先给一张问题总览表，然后每次只谈一道题，按固定四段（背景 / 分歧点 / 选项 / 推荐）讲完，等用户拍板；拍板后立即写进裁决记录文件并展示原文，才进入下一题。

边界划分：

- **管**：提问的形式（纯文本、一题一屏）、表达的海拔（人话、锚定、代价落地、禁黑话）、裁决的记录（落点、时机、自包含）、假决策的识别。
- **不管**：问什么、问几个。这些仍由上游流程决定——总控、`lightweight-design`、`adversarial-review`、`plan-goal` 等流程的实质步骤和问题内容一律不受影响。本 skill 不新增任何决策权：该停机问用户的照样停机，该走评审的照走原流程。
- **触发方式**：仅用户手动输入 `/one-by-one`，AI 永不主动激活。

## 解决什么问题

一个改动往往牵出五六个决策点。把它们交给用户拍板时，常见五种失败方式：

- **弹窗遮挡、被迫盲选**：弹窗式提问在 CLI / 桌面 / IDE 插件多端存在遮挡问题——弹窗盖住上方的解释文字，用户看不到背景就得选，或者干脆取消，然后发现刚才那批问题没人能重新问一遍。
- **批量抛问题淹没重点**：一次列出六个决策点、每个带三个选项和两段论证，用户要自己在几千字里找"哪个是真的要我定的"。真正影响走向的那一道，和三道其实无所谓的混在一起。
- **AI 黑话让人拍不了板**："选 A 写入放大更高""方案 B 心智负担较大"——读完不知道自己会看到什么不同、会卡住什么动作，只能凭感觉选，或者反复追问。
- **上下文压缩后裁决丢失**：长会话里拍板过的事，压缩之后 AI 忘了，下次又拿同一道题来问；更糟的是 AI 按自己记忆里的"大概选了 B"继续推进，而用户当时选的是 A。
- **假决策**：两个反方向的错——把 AI 已论证为唯一解的题也拿来问（浪费用户注意力，而且让用户以为每道题都值得细看）；或者反过来，AI 觉得"这个显然选 A"就把上游流程列出的决策点吞掉不问了，用户根本不知道这道题存在过。

## 为什么这么设计

- **一题四段、总长一屏**：背景 1–2 句、分歧点一句、选项每项一行、推荐一句。一屏是硬预算：锚点计入预算，放不下就**拆题**，不砍锚点、不破一屏。试金石是"用户不打开 IDE、不追问，能否直接拍板"，不能就重写。
- **先落盘后推进**：裁决写进文件、向用户展示原文之后，才允许进入下一题。记录必须自包含（背景、选项、裁决、理由），达标标准是压缩上下文后**只重读记录文件**就能完整恢复裁决语义。问题总览表也随第一条记录落到同一文件，每裁一题更新状态——会话中断或压缩后凭它恢复进度。等待裁决期间，禁止假定某个选项成立而继续干相关的活。
- **锚定与代价落地**：会话内部产生的名词（方案名、编号、新标签）默认用户不在场，首次出现必须带一句话锚点——它是什么、在哪、扮演什么角色；内部编号首次引用就地展开，不许让用户跳转查阅。任务内新起的标签哪怕字面全是通用技术词，也要锚定到具体对象（作用于哪份数据、存在哪、谁消费）。代价必须写成用户可感知的结果，有依据就给数量级并注明出处，没有就明确标「量级未知」，禁止编造数字，禁止只给实现层形容词。
- **假决策三分法**：①上游流程列出的决策点**一律不吞**，AI 论证为唯一解的照样出题，标注「已论证唯一解 + 理由」，用户一句话秒批即可；②AI 在本会话自造的题，讲不出"选 A 和选 B 用户会遇到什么不同"就不出题，但要在总览表**正文**列一行告知（不能藏到表下附注）；③"答不出差异"不是吞题理由——那是背景不足，降级为「我没搞懂，请求补背景」。判定标准前后不一致（一边说唯一解不占用用户、一边又抛唯一解题）视为流程违规。
- **只管形式、不夺决策权**：这是最关键的取舍。它与 `plan-goal`「决策点禁止打包成一次总体同意」同向，但自身不新增任何"该不该问"的判断权——否则一个本来只管表达的 skill 会悄悄变成第二套流程。
- **反棘轮**：给本 skill 加新规则必须经用户裁决。每出一次事故就往规则里加一条，规则会单向膨胀到没人读得完；把"加规则"本身也变成一道要拍板的题，才能刹住。

## 怎么用

**触发方式**：用户手动输入 `/one-by-one`。建议在 `settings.json` 用 `skillOverrides` 把它设为仅用户可调用，作为"AI 永不主动激活"的兜底。生效到本会话结束，或用户明说退出（「恢复弹窗」「退出逐题模式」）。

**三种入口场景**：

| 入口场景 | 第一步动作 |
|---|---|
| 用户刚取消了一个弹窗 | 把弹窗里那批问题按本模式重新提出 |
| 用户看不懂刚才的解释 / 提问 | 先按表达规范把刚才的内容重讲一遍，再进入逐题流程 |
| 预防性触发（裁决还没开始） | 直接开始逐题流程 |

**流程**：

```
① 问题总览表：编号 + 一句话主题 + 状态（先让用户看到一共几件事）
② 每次只谈一题：四段讲完，纯文本等裁决
③ 用户裁决 → 立即落盘 → 展示记录原文 → 更新总览状态 → 下一题
④ 全部谈完 → 输出本轮裁决总表
```

记录落点按优先级：当前任务已有 `用户裁决记录.md` → 追加 DEC-x 沿用编号；正在编辑的方案文档有「决策记录」节 → 追加该节；都没有 → 新建日期命名的记录文件，落点用纯文本问用户一次。

**最小示例**（虚构域：支付）

```
第 2/4 题：支付回调重复到达时怎么处理

背景：第三方支付网关会在网络抖动时把同一笔成功回调重发 2–3 次（网关文档明示），
      当前回调处理没有去重。
分歧点：靠数据库唯一约束拦，还是靠订单状态机拦。
选项：
  A 在支付流水表加「网关流水号」唯一索引 —— 重复回调直接被数据库拒掉；
    代价：历史数据里若已有重复流水，加索引会失败，得先清一遍（量级未知）。
  B 回调进来先查订单状态，已支付则直接返回成功 —— 不动表结构；
    代价：查状态和改状态之间有并发窗口，两条回调同时到仍可能重复记账。
推荐：A。B 的并发窗口在高峰期真的会撞上，而 A 的代价是一次性清理。
```

用户回「A」后，落盘并展示：

```markdown
### DEC-2：支付回调重复到达的去重方式（2026-08-23）
- 背景：网关会重发成功回调 2–3 次，现无去重。
- 选项：A 支付流水表加网关流水号唯一索引；B 回调先查订单状态再处理。
- 裁决：A
- 理由：B 存在并发窗口，高峰期会重复记账；A 代价为一次性历史数据清理。
- 影响：支付流水表加索引；上线前需先清理历史重复流水。
```

**常见坑**：

- **AI 自己打开这个模式**：本 skill 仅用户触发。AI 觉得"这次问题多，逐题问更好"就自行激活，违反触发纪律。
- **记录写在会话里、没进文件**：只在回复里复述一遍裁决不算落盘；压缩后就没了。
- **把多题打包求一次总体同意**：用户主动一次答多题可以逐条落盘照收，但 AI 不得主动打包。
- **借"唯一解"之名吞题**：上游流程列出的题一道不能少；唯一解也要出题，只是标注后让用户秒批。
- **代价写成实现层形容词**："成本最高""写入放大"读者拍不了板，要写成会看到什么不同、卡住什么动作。
- **为了一屏砍锚点**：一屏放不下的正确动作是拆题，不是删掉锚点或删掉影响裁决的代价。
- **等裁决期间偷偷推进**：禁止假定某选项成立而先干相关的活，哪怕"反正大概率选 A"。
