# code-to-7layer

> 项目无文档、又不想手工拍脑袋排计划？这个 skill 扫一遍代码，反推出「该补哪些文档」的任务总控编排表。

## 这是什么

它是一台**冷启动编排器**：面对一个没有文档（或文档严重过时）的代码库，自动扫描出项目形态、业务域、活跃面，然后产出一份「扫描摘要 + 任务总控文档」，把「该补的七层文档」拆成一张可以逐个推进的子任务表。

**它管的（交付物边界）**：

- Phase 0：自动扫描代码，识别项目形态、业务域、废弃/多版本代码
- Phase 1：把扫描结果一次性丢给你确认（形态对不对、域分得对不对、废弃代码要不要）
- Phase 2：生成「任务总控文档」——一张子任务表，规定每个域每一层各是一个子任务，连依赖顺序都排好

**它不管的**：

- 不真的把每一层文档写出来。具体撰写是「Phase 3」，由 `/control` 这个 skill 逐个子任务驱动，每个子任务单独消耗一次会话预算。
- 不做增量同步（代码改了同步文档）——那是 `doc-layer-system` 的活。
- 不单独补 L1 需求——那是 `docs-from-code` 的活。

一句话：它是排兵布阵的参谋，不是冲锋陷阵的士兵。期望「跑一次就拿到全套文档」是误用。

## 解决什么问题

不用它，从零给一个老项目补文档时你会遇到：

1. **不知道项目是个啥**。是纯后端、纯前端还是全栈？该不该写交互层文档？人工判断容易漏，写了一堆用不上的层，或漏了该写的层。
2. **域边界拍脑袋**。手工划分业务模块时，要么把两个其实是一个域的拆开，要么把废弃的 `/v1` 接口也当成现役功能写进文档，文档一出生就是假的。
3. **任务无从下口**。「补七层文档」是个巨型任务，没人知道先写哪个、后写哪个、谁依赖谁，最后要么烂尾，要么写到一半发现 L1 需要 L3 做基础却还没写。
4. **一次性塞爆上下文**。想让 AI 一口气把所有文档写完，结果会话预算瞬间耗尽，质量还崩。

## 为什么这么设计

- **扫描与撰写分离**。本 skill 只负责「扫描 + 排计划」，撰写交给 `/control` 逐子任务跑。核心取舍：宁可分多次会话、每次只啃一个子任务，也不要一次性把上下文撑爆导致全盘崩坏。
- **三层形态检测**。从仓库级（是不是 monorepo）→ 子项目级（什么框架）→ 运行时入口级（真实执行形态），层层确认，避免单一信号误判。形态决定「裁剪掉哪些层」——纯后端就不写 L2/L5。
- **只问一次**。所有待确认项（形态、域、废弃面、输出路径）合并成一条消息让你拍板，不来回挤牙膏。拍板之前绝不创建任何文件。
- **活跃面识别**。先把废弃代码、多版本并存、Feature Flag 封锁的代码挑出来，默认**不写进正式文档**，交你裁决。这是为了不让文档一出生就背上历史包袱。
- **机械层先行**。L3 契约、L4 持久化是「从代码照抄」的机械层，无依赖、可并行、最先做；L1/L2 这种「重建意图」的层最后做，因为它们要以事实层为基础。

## 怎么用

### 1. 触发词

「冷启动建文档骨架」「反推文档体系总控」「从代码反推文档」「代码到七层」「反推文档体系」。

### 2. 流程

```
Phase 0   →  Phase 0.5  →  Phase 1      →  Phase 2     →  Phase 3（另开会话）
扫描代码     活跃面识别     一次性确认       生成总控表      逐子任务写文档
                                          ↑ 本 skill 到这就停
```

- **Phase 0**：进 skill 后无需你输入，自动扫。输出形态判断（含置信度和证据文件路径）、域候选（每个域附命中的文件作证据）。
- **Phase 0.5**：挑出疑似废弃 / 多版本 / Feature Flag 代码。
- **Phase 1**：把上面所有结果合并成一条消息让你确认。有异议直接改。**这步之前不会创建任何文件。**
- **Phase 2**：你确认后，在 `docs/00-任务总控/YYYY-MM-DD-七层文档反推/README.md` 生成总控表。每个「域 × 层」是一个子任务，跨域共享能力独立成「共享-」子任务。
- **Phase 3**：本 skill 不做。用 `/control <关键词> Tn` 一个个推进。

### 3. 最小示例

```
你：从代码反推文档（指向一个 Spring Boot 项目）

它（Phase 1 一次性确认）：
  我扫描了项目结构，请一次性确认：
  1️⃣ 项目形态：纯后端（置信度：高，证据：pom.xml + UserController.java）
     适用层：L1 / L3 / L4 / L6 / L7    省略层：L2 / L5
  2️⃣ 域候选（3 个）：
     - 「用户」（信号：controller/UserController.java）
     - 「订单」（信号：controller/OrderController.java）
     - 「支付」（信号：controller/PaymentController.java）
  3️⃣ 活跃面：发现 /v1/order 与 /v2/order 并存 → 以哪个为准？
  4️⃣ 输出路径：docs/01-需求/、docs/03-技术设计/接口/ …（默认，可改）

你：形态对；以 v2 为准；其余默认。

它（Phase 2）：
  已生成总控文档 docs/00-任务总控/2026-06-23-七层文档反推/README.md
  子任务总表（按层批次推进）：
  | T1 | 用户-L3契约   | 待完成 | —        |
  | T2 | 订单-L3契约   | 待完成 | —        |
  | T5 | 用户-L6服务端 | 待完成 | T1+T3    |
  | ...                                          |
  接下来用 /control 推进，每个子任务一次会话。
```

### 4. 常见坑

- **以为一次跑完拿全套文档**。错。本 skill 止步于「总控表」，文档撰写要另开会话用 `/control` 一个个跑。
- **跳过机械层直接写需求**。禁止。L3/L4 是 L1/L2 的事实基础，顺序不能反。
- **把废弃代码写进文档**。Phase 0.5 挑出来的疑似废弃面，必须等你 Phase 1 确认才能决定纳不纳入，默认不写。
- **硬暂停字段不暂停**。鉴权/金额/状态机核心/个人信息合规这几类字段含义不明时，必须停下来问你，不允许标个「待确认」就糊弄过去。
- **把工作底稿当成最终文档**。提取期用的「来源/状态/置信度」标注是给 AI 自己核对用的；L5/L6 这种设计层的正文里禁止出现这些尾注，否则文档退化成谁也读不进去的法证报告。
