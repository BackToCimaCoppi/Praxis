# ask-opus

> 把最复杂的分析和执行任务派给一个干净的 Opus 子线程：主线程收集弹药，Opus 做最高规格的推理。给"质量第一、成本不是首要考量"的硬任务用。

## 这是什么

ask-opus 与 ask-sonnet 是同一套"派活问询"机制，区别只在子线程档位——这里用的是 Opus（L3）。它定义了分层协作：

- **主线程（你）= L1 信息收集者**：读文件、提取事实、压成"最小充分包"。
- **子线程（Opus）= L3 推理者**：在干净上下文里做最高深度的推理、架构设计、复杂代码生成。

它管 **问模式**（Opus 只读不改，输出结论）和 **派模式**（Opus 在授权范围内动手改文件）两件事。

它**不管**：自动路由（不说触发词就不调子线程）；也不替子线程下结论。

**何时选 Opus 而非 Sonnet**：需要多轮推理 / 复杂权衡（如跨子系统的架构决策）、代码生成量大且逻辑复杂、需要最高质量、或 Sonnet 已答但用户认为不够可信需要第二意见。一般任务优先用 ask-sonnet，Opus 留给真正的硬骨头。

## 解决什么问题

不用它，直接把全部上下文丢给强模型，会遇到：

1. **token 浪费**：读文件这种廉价机械活也用最贵的模型承担，成本不成比例。
2. **注意力稀释**：原始上下文越杂，强模型越分心，真正需要它算力的判断点反而被埋没。
3. **越俎代庖**：把"已经符合规范"当结论写进去，剥夺了子线程独立验证约束的能力。
4. **派活失控**：让模型自由改代码，可能动了一堆没授权的文件，事后无法纠正。

## 为什么这么设计

1. **L1/L3 分层**：把昂贵的深度推理和廉价的信息收集拆开，只让 Opus 处理"真正需要最强算力"的那部分。
2. **传原文，不传结论**：约束条件内嵌原文，让 Opus 自己验证是否满足，而不是接受主线程的预判。
3. **给清单，不设路障**：文件清单是"最小必读"而非"只准读这些"——Opus 比主线程更清楚该补读什么，放手让它读；但**写**的范围仍由授权边界严格限定。
4. **来源声明**：主线程必须显式告诉 Opus 读了什么、漏了什么，否则它会基于错误假设作答。

## 怎么用

1. **触发词**
   - 问模式："问一下opus"
   - 派模式："让opus去做"、"让opus直接XX"
   - 不说触发词 → 主线程自己处理。触发词模糊 → 先问"问模式还是派模式？"

2. **流程**
   - **问模式**：
     1. 按槽位（具体问题 / 文件引用 / 背景事实 / 约束条件 / 判断标准 / 外部信息）选填上下文
     2. 每项过 RAM 检验句：「Opus 需要 [这项]，才能 [回答问题]，否则卡在 [具体卡点]」，填不完整就删
     3. 写"L1 信息来源声明"（交付形式、最小必读文件清单、未纳入的已知信息）
     4. 用 Agent 工具（model: opus）发出，prompt 末尾声明"不要改任何文件"
     5. 消化结论，用自己的话回答用户，附独立判断；若 Opus 输出"⚠️ 信息不足"，必须向用户说明它基于什么假设
   - **派模式**：
     1. 发任务 + 验收标准 + 禁止区 + 约束（不预设文件清单）
     2. Opus 探索代码，先回"改动范围计划"
     3. 主线程确认/调整范围 → Opus 施工
     4. 主线程按验收清单（范围 / 编译 / 约束 / 验收标准 / 越界）检查 → 报告用户

3. **最小示例**（问模式）

   输入：
   ```
   这个跨三个子系统的消息一致性方案有没有根本性缺陷？

   L1 信息来源声明：
   - 交付形式：直接回复，不写文件
   - 已读文件清单（最小必读，可自行补读）：
     - .../MessageDispatcher.java（只读：dispatch）
   - 未纳入本包的已知信息：无

   背景事实：三个子系统通过消息队列解耦，目前用最终一致性
   约束条件：禁止引入分布式事务框架（运维不接受）
   判断标准：极端情况下不能出现消息丢失或重复消费

   输出要求：直接输出结论，不要改任何文件。
   ```

   产出：一份结论，指出方案在哪些边界条件下会破一致性、约束下有哪些可行的补救方向。

4. **常见坑**
   - **该用 Sonnet 却用了 Opus**：Opus 费用显著更高，简单问答 / 查找别动它。
   - **约束写成结论**：贴规则原文，别替 Opus 下"已符合规范"的判断。
   - **一次调用反复追问**：每次追问都开新的 Agent 调用，别在同一子线程里来回聊。
