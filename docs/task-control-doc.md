# task-control-doc

> 把一个大任务，拆成一叠「换个新会话也能照着干」的自包含工作包。

## 这是什么

task-control-doc 是一套「怎么写一份任务总控文档」的方法论 skill。

当一件事大到一个会话做不完、需要分多次推进时，它教你产出一份总控文档：包含任务背景、总目标、完成定义、范围/非范围、子任务总表，以及每个子任务的「自包含工作包」。文档统一落在 `docs/00-任务总控/{YYYY-MM-DD}-{任务名}/` 下。

边界说明：

- **管**：怎么把大任务切成子任务、每个子任务的工作包怎么写、文档放哪、用哪个模板、子任务总表的列名和状态枚举怎么写（这两项是配套脚本的硬依赖）。
- **不管**：怎么去执行某个子任务、执行时如何守住边界、状态如何回填、最后怎么归档——那是配套 skill `control` 的活。

一句话：task-control-doc 负责「画图纸」，control 负责「照图纸施工」。本 skill 只在创建总控时介入，建完即退场。

## 解决什么问题

不用它，大任务在多会话里推进时常踩这些坑：

1. **上下文爆炸 / 污染**：把整个大任务塞进一个会话，越聊越长，模型开始遗忘前文、串台，越到后面越不可靠。
2. **接手即迷路**：换个新会话继续干，新会话不知道背景、不知道前面做到哪、不知道这一步该读哪些文件，于是从头乱翻或者凭空脑补。
3. **任务边界漂移**：没有事先写死「范围 / 非范围」，后续每个会话都顺手多做一点，任务像滚雪球一样无限膨胀。
4. **进度无处可查**：做到哪了、哪个子任务卡住了、下一个能做哪个，全靠口头记忆，多 worktree 并行时尤其混乱。

## 为什么这么设计

核心机制是 **「子任务即自包含工作包」**：

- 每个子任务展开成一个独立小节，含「子任务背景 / 强制阅读（核心必读 1-3 个）/ **背景导航（可选，不设上限）** / 输入 / **写入范围（机器检查）** / 要做的事情 / 不做什么 / 预期效果 / 输出物 / 完成判定 / 依赖关系 / 风险 / 会话启动提示词」。
- 新会话读「这一个子任务详情 + 它列出的强制阅读文件」就能开工——但这是**准入下限，不是视野上限**：执行者应主动补读背景导航与自行判断需要的背景。强制阅读清单卡的是「至少读这些」，不是「只准读这些」。
- **读什么放开，写什么焊死**：「写入范围」把「只准动本子任务的东西」从口头约定变成机器检查——每个工作包记录开工时的提交 `start_commit`、允许写入的路径 `allowed_write_paths`、唯一允许的跨任务写入 `allowed_cross_task_writes`（精确到父级 README 的 Markdown 标题，通常只有「子任务总表」和「进展记录」两处）。交付前对本子任务列出的候选提交跑 control 配套的写入范围检查器 `check_write_scope.py`，候选提交里夹带越界文件直接失败，越界不得交付；无关提交不参与检查。
- 每个子任务末尾自带一段「会话启动提示词」，可直接复制到新会话开干；提示词的步骤清单里固定包含「交付前跑写入范围检查」这一步。

关键取舍：

- **强制阅读硬限制在 1-3 个文件**，全局强制阅读最多 1-2 个。宁可写细子任务级阅读，也不在全局堆文件。但要和「背景导航」分清：前者是**开工准入的最小充分集**（卡的是成本），后者不设上限（管的是视野）。早期版本把这两件事混成一个「不读清单」，结果为省上下文而饿着执行者——背景不足导致的误判，代价远大于多读几个文件。
- **创建阶段只列一级子任务 T1/T2/T3…，不预先拆二级**。因为动手前根本不知道哪一级会真的太大；需要拆分时再由人在执行中触发 `/control <key> split Tn`，最多两级。
- **子任务总表的列名和状态值是脚本硬依赖，不可自定义**：标题必须叫 `子任务总表`；四列名必须是 `编号 / 子任务 / 状态 / 依赖 / 预期输出`（有少量别名白名单）；状态只能是 `待完成 / 进行中 / 已完成 / 阻塞 / 已取消`。拆分模式下子任务文件名前缀（如 `T1-xxx.md`）必须和总表编号列完全一致，因为 `next_subtask.py` 用 `glob("T1-*.md")` 定位文件。这些约束换来的是 control 那套脚本能自动渲染状态、推荐下一步、校验归档。
- **不写「执行模式」列**：用哪个模型由人在新会话开头用 `/model` 自己定，文档不预定义。

## 怎么用

### 1. 触发词

「为某件事做总控文档」「建任务总控」「这个大任务我想分多会话做」「按标准研发流程建总控」。

中小任务别用——计划模式或 `lightweight-design` + `construction-blueprint` 就够了，总控是给「大、复杂、跨多会话」的任务准备的。

### 2. 流程

1. **自检任务够不够大**：3-7 个子任务、要分多会话、上下文容易爆 → 才上总控。
2. **确认项目已初始化**：`docs/00-任务总控/README.md` 要存在；没有就先跑 control 的 `bootstrap_project.py`。
3. **建任务目录**：`docs/00-任务总控/{YYYY-MM-DD}-{任务名}/`，日期用创建日（防多 worktree 编号撞车），同日多任务加字母后缀。
4. **选载体并套模板**（创建时必须基于模板填充）：
   - 单文件模式（默认，≤7 子任务且各 <50 行）：全部写进 `README.md`，套 `assets/任务总控模板.md`。
   - 拆分模式（8+ 子任务或单包很长）：`README.md` 只放背景+总表+进展，每个子任务拆成独立 `T{n}-{子任务名}.md`，套 `assets/拆分模板/`。
   - （正交可叠加）研发型任务可套「研发流程预设」，由 AI 据一句总需求把八阶段实例化成子任务树，套 `assets/研发流程模板/`。它只决定「有哪些子任务、怎么连依赖」，载体仍按上面规则选。八阶段是：

     ```
     ① 调查 → ② 开放探讨 → ③ 轻量设计 → ④ 测试用例设计 → ⑤ 真值收敛与规格冻结
                                                                    ↓
                                    ⑧ 候选终审 ← ⑦ goal 执行 ← ⑥ goal 章程
     ```

     这条流水线的重心是**把人的出场压到两次**：⑥ 章程拍板一次，⑧ 候选终审一次，中间⑦全自主跑。
     配套四条硬约束：
     - **⑤ 五项冻结闸门全绿才能进⑥**。
     - **⑥ 红队评审按风险触发**（命中死亡线 / 跨域 / 契约破坏，或用户显式要求才评，不再每次必做）；章程同时产出一份**无 PASS/FAIL 的「goal 启动服务单」**，把密钥、登录、真实设备这类用户动作分成四类、提前清算与候选无关的那部分，但不为环境或测试资产签发准入。
     - **⑦ 第一个里程碑固定为 M0 启动检查**：在既有授权内准备并修复环境、测试资产、runner、夹具与证据工具（不设独立的「执行准备」阶段，也不给逐条 AC 预签 Ready）；停机白名单只剩三条（冻结真值矛盾 / 死亡线业务变更 / 未预授权的不可逆或外发动作），跑满限轮只交付 `EXECUTION_BLOCKED` 断点；goal 首次启动、`--resume`、新会话或上下文压缩后，第一次写入前必须从磁盘重读工作包、章程、断点与飞行日志尾部。
     - **⑧ 不可塌缩、不可省略，且由全新上下文只读执行**：终审只出报告和退回指针、不实施整改；缺陷按唯一路由退回——产品 / 测试资产 / runner → 同一 goal，用例语义 → 测试用例设计，正式规格或业务语义 → 轻量设计 + 规格冻结，缺授权 → 用户补权。自主执行交出候选后无人终审，是有事故记录的结构缺口（候选悬空无人验收、未合并分支在共享环境互相覆盖）；终审内顺手修则会把它变成第二个施工 loop。

     套研发流程预设时，各阶段的强制阅读必须按职责绑定到具体 skill（测试用例阶段绑 `test-standards` + `test-case-design`，章程阶段绑 `goal-charter`，执行阶段绑章程 + `test-execution-router` + 项目执行入口，终审阶段绑证据协议 + 冻结 L7），不能只在背景导航里「提一下」。
5. **填必备章节**：任务背景 / 总目标（结果导向 3-7 条）/ 完成定义（可检查）/ 范围 / 非范围（防扩张）/ 全局强制阅读 / 全局约束 / 子任务总表 / 子任务详情 / 风险待确认 / 进展记录 / 更新规则。
6. **逐个写子任务工作包**：每个都按「自包含」标准写，强制阅读精准、写入范围结构化（`start_commit` / `allowed_write_paths` / `allowed_cross_task_writes`）、输出物可检查、完成判定可验、末尾带会话启动提示词。
7. **过程资产规则告知子任务作者**：执行中产生的中间文档（设计稿、清单、批判稿等）只能进唯一目录 `_shared/`，归属靠文件名前缀——子任务专属用 `T{n}-` 前缀，任务级共享用无前缀中文名。禁止平铺到任务根目录，禁止新建 `_T{n}/` 目录。所有资产路径登记在对应子任务的「输出物」字段。
8. **登记到活跃索引**：在顶层 `docs/00-任务总控/README.md` 的「当前活跃任务」表追加一行。

### 3. 最小示例

输入：

> 我要把支付模块重构成新架构，活儿不小，想分几次会话做，帮我建个总控。

产出（单文件模式 `docs/00-任务总控/2026-06-23-支付重构/README.md` 的子任务总表部分）：

```markdown
## 8. 子任务总表

| 编号 | 子任务 | 状态 | 依赖 | 预期输出 |
|------|------|------|------|---------|
| T1 | 现状梳理与新架构设计 | 待完成 | 无 | 架构方案、接口契约 |
| T2 | 数据层改造 | 待完成 | T1 | 新数据层代码 |
| T3 | 接口层迁移 | 待完成 | T2 | 迁移后接口代码 |
```

每个子任务在 §9 展开成独立工作包，末尾带可直接复制的「会话启动提示词」。之后用 `control` skill 逐个推进。

### 4. 常见坑

- **改了总表列名或状态枚举**：脚本立刻识别失败。`子任务总表` 这个标题、四列列名、五个状态值都是硬锚点，不能改别名。
- **拆分模式文件名和编号对不上**：表里写 `T1`，文件却叫 `T01-xxx.md` 或 `t1-xxx.md` → `next_subtask.py` 定位不到。前缀必须完全一致。
- **创建阶段就把二级拆好**：违背设计意图，动手前不知道哪级会爆。先只列一级，需要时再 split。
- **全局强制阅读堆一堆文件**：违反最小上下文原则。具体执行所需文件应下沉到子任务级，全局最多 1-2 个。
- **非范围章节空着**：等于没给后续会话设护栏，任务会无限膨胀。
- **输出物写得抽象**：「把需求整理好」不可检查；要写成「补齐 `docs/01-需求/xxx.md`」这种明确可交付物。
- **过程资产平铺或新建 `_T{n}/` 目录**：只能进 `_shared/`，靠文件名前缀区分归属。
- **工作包没写「写入范围」，或候选提交夹带越界文件**：交付前的写入范围检查直接失败。跨任务写入只允许精确到标题的例外（父级 README 的「子任务总表」「进展记录」），goal 章程回填下游 goal 执行包的「会话启动提示词」段是流程里唯一另加的例外。
- **把 goal 章程红队当成每次必做，或在候选终审里顺手修 bug**：现行规则是章程评审按风险触发；终审只读，发现问题按固定路由退回同一 goal 或上游阶段，不在终审内整改。
