# test-execution-router

> 冻结用例怎么变成真正跑过的证据：同一次自主执行内先做 M0 启动检查再正式验证，路由到项目执行层、按顺序跑、逐条对账、证据单向、失败必须分类。

## 这是什么

测试三件套的第三层——**执行层入口**。它读已冻结的用例规格，生成执行面矩阵，按测试面把每条用例路由到项目自己的执行 skill，然后约束执行顺序、证据收集、失败分类和交付收口。

它在同一次自主执行（goal，见 `goal-charter`）里分两种模式工作：**`bootstrap` M0 启动检查**——goal 的首个里程碑，只负责把测试资产、runner、夹具、环境适配和证据工具修到"能开始工作"，每个命中面跑一个最小健康探针；**`verification` 正式验证**——在各施工切片内和候选交付前跑冻结矩阵、封存原始证据、派生证据状态。

它本身**不含任何项目命令**：命令、凭据、浏览器与设备细节全部在项目执行 skill 里，本 skill 只负责"谁该去哪儿、跑完要交什么"。

- **管**：两种模式的硬门与边界、执行面矩阵、路由、执行顺序、测试资产与环境的构建/修复、单向证据链、编号覆盖核对、失败分类、可复用执行资产的晋升与交接、执行报告与交付判断。
- **不管**：用例口径（回 `test-case-design` 改）、要不要测这个面（回 `test-standards`）、项目具体命令（进项目执行 skill）。

## 解决什么问题

用例写得再好，执行环节仍有四条路能把它稀释掉，而且每条都很好找借口：

- **边执行边改断言**：跑不过就顺手把断言调松，规格冻结在这一步前功尽弃。
- **"环境不方便"就跳过自动化**：一句话跳过，没有阻断、没有登记。
- **手工验证计入自动化覆盖**：报告上看起来覆盖率一样，实际没有任何可重复的回归资产。
- **失败只写"测试失败"**：不分类就没有处置。产品 bug、脚本 bug、规格过期、环境问题、间歇性失败，处理方式完全不同——混成一句话之后，最省事的处置永远是改断言。

还有一个更隐蔽的：**编号出现 ≠ 覆盖**。测试文件里写了 `AC-7` 三个字，不代表那条断言的语义、测试形状真的被验证了。没有一道明确的对账工序，编号机制自己就会退化成走过场。

证据链上还有两种更难察觉的失真：

- **状态账本自证**：先在账本里填一个 VERIFIED，再去找（或补）能对上的运行痕迹。套件退出码为零、日志里出现某个哈希、文件存在——这些"代理观测"看起来是绿的，却证明不了任何一条断言。
- **启动阶段提前签发 Ready**：环境刚能跑通一个探针，就把逐条验收标成"就绪"；或者反过来，把"准备好了才能开工"做成一道独立门票，测试基础设施的每个小毛病都能把整条上游卡死。

还有一条跨任务的漏洞：一个任务里辛苦修好的 runner 和夹具，要么只留在本地工作树，下一个任务无声重造；要么躺在别的分支上，却被宣称"已经继承"。

## 为什么这么设计

- **同一 goal 内分两种模式，但不设独立"就绪门票"**：`bootstrap` 只回答"执行基础设施坏了，还是可以开始工作"，报告状态仅限 `HEALTHY / REPAIRED / BLOCKED_AUTH / MANUAL_BOUNDARY`，禁止逐 AC 预演或签发 Ready；它的失败先在 goal 内自愈，不回退上游。只有冻结真值互相矛盾、死亡线业务规则要变、未预授权的不可逆/外发动作、计划内的真实人工里程碑才交给用户；安全路径穷尽时只交付 `EXECUTION_BLOCKED`。
- **两种模式共用四道硬门**：必须已读冻结用例、已确认执行落点、已生成执行面矩阵（单元 / 接口 / DB 预置 / DB 终态 / Web 或后台 UI / 小程序 UI / 视觉 / 手工，命中面各一行，N/A 要有可核理由）、已识别项目执行 skill（没有就先报缺口）。四门都是"事前可验"的，不给"跑起来再说"留口子。涉及真实动作时还必须有上游用户授权锚点，锁定目标环境、精确动作、目标对象、费用上限与副作用范围。
- **路由表按测试面而不是按工具**：单元 / 接口 / DB / Web UI / 小程序 UI / 视觉 / 交付验证 / 手工，各自指向项目执行 skill 的对应参考。这样换工具只改项目层，方法论层不动。
- **默认执行顺序按"快反馈 + 依赖"排**：静态与单元最先（暴露局部缺陷最便宜），然后数据前置、接口、DB 校验，再到 UI 自动化与视觉验收，最后交付收口。允许调整但必须说明原因（例如 UI 用例依赖接口造数完成）。
- **编号覆盖核对是独立工序**：逐条把冻结的断言编号在测试资产里找到字面落点；项目检查器必须通过，没有检查器的项目才用人工逐条对账表。**有编号无落点 = 阻断**。
- **证据链单向**：顺序固定为 raw 运行先发生 → 采集时不可变信封 → AC 映射 → 状态账本，信封与 raw 放在同一个内容寻址包里，任何状态都只能从该包重算。自动化 raw 必须来自框架原生报告或真实扫描器输出，wrapper 只准规范化与装配；套件退出码、文件存在、日志/聚合哈希、源码位置都是代理观测，不能单独签发 `VERIFIED`。多个 AC 可共享一个真实测试，但每个 AC 要满足用例层定义的全部证明部件，缺一即 `MISSING`。
- **消费者完整性与观测分布报告**：每个已执行的测试/套件必须被至少一个 AC 消费，或显式声明只是辅助；任何失败、错误、跳过、已绑定未执行的测试都阻断候选。候选交付前要出一份观测分布报告，把代理观测、重复簇、孤儿套件、未消费失败、多部件缺口列成数量与明细，任一非零不得报 `CANDIDATE_READY`。
- **失败分类是封闭清单**：产品 bug / 测试基础设施 bug / 规格语义缺陷 / 环境 / 间歇 / 物理边界 / 缺授权——每一类都绑定了唯一处置方式。其中"测试基础设施 bug 在 goal 内修资产，**不改用例断言**、不让小错使全部上游失效"是防作弊的最后一道；"缺授权"单独成类，是为了堵住"没权限就偷偷降级成模拟"这条路。
- **区分真连绿与模拟绿**：交付判断里两者分开计，模拟绿必须逐条写明真实链路的收口去向。合并统计等于把风险藏进汇总数字里。
- **规格缺陷按语义影响面处置**：`SPEC_STALE` 默认热修——附修改方案经业务决策负责人按项目治理批准后直接修订用例/正式层，按影响面作废并重跑下游，回同一 goal 续跑；热修不可靠且获相应批准才回退用例设计或设计与规格冻结子任务。执行层只做分流，不做裁决。
- **可复用执行资产必须晋升并登记，而不是留在本地**：候选交接前把本轮新增/修复的执行资产分成任务临时、领域/场景复用、项目通用三类；后两类要提交到项目稳定路径并登记入口、前提、验证命令与已知消费者。资产只在兄弟分支上时标 `PROPAGATION_REQUIRED`，后续任务在 commit 可达前不得宣称继承成功。这是交接义务，不是新的准入闸：登记不完整不停机。

## 怎么用

**触发场景**：goal 启动检查（M0）、把用例规格落成脚本、正式测试、测试失败需要分类。

**流程 · `bootstrap` M0 启动检查**：

1. 读冻结用例、执行面矩阵、上游授权与项目执行 skill，逐面加载对应参考。
2. 先盘点项目已有的正式测试基座、稳定 runner/夹具/环境适配及其登记索引，逐项记录稳定路径、来源 commit、当前分支是否可达；可复用且可达的先复用，禁止无声重造。
3. 每个命中面填写环境身份/保真度、凭据位置、数据建立/清理/恢复、部署通路、预算、最小健康探针与人工边界；N/A 面写证据化理由。
4. 实现或修复执行落点、测试资产、runner、夹具、环境适配与证据工具——错误命令、路径、依赖都属于本模式自愈项。
5. 每个命中面只跑一个健康探针，报告状态限于 `HEALTHY / REPAIRED / BLOCKED_AUTH / MANUAL_BOUNDARY`。
6. 输出启动检查报告：它是 goal 的首个运行记录，不是章程准入证明，也不冻结测试资产版本。

**流程 · `verification` 正式验证**：

1. 复验冻结用例、启动检查报告、当前测试资产和候选 commit/tree。
2. 按路由表交给项目执行 skill 跑冻结矩阵；发现测试基础设施缺陷就在同一 goal 内修，登记影响面并重跑受影响部分。
3. **编号覆盖核对**：逐条找字面落点，项目检查器必须通过；有编号无落点即阻断。
4. 每次运行按单向证据协议封存 raw 与信封，再派生 `VERIFIED / BLOCKED / MISSING / WAIVED`。
5. 跑项目执行证据检查器；失败按分类表路由，产出执行报告（执行矩阵、编号覆盖、语义证据分布、数据策略、失败分类、交付判断）。

**失败分类表**：

| 分类 | 含义 | 处置 |
|---|---|---|
| `PRODUCT_BUG` | 实现与冻结用例或上游真值不符 | 路由 goal 修产品代码，重跑 |
| `HARNESS_BUG` | 测试资产、runner、夹具或证据工具错了，但用例口径对（旧 `TEST_BUG` 等价映射到此类） | goal 内修复，按影响面重跑，**不改用例断言** |
| `SPEC_STALE` | 冻结用例或上游正式真值的语义确有缺陷 | 默认热修：修改方案获用户一次批准后修订用例/正式层，按影响面作废重跑下游并续跑；不可靠才回退上游子任务 |
| `ENV` | 服务、网络、依赖、测试数据环境问题 | goal 内修环境或重建数据后重跑 |
| `FLAKE` | 时序或异步导致间歇失败 | 修等待与隔离；连续 flake 不得当通过 |
| `MANUAL_REQUIRED` | AI 无法操作真实设备/原生对象/原生授权等物理边界 | 输出物理边界证明、runbook、客观回传要求与写明责任角色的人工里程碑 |
| `AUTHORITY_REQUIRED` | 所需真实动作未获授权或凭据位置未知 | 停在对应环境所有者/发布授权人补权或告知受控位置；不得猜测或偷偷降级为模拟 |

**常见坑**：

- **在这一层改用例口径**：口径问题一律回用例层改并留痕，执行层没有裁决权。
- **把手工验证计进自动化覆盖**：两者在报告里必须分开，手工只产出 runbook 与回传要求。
- **把能自动化的东西降级为手工**：AI 可控浏览器/开发者工具、DOM 或数据断言、截图与 VLM 判读都不算物理边界；`MANUAL_REQUIRED` 必须附物理边界证明。
- **跳过编号覆盖核对**：这是整条追溯链唯一的机械验证点，跳过之后前面所有编号工作都变成装饰。
- **失败后先改断言再说**：先分类，分类结果决定改哪一侧。改测试资产里的断言只在"资产把用例翻译错了"这一种情况下合法，用例口径本身不动。
- **在启动检查里给逐 AC 签 Ready**：M0 只证明基础设施能开工；完整的 AC 证明只能从正式验证的 raw 单向证据链产生。
- **状态账本自证、拿代理观测当绿**：先有 raw 再有账本，反向补 raw、事后补绑候选版本或环境、把派生聚合物冒充 raw 全部禁止；套件退出码为零不等于任何一条 AC 通过。
- **修好的 runner 只留在本地**：候选交接必须有"执行资产交接"段；没有可晋升资产就明写"本轮无可晋升资产"，别让下一个任务重造或误以为已继承。
- **报告只写通过/失败**：必须给出可交付判断、真连绿与模拟绿分计、阻断项与手工例外。
