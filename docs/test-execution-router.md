# test-execution-router

> 冻结用例怎么变成真正跑过的证据：路由到项目执行层、按顺序跑、逐条对账、失败必须分类。

## 这是什么

测试三件套的第三层——**执行层入口**。它读已冻结的用例规格，生成执行矩阵，按测试面把每条用例路由到项目自己的执行 skill，然后约束执行顺序、证据收集、失败分类和交付收口。

它本身**不含任何项目命令**：命令、凭据、浏览器与设备细节全部在项目执行 skill 里，本 skill 只负责"谁该去哪儿、跑完要交什么"。

- **管**：执行前硬门、执行矩阵、路由、执行顺序、编号覆盖核对、失败分类、执行报告与交付判断。
- **不管**：用例口径（回 `test-case-design` 改）、要不要测这个面（回 `test-standards`）、项目具体命令（进项目执行 skill）。

## 解决什么问题

用例写得再好，执行环节仍有四条路能把它稀释掉，而且每条都很好找借口：

- **边执行边改断言**：跑不过就顺手把断言调松，规格冻结在这一步前功尽弃。
- **"环境不方便"就跳过自动化**：一句话跳过，没有阻断、没有登记。
- **手工验证计入自动化覆盖**：报告上看起来覆盖率一样，实际没有任何可重复的回归资产。
- **失败只写"测试失败"**：不分类就没有处置。产品 bug、脚本 bug、规格过期、环境问题、间歇性失败，处理方式完全不同——混成一句话之后，最省事的处置永远是改断言。

还有一个更隐蔽的：**编号出现 ≠ 覆盖**。测试文件里写了 `AC-7` 三个字，不代表那条断言的语义、测试形状真的被验证了。没有一道明确的对账工序，编号机制自己就会退化成走过场。

## 为什么这么设计

- **执行前设四道硬门**：必须已读冻结用例、已确认执行落点、已生成执行矩阵、已识别项目执行 skill（没有就先报缺口）。四门都是"事前可验"的，不给"跑起来再说"留口子。
- **路由表按测试面而不是按工具**：单元 / 接口 / DB / Web UI / 小程序 UI / 视觉 / 交付验证 / 手工，各自指向项目执行 skill 的对应参考。这样换工具只改项目层，方法论层不动。
- **默认执行顺序按"快反馈 + 依赖"排**：静态与单元最先（暴露局部缺陷最便宜），然后数据前置、接口、DB 校验，再到 UI 自动化与视觉验收，最后交付收口。允许调整但必须说明原因（例如 UI 用例依赖接口造数完成）。
- **编号覆盖核对是独立工序**：逐条把冻结的断言编号在测试资产里找到字面落点；有检查器就跑检查器，没有就人工产出逐条对账表。**有编号无落点 = 阻断**。
- **失败分类是封闭清单**：产品 bug / 脚本 bug / 规格过期 / 环境 / 间歇 / 确需手工——每一类都绑定了唯一处置方式。其中"脚本 bug 修脚本，**不改用例断言**"是防作弊的最后一道。
- **区分真连绿与模拟绿**：交付判断里两者分开计，模拟绿必须逐条写明真实链路的收口去向。合并统计等于把风险藏进汇总数字里。
- **规格过期在自主执行态下的特判**：常规情况下"规格已变、用例过期"要停机请人裁决；但如果是**刚刚冻结的规格立刻就过期**，那说明规格本身错了，应当走回炉出口（终止本次自主执行、退回设计步），而不是原地停机等人。

## 怎么用

**触发场景**：准备执行测试、把用例规格落成脚本、部署后跑自动化、自主执行交付前的测试环节、测试失败需要分类。

**流程**：

1. 读冻结用例规格与测试矩阵。
2. 校验每条用例的来源、数据策略、自动化方式、执行落点。
3. 生成执行矩阵：测试面、执行顺序、所需数据、证据路径、阻断条件。
4. 按路由表交给项目执行 skill 的对应参考。
5. 执行或实现测试资产。
6. **编号覆盖核对**：逐条找字面落点，有编号无落点即阻断。
7. 收集证据：命令与工具、结果、截图或日志、数据库终态、失败分类。
8. 产出执行报告，未通过项必须给下一步处置。

**失败分类表**：

| 分类 | 含义 | 处置 |
|---|---|---|
| `PRODUCT_BUG` | 实现与冻结用例或上游真值不符 | 修产品代码，重跑 |
| `TEST_BUG` | 脚本错了但用例口径对 | 修脚本，**不改用例断言** |
| `SPEC_STALE` | 上游真值已变，用例过期 | 停机请人裁决；自主执行态下走回炉出口 |
| `ENV` | 服务、网络、账号、依赖、数据环境问题 | 修环境或重建数据后重跑 |
| `FLAKE` | 时序或异步导致间歇失败 | 修等待与隔离；连续 flake 不得当通过 |
| `MANUAL_REQUIRED` | 确实无法自动化 | 输出 runbook 与客观回传要求 |

**常见坑**：

- **在这一层改用例口径**：口径问题一律回用例层改并留痕，执行层没有裁决权。
- **把手工验证计进自动化覆盖**：两者在报告里必须分开，手工只产出 runbook 与回传要求。
- **跳过编号覆盖核对**：这是整条追溯链唯一的机械验证点，跳过之后前面所有编号工作都变成装饰。
- **失败后先改断言再说**：先分类，分类结果决定改哪一侧。改断言只在"脚本翻译错了"这一种情况下合法。
- **报告只写通过/失败**：必须给出可交付判断、真连绿与模拟绿分计、阻断项与手工例外。
