# commit-changes

> 受控的 git 提交流程：先看清改了什么，再逐文件 stage，最后写一条规范的中文提交信息。

## 这是什么

一套「提交前必须走完的检查动作」。它把一次 git 提交拆成固定步骤：跑门禁脚本 → 看状态 → 读 diff → 拟定 stage 清单并等你确认 → 写提交信息 → 提交 →（按需）推送。

边界：

- **管**：staging 哪些文件、提交信息怎么写、提交前是否过门禁、是否推送。
- **不管**：代码本身写得对不对（那是 review 的事）、分支策略、合并冲突解决、远端权限。
- **硬规矩**：永远不用 `git add -A` 或 `git add .`；不主动 amend、不主动 force-push；未经明确要求不推送。

## 解决什么问题

不用它时，自动化提交容易踩这几类坑：

1. **一把梭 stage**：`git add .` 把临时文件、调试代码、半成品、别的任务的改动一起提交进去，污染历史，回滚困难。
2. **盲提交**：没读 diff 就提交，把不该带的改动（密钥、注释掉的代码、跑偏的实验）一起带走。
3. **提交信息混乱**：信息要么是 `update`、`fix bug` 这种废话，要么中英混杂、没有类型前缀，后人翻历史完全看不出这次改了什么。
4. **跳过门禁**：项目本来有提交前检查脚本，但手一快直接提交，把本可拦下的问题带进主干。

## 为什么这么设计

- **stage 必须逐文件、且要你确认**：这是最核心的取舍。宁可慢一点逐个 `git add <路径>`，也不接受 `git add .` 的便利——因为一次错误的批量 stage 比慢几秒钟代价大得多。stage 清单先报给你、等你点头再执行，把「提交什么」的决定权留在人手里。
- **先门禁、再看、再提交**：门禁脚本 `exit 1` 直接中止整个流程，逼你先修问题；`[WARN]` 不阻断但会写进最终汇报。顺序固定，避免「提交完才发现检查没过」。
- **提交信息走固定模板**：`<类型>: <简要描述>`，类型限定在固定几个词里，强制中文。模板本身就是约束，挡掉「随手写一句」的随意。
- **保守默认**：不 amend、不 force-push、不自动 push。这些都是高破坏性操作，只在你明确说出口时才做。

## 怎么用

1. **触发词**

   「提交」「commit」「push」「推送」「帮我提交」。

2. **流程**（一步步走查）

   - **Step 0 门禁（有则必跑）**：若项目存在提交前门禁脚本（如 `.claude/hooks/pre-commit-check.sh`）就先跑。`exit 1` → 停下，报告失败项，修完再来；有 `[WARN]` → 记下，照常往下走。没有门禁脚本则跳过本步。
   - **Step 1 看状态**：`git status --short`，分清哪些是已跟踪的修改、哪些是新文件。
   - **Step 2 读 diff**：`git diff` 看工作区、`git diff --cached` 看已暂存，判断改动主题、涉及模块、有没有混进无关改动需要拆开提交。
   - **Step 3 拟 stage 清单并等确认**：以 `git add <具体路径>` 形式列出要 stage 的文件，报给你，等你确认后才执行。**禁止 `git add -A` / `git add .`**。
   - **Step 4 写提交信息**：格式 `<类型>: <简要描述>`，类型限 `修复` / `功能` / `重构` / `规范` / `文档` / `配置`。
   - **Step 5 提交**：`git commit -m "<message>"`。
   - **Step 6 推送**：只有你明确说了「push / 推送」才执行，否则不动远端。

3. **最小示例**

   ```
   输入：帮我把刚改的登录逻辑提交了

   走查：
     git status --short
       M  src/auth/login.ts
       M  src/auth/session.ts
       ?? src/auth/debug.tmp        ← 临时文件，不 stage

   拟 stage（等确认）：
     git add src/auth/login.ts src/auth/session.ts

   提交信息：
     修复: 登录会话过期后未正确清理本地态

   产出：
     git commit -m "修复: 登录会话过期后未正确清理本地态"
     （未要求 push，停在本地）
   ```

4. **常见坑**

   - **想偷懒用 `git add .`**：这是红线，再急也不行。新文件、临时文件得一个个看清楚再决定。
   - **门禁 `exit 1` 还硬提交**：检查失败必须先修，不能跳过。
   - **把看不懂的改动一起提交**：工作区里有你不理解、与本次任务无关的改动时，拆出去单独处理，别打包带走。
   - **以为提交完会自动 push**：默认不推送，需要上远端要明说。
   - **提交信息漏类型前缀或写成英文**：必须是中文 + 固定类型前缀。
