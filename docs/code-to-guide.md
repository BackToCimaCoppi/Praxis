# code-to-guide

> 接手一个看不懂的陌生代码库？这个 skill 组建一支只读调研小队，一次性产出一套「AI 读一遍就能上手」的项目导览文档。

## 这是什么

它是一个**轻量级、只读、一次性**的项目调研工具。给它一个陌生或遗留代码库，它会自动扫描结构、按模块派出并行子 agent 调研、汇总成一套结构化的项目导览文档（放在 `docs/<项目名>/` 下），最后还会派一个「新人 agent」只读这套文档来验收清晰度。

**它做什么**：

- 读现有项目代码，理解模块结构、数据模型、接口、业务逻辑
- 产出两层文档：**参考层**（是什么——字段表、接口表、枚举）和**理解层**（为什么/怎么用——设计动机、业务场景）
- 建一个 README 作为 AI 读文档的唯一入口（含文档地图、推荐阅读路径、术语速查）

**它不做什么**：

- 不改项目代码（纯只读）
- 不建七层文档体系，不产出需求文档（L1）
- 不跟随项目生命周期演进——它是一次性快照，不是持续维护的文档体系

## 解决什么问题

接手陌生代码库时，不用它你会遇到：

1. **整体认知建不起来**。代码几百个文件，从哪读起？模块边界在哪？人工一个个翻，翻到一半就晕了。
2. **AI 每次都得重新摸索**。没有结构化导览，让 AI 帮你改这个项目，它每次都要把代码翻一遍，上下文反复浪费。
3. **「是什么」和「为什么」混在一起**。光看字段表知道有哪些接口，但不知道为什么这么设计；光看设计文档又查不到具体字段。两者混写，AI 每次加载都被无关信息淹没。
4. **跨模块业务流程没人讲清**。支付链路、商品创建链路这种跨好几个模块的流程，单看任何一个模块的代码都拼不出全貌。

## 为什么这么设计

- **主 agent 扫结构，子 agent 啃模块**。Phase 1 主 agent 亲自摸出模块地图，Phase 2 按内聚模块拆成 6~8 个并行的只读子 agent（`Explore` + `sonnet`），每个 agent 只负责一个 bounded context、只给明确文件清单。核心取舍：scope 一定要小，宁可拆多也别合并太多，否则上下文被稀释、报告失真。
- **参考层与理解层物理分离**。两层必须是不同文件，绝不混写。因为混写会让 AI 每次加载都背上大量无关信息——查字段时不想看设计动机，看动机时不想被字段表淹没。
- **理解层必须单独投入**。模块级报告天生拼不出跨模块业务流程，所以设计动机和业务场景需要主 agent 综合，复杂链路还要专门追一轮「流程追踪 agent」。
- **README 最后写**。它是 AI 读文档的唯一入口，依赖所有其他文档写完才能准确做索引和阅读路径，所以一定最后生成。
- **新鲜视角自检**。最后派一个没有任何调研上下文的 agent，只读文档（禁读代码）复述项目、挑毛病、打分。这是用「局外人视角」检验文档到底能不能让人看懂。

## 怎么用

### 1. 触发词

「理解陌生项目」「生成项目导览文档」「代码到说明书」「AI 友好项目文档」「摸清一个代码库」「分析这个项目」「给这个项目做文档」「项目说明书」「项目调研文档」。

### 2. 流程

```
Phase 1  项目扫描      → 主 agent 摸结构，产出模块地图（表格）
Phase 2  并行派发      → 按模块拆 6~8 个只读子 agent，并行调研
Phase 3  汇总两层文档  → 参考层（NN-模块.md）+ 理解层（00-design.md / NN-scenarios.md）
Phase 4  建 README     → AI 唯一入口：文档地图 + 阅读路径 + 术语速查
Phase 5  新鲜视角自检  → 独立 agent 只读文档复述+挑刺+打分，主 agent 据此修补
```

- **Phase 2 子 agent 铁律**：只读不写文件（统一由主 agent 汇总后写，避免并发写冲突）、给死文件清单不让它自己扩展搜索、返回结构化中文报告。
- **Phase 3 两层分离**：参考层每个模块一份文件，可并行整理；理解层跨模块，主 agent 综合。
- **每份参考文档头部加导读行**，链回 README 和 design，否则 AI 在文档间迷路。

### 3. 最小示例

```
你：摸清一下这个项目（指向一个 Java 后端代码库）

它（Phase 1 模块地图）：
  | 模块名 | 目录路径        | 核心职责       | 代表文件                  |
  | 商品   | src/.../product | 商品建模与查询 | Product.java, ProductSvc  |
  | 订单   | src/.../order   | 下单与履约     | Order.java, OrderService  |
  | 支付   | src/.../pay     | 支付链路       | PayService, PayChannel    |

它（Phase 2~5，自动并行调研后产出）：
  docs/<项目名>/
    ├─ README.md          ← AI 入口：文档地图 + 阅读路径 + 术语速查
    ├─ 00-design.md       ← 为什么这样分层/拆模块
    ├─ 01-data-model.md   ← 参考层：实体字段表
    ├─ 02-order-api.md    ← 参考层：接口表
    └─ 03-scenarios.md    ← 理解层：支付链路端到端数据流
  新鲜视角自检：清晰度 4/5，已补充「ExampleMode」术语解释。
```

### 4. 常见坑

- **让一个 agent 负责「整个项目」**。scope 太大上下文被稀释，报告会糊。一定按内聚模块拆小。
- **指望从模块报告拼出业务场景**。拼不出来。理解层必须单独投入，跨模块流程要专门追踪。
- **字段手册和叙述混写**。参考层和理解层必须物理分成不同文件，否则 AI 每次加载都吃一堆无关信息。
- **忘记反链**。每份参考文档都要有头部导读行（含 README 和 design 的链接），不然 AI 在文档间迷路。
- **先写 README**。README 依赖所有其他文档写完才能准确索引，必须最后写。
- **子 agent 自己写文件**。多个 agent 并发写同一目录会冲突或重复。子 agent 只返回报告文本，主 agent 统一落盘。

> 注意：本 skill 与七层文档体系（`code-to-7layer` / `doc-layer-system`）完全无关，产出的是「项目说明书」而非「需求文档」。要建七层体系或补 L1 需求，请走对应 skill。
