# long-doc-governance

> 文档太长时才治理，而且只在你正好要实质改它的那一轮顺手拆——不主动去翻动现有文档。

## 这是什么

长文档治理是一套**增量式拆分文档**的方法论：当一份业务文档长到超过阈值、且本轮任务正好要对它做实质修改时，把它按业务边界拆成多个子文件，并修好所有引用。它管的是"什么时候该拆、怎么判断微改豁免、怎么安全拆"。

- **管**：`docs/` 下的业务文档（接口协议、Schema、设计文档、总控等）的长度治理与拆分。
- **不管**：归档目录（`05-归档/`、`06-05-归档/`）下的文档不治理；`CLAUDE.md` / `AGENTS.md` / `SKILL.md` 不受管控、不扫描。

## 解决什么问题

不做长文档治理，或者治理方式不对，会遇到这些痛点：

- **超长文档难维护**：一份上千行的接口文档，AI 读它要烧大量上下文，人改它也容易改错位置。
- **一上来就大拆特拆**：看到长文档就主动重排，结果引入一堆与本次任务无关的改动，评审和回退都变重。
- **微改也被当成大工程**：只是修个错别字、bump 个版本号，却触发整篇拆分，纯属浪费。
- **拆分喧宾夺主**：主任务只要 10 分钟，拆文档却要花 1 小时，没人提前告知，时间预算失控。

## 为什么这么设计

- **增量治理，不主动拆**：只在"本轮对超长文档做实质修改"时才治理，绝不主动去翻动现有文档。这样拆分总是搭着已有改动一起发生，不凭空制造大 diff。
- **微改豁免**：错别字、纯排版、链接修复、版本号 bump、< 20 行的措辞润色都豁免。自检方式是 `git diff --stat` 看增删行数——语义增量 > 20 行 或 新增 H2/H3 标题 → 算实质修改。
- **拆分预算退路**：拆之前先估时间（`目标行数 / 200 × 5 分钟`）。一旦预估时间 > 主任务工作量 × 1.5，**停下来让用户三选一**，不自作主张地把小任务拖成大工程。
- **按业务边界拆，不按行数切**：子文件以功能模块划分，每个子文件目标 < 警告阈值 × 70%，留出后续增长空间。

## 怎么用

1. **触发词**：`post-change-check` 报 `[CRITICAL]` 长文档警告且本轮有实质修改；用户说"拆文档"、"文档太长"、"split doc"、"文档拆分"；或本轮要实质修改的文档行数已达强制阈值。

2. **流程**：
   - **先判微改还是实质改**：`git diff --stat` 看增删；纯错别字/排版/链接/版本号/< 20 行润色 → 微改豁免，不治理。新增 H2/H3 或语义增量 > 20 行 → 实质修改，继续。
   - **对照阈值表**（只对 `docs/` 业务文档生效）：

     | 类型 | 警告阈值 | 强制阈值 |
     |---|---|---|
     | 接口协议 / 测试 / Schema | 600 行 | 1000 行 |
     | 设计文档 / 总控 / 施工蓝图 / 技术方案 | 800 行 | 1500 行 |

   - **估拆分预算**：`预估时间 ≈ 目标行数 / 200 × 5 分钟`。若 > 主任务 × 1.5，给用户三选一（A 先拆再做 / B 单独排拆分任务本次先改完 / C 本次例外，在任务级设计文档写明原因）。
   - **分析结构**：`grep -n "^## " <file>` 列出 H2 标题与行号，`wc -l` 看总行数，按功能模块识别业务边界。
   - **规划子文件**：每个子文件 < 警告阈值 × 70%；原文件改名移入新目录，建 `00-总览` 索引列各子文件链接。
   - **执行拆分**：子文件路径遵守层级编号规则（`NN-名称.md`）。
   - **修复引用**：`grep -rn "旧文件名" .`（连 `.md` / `.java` / `.ts` 一起查），逐个改为新路径，确保 anchor 锚点仍在。
   - **验证**：若项目有文档层级门禁脚本则运行，没有就人工核对层级编号检查通过。
   - **提交**：提交信息形如 `重构: 长文档治理 — XXX 拆分为 XXX/ 子目录`。

3. **最小示例**：

   ```
   输入：03-01-前后端接口协议.md（1200 行，命中接口协议强制阈值）
          本轮要给它新增"第三方支付回调"一节（实质修改）

   产出（按业务模块拆分）：
   03-01-前后端接口协议/
     ├── 00-总览与公共约定.md   ← 鉴权、错误码、分页、命名约定 + 子文件索引
     ├── 01-用户模块.md
     ├── 02-订单模块.md
     └── 03-第三方集成.md       ← 新增的支付回调写在这里
   ```

4. **常见坑**：
   - **没改也去拆**：本轮没有对该文档实质修改，就不该治理它——增量治理是底线。
   - **把实质改当微改**：重写一段 50 行设计描述、把功能从一处搬到另一处、新增接口参数说明，都不算微改。
   - **按行数硬切**：拆分要按业务边界（功能模块），不是机械地"每 500 行切一刀"。
   - **漏修引用**：只搜 `.md` 漏了代码里的路径引用，或拆完锚点失效，导致跨文档链接断裂。
   - **不问就大拆**：拆分预算超主任务 1.5 倍却闷头拆，把小任务拖垮——必须停下来让用户三选一。
   - **去拆豁免对象**：动了归档目录文档，或扫描了 `CLAUDE.md` / `AGENTS.md` / `SKILL.md`，这些都不受管控。

> 项目特定值（阈值表覆盖的具体路径模式、文档长度检查脚本、文档层级门禁脚本路径）不在本 skill 硬编码，由你自己项目的项目级补丁声明。
