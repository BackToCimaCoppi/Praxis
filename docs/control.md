# control

> 照着总控文档，一次只推进一个子任务，做完即停，绝不越界。

## 这是什么

control 是任务总控文档的「执行引擎」。它读取 `docs/00-任务总控/` 下某份活跃总控，按里面的子任务定义推进任务——但每次只动一个子任务，做完立刻停下回填状态，等你下一步指令。

它配套一组脚本（`render_control_status.py`、`next_subtask.py`、`split_subtask.py`、`archive_control.py` 等），负责解析总控、渲染状态表、推荐下一个可执行子任务、拆分父任务、归档。AI 不自己解析总控文档，全交给脚本。

边界说明：

- **管**：选定目标总控、按触发粒度读最小必要上下文、严格在单个子任务范围内执行、回填状态、归档、拆分。
- **不管**：怎么写一份总控文档——那是配套 skill `task-control-doc` 的活。control 只消费已经写好的总控。

一句话：task-control-doc 负责「画图纸」，control 负责「照图纸施工」，而且一次只施工图纸上的一个格子。

## 解决什么问题

不用它，按总控推进多会话任务时常踩这些坑：

1. **AI 顺手越界**：让它做 T3，它看 T4「很容易顺便做」就一起做了，结果改动超出预期、和你的节奏脱节、评审范围失控。
2. **读太多上下文**：每次推进都把整份总控、所有子任务、规范文档全读一遍，上下文爆炸又慢。
3. **状态靠人脑记**：做到哪了、哪个能做、哪个卡住了，没有统一视图；多 worktree 并行时尤其乱。
4. **状态表被 AI 自由排版**：每次查进度，AI 按自己心情重排表格、省略列、转成 bullet，前后对不上，无法稳定追踪。

## 为什么这么设计

核心机制是 **「严格单子任务边界 + 做完即停 + 脚本即真值」**：

- **执行边界是最高红线**：`/control <key> Tn` 就只做 Tn——不做 Tn-1、不做 Tn+1、不做同级兄弟、不「顺手」做相关任务。可以**读**其他子任务的产出物（依赖需要），但绝不**写**入其他子任务范围。Tn 的输出物全部产出 → 立刻停止、回填状态、向你报告，等下一步。
- **如果发现 Tn 范围定义有问题**（该扩大或缩小）→ 停止施工、向你报告，绝不自行扩张。
- **按触发粒度读最小上下文**：`/control list` 只读活跃索引 README；`/control <key>` 多读目标总控的背景和总表；`/control <key> Tn` 才读该子任务详情和它列出的强制阅读文件。命令越具体，读得越精准，绝不预读所有文件。
- **status 输出契约（硬规则）**：所有查进度的请求，最终呈现以脚本 stdout 为准，AI 必须**逐字复述**——禁止重排版、合并行、省略列、改列名、转 bullet。这消除了「AI 看到脚本输出后自由排版」的不确定性。脚本报错就把原文给你，不「修复式 freestyle」。

关键取舍：

- **为什么严格单子任务、做完即停**：这是为了让任务可控、可审、可暂停。每个子任务是 task-control-doc 切好的自包含工作包，单独完成就该停，由你来决定下一步——AI 没资格替你做任务调度。这也呼应它的最高红线「绝不扮演催活的角色」。
- **为什么开始前必须从磁盘重读**：子任务开始时状态先改 `进行中`，然后**重新从磁盘读取**子任务详情和强制阅读文件，不依赖聊天历史——保证哪怕是新会话接手也能拿到准确上下文。
- **为什么 AI 不自己解析总控**：脚本已处理解析、状态派生、下一步推荐、归档校验。AI 自己解析容易出错，统一交给脚本是单一真值源。

## 怎么用

### 1. 触发词

「继续总控」「执行 T3」「查看总控状态」「给我一个总控任务表」「现在做到哪了」，以及各种 `/control ...` 命令。

### 2. 流程（一步步走查）

control 按触发模式分流，每种模式读不同的最小上下文：

| 命令 | 作用 | 读什么 |
|------|------|--------|
| `/control init` | 新项目首次初始化骨架（幂等） | 不读，直接调 `bootstrap_project.py` |
| `/control list` | 列出所有活跃总控 | 只读活跃索引 README |
| `/control status` | 查看当前总控状态表 | 调 `render_control_status.py`，逐字复述 |
| `/control <key>` | 进入指定总控，列可执行子任务等你选 | 目标总控背景+总表 |
| `/control <key> Tn` | 执行指定子任务（严格边界，支持 `Tn.x`） | 该子任务详情+它的强制阅读 |
| `/control <key> split Tn` | 把父任务拆成 Tn.1~Tn.N（先和你对齐边界） | Tn 父任务详情 |
| `/control blocked` | 列出所有阻塞子任务 | 调 `list_blocked.py` |
| `/control switch` | 交互式选一个总控写入激活指针 | 只读 `--list` 输出 |
| `/control use <key>` | 直接按关键词设激活总控 | `set_active.py` |

执行一个子任务（最常见路径）的完整走查：

1. **进入**：解析触发模式 → 确定最小上下文 → 用脚本拿索引。多候选时停下让你选。
2. **选子任务**：你没指定 Tn 时，优先恢复 `进行中` 的，再选第一个依赖已满足的 `待完成`。不跳过未解决的依赖，全阻塞就报告并停。
3. **执行（严格边界）**：子任务状态改 `进行中` → 从磁盘重读详情和强制阅读 → 改动严格限于「要做的事情」、遵守「不做什么」→ 完成「输出物」、过「完成判定」。
4. **完成即停**：立刻停止，不做下一个。
5. **回填**：总表状态→`已完成`；子任务详情的当前状态、输出物、残余风险回填；进展记录追加一行 `YYYY-MM-DD：[Tn] 完成，[摘要]`。阻塞则设 `阻塞`，写明阻塞什么、为何、最佳下一步。
6. **报告**：告诉你目标总控+子任务编号、改了什么/没改什么（突出边界遵守）、残余风险、建议下一步——但不主动接着做。

整体任务（不是单个子任务）全部完成后，经你确认才调 `archive_control.py <key> --version V1 --apply` 归档；归档前校验所有子任务必须 `已完成` 或 `已取消`。

### 3. 最小示例

输入：

> /control 支付重构 T2

产出（行为）：

1. 读目标总控背景+总表，再读 T2 子任务详情及其强制阅读文件（不读 T1、T3 详情）。
2. T2 状态改 `进行中`，严格在 T2「要做的事情」范围内施工（可读 T1 产出物作为依赖输入，但不碰 T1/T3 的代码范围）。
3. 产出 T2 输出物、过完成判定。
4. 立刻停止，回填总表 T2→`已完成`、进展记录加一行，向你报告「改了什么 / 没改什么」，并提示「下一步可执行：T3（依赖已满足）」。

查状态示例：

> /control 支付重构 status

→ 调 `render_control_status.py 支付重构`，把脚本输出的状态表**逐字复述**给你，最多在表后追加一条固定模板的「下一步建议」。

### 4. 常见坑

- **以为「顺手做」是帮忙**：恰恰相反。让做 T3 就只做 T3，多做一行都是越界。发现范围该改时报告，别自己扩。
- **跨子任务写入**：可以读其他子任务的产出物，但绝不能写入其他子任务范围，哪怕「很容易顺便做」。
- **过程资产乱放**：执行中产生的中间文档只能进 `_shared/`，且带 `T{n}-` 前缀（任务级共享无前缀）。不可用别的子任务前缀、不可平铺到任务根目录、不可新建 `_T{n}/` 目录。
- **手改状态表呈现**：status 类查询必须逐字复述脚本输出，不准重排版、省列、转 bullet。脚本报错就把原文给用户，别自行「修复」。
- **依赖未满足就硬上**：不跳过未解决的依赖；全阻塞就报告原因并停。
- **拆分粒度 AI 自己定**：`split Tn` 必须先和你对齐拆几个、各做什么、依赖顺序，复述一遍确认后才调脚本（默认 dry-run，`--apply` 才写盘）；只允许两级，`Tn.x` 不可再拆；拆完不顺手执行任何子任务。
- **跳过 bootstrap**：新项目没建过骨架就直接用，会找不到 `docs/00-任务总控/`。先跑 `/control init`。
