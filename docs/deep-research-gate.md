# deep-research-gate

> 把「扇出」分成该放行的和该焊死的两类：有界并行直接跑，深度研究和递归工作流必须开闸才准动。

## 这是什么

一道决策门。每当你（或你的 AI）准备"并行派一批子 agent"或"开一次深度研究"时，先过这道门：它用三个判据把这次扇出判成绿灯或红灯，绿灯直接放行，红灯走"开闸 → 跑 → 关闸"的受控流程。

它同时给出引擎级的硬防护配置——两个 settings 开关，把动态工作流引擎默认焊死，让任何子 agent 都绕不过去。

边界划分：

- **管**：扇出前的分类判定、工作流引擎的开关纪律、开闸后的关闸责任、派研究类子 agent 时的类型约束。
- **不管**：具体某个调查该怎么做、检索结果怎么整合、子 agent 的 prompt 怎么写。

## 解决什么问题

AI 编码工具普遍支持"派子 agent"和"深度研究"，但这两件事的成本差着数量级，而界面上它们长得一样。不加区分会同时踩两个反方向的坑：

- **静默烧穿配额**：派出去的子 agent 若默认拿到全权限，它可以为了核实一个小数据点，自行触发一次深度研究——在内部再展开一整层子 agent。主线程以为自己只派了几个助手，实际每个助手都能再开一层。如果权限模式又配置成跳过确认弹窗，这一切没有任何提示，等发现时配额已经见底、账号锁死，之后所有本可以正常进行的工作一起被打断。
- **因噎废食**：出过一次上面的事故后，最常见的过度矫正是"以后少派 agent"，于是本来可以一次并行几十路的批量模拟、只读核验，被硬拆成串行慢慢跑。**这同样是错的**，而且因为它不会报错，几乎没人纠正。

真正的分界线不是"子 agent 多不多"，而是"这次扇出会不会失控放大"。没有这条线，团队只能在"随时可能被烧穿"和"什么都不敢并行"之间二选一。

## 为什么这么设计

- **按「能否算出上界」分类，而不是按数量**：判据三问全都指向同一件事——这次扇出的成本事前算不算得出来。已枚举的 N 个子任务是 O(N) 封顶；开放式调查则由子 agent 自己决定查多深，事前无解。**宽度不危险，深度递归才危险。**
- **深度焊死在 1 层，是宽度安全的前提**：只允许主线程这一层扇出，所有子 agent 都是叶子。有了这条，宽度再大也只是线性成本——所以绿灯才敢说"放心并行"。
- **用引擎开关而不是确认弹窗**：弹窗会被"跳过确认"类权限模式吞掉，而且子 agent 触发时根本没人在看。`disableWorkflows` 是引擎级开关，触发时当场被拒、零 token 消耗，子 agent 绕不过。
- **只焊工作流引擎，不碰普通并行**：这是本 skill 最关键的取舍。开关管的是动态工作流引擎（深度研究和大规模递归 fan-out 的总闸），而普通的 Agent 并行调用根本不经过它。写清楚这个作用域，是为了防止有人拿"开关开着"当借口拒绝一切并行。
- **给研究类子 agent 指定只读类型**：这是比开关更根本的一道闸。只读搜索 agent 手里没有派 agent、调 skill、跑 workflow 的工具，**物理上扇不出去**——不依赖任何人的自觉。
- **承认残余风险而不假装解决**：整个开闸机制押在"人记得关闸"上。文档把这一点明写成结构性漏洞，而不是藏起来，因为忘记关闸会精确复刻原始灾难（gate 开着过夜 + 无人值守时触发）。推荐补一个会话启动自检钩子（`SessionStart`：发现 `disableWorkflows` 不是 `true` 就焊回并告警）堵住跨会话这条路——但它只在**下一个会话启动**时补救，当前会话内忘关仍无人拦，所以「同一会话内开闸→关闸闭环、关闸先于报告结果」这条纪律不变。

## 怎么用

**触发词**：深度研究、deep research、开工作流、跑工作流、大规模检索、fan-out、并行派一批 agent、要不要并行、深挖某个课题。

**第一步永远是分类**：

| | 🟢 绿灯·有界并行 | 🔴 红灯·无界/递归/工作流 |
|---|---|---|
| 数量 | 已枚举、算得出上界 | 子 agent 自己决定要不要再扩 |
| 任务性质 | 执行已交代清楚的事 | 开放式调查，查多深由它定 |
| 递归 | 不递归，子 agent 是叶子 | 内部还会再派 / 触发深度研究 |
| 怎么办 | **直接并行，串行才是错** | 开闸流程 + 经用户同意 |

判据三问任一为"是"→ 红灯：数量算不出上界？会递归？是开放式调查？

**绿灯**：直接并行，不必问、不必缩。派研究/检索类子 agent 时**显式指定只读搜索类型**。

**红灯**：走四步——

1. 先确认值不值（普通几轮检索够不够？够就别开）
2. 开闸：`disableWorkflows` 改 `false`
3. 跑，全程盯着
4. **关闸**：跑完立刻改回 `true`

**常见坑**：

- **关闸忘在报告之后**：正确顺序是"关闸 → 再报告结果"。反过来的话，会话一中断 gate 就留在开着的状态过夜。
- **把开关当成禁止并行的理由**：开关焊的是工作流引擎，不是 Agent 并行调用。绿灯任务受这个开关零影响。
- **派研究 agent 不指定类型**：默认的通用 agent 拥有完整工具集，这是失控的起点。
- **从事故里学错教训**：炸配额的是"子 agent 能递归 + 工作流引擎放大"，不是"主线程派了一批子 agent"。别把有界并行一起连坐。
