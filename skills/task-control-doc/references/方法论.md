# 任务总控文档方法论

> 本文从 `task-control-doc/SKILL.md` 抽离的方法论部分。
> SKILL.md 只保留可操作步骤；为什么要这么做、何时该用、常见风险等论述放在这里。
> 当对总控的"形式 vs 实质"产生疑问时，回到本文阅读。

---

## 1. 为什么要做任务总控文档

任务总控文档的作用不是"写一份计划书"，而是建立一个**跨会话、跨 agent 的任务控制平面**。

它解决四个问题：

1. 长会话上下文越来越贵
2. 前半段收集到的关键信息，后半段可能被遗忘
3. agent 崩溃或会话中断后，难以低成本恢复
4. 一个大任务拆给多个新会话时，容易缺背景、漏约束、重复劳动

---

## 2. 核心原则

### 2.1 总控文档是任务真相入口

对于某个大型任务，任务总控文档应成为该任务的**唯一调度入口**。

关键背景、强制阅读、子任务目标、交付物、状态，不应该只存在于聊天记录里。

### 2.2 子任务即工作包（核心原则）

每个子任务都应该是一个**自包含工作包**：

- 新会话读「子任务详情 + 强制阅读文件」即可开工——这是**准入下限，不是视野上限**
- **鼓励**执行会话主动补读：「背景导航」、父级总控、其他子任务详情、相关正式文档、代码现状——把背景挖够再动手
- **视野放开、扇出焊死**：自主补读 = 亲自读（直接读文件 / 检索），不为补背景派子 agent / 起深度调查
- 执行与写入范围仍严格限于本子任务
- 用户自己在新会话开头选模型（不预定义"执行模式"）
- 子任务详情末尾有「会话启动提示词」可直接复制

这是为什么子任务详情结构会包含：强制阅读（核心必读）/ 背景导航（可选）/ 输入 / 要做的事情 / **不做什么** / 输出物 / 完成判定 / 会话启动提示词 这一整套。

如果一个子任务离开当前上下文就无法执行，说明它拆分得还不够好，或者"强制阅读清单"写得不够完整。

> **历史注（2026-07 修订）**：旧版要求"只读工作包、不读其他子任务详情"，为弱执行模型（上下文易污染、不会自主取舍）设计。强模型时代（Fable 5 / GPT-5.6 级）实践证明：喂太少导致执行者背景不足做出错误判断的代价，远大于多读几个文件。故改为"钉死靶子（做什么、写哪、何时停），放开视野（读什么），焊死扇出（不派 agent 补背景）"。

### 2.3 总控文档只保留高价值上下文

总控文档不是聊天日志转录。

不要把所有思考过程都塞进去，只保留会影响后续执行的高价值内容：

- 任务背景
- 核心约束
- 关键结论
- 强制阅读文件
- 子任务定义
- 当前状态
- 风险与待确认

### 2.4 子任务拆分要既能执行，又不过度碎片化

拆太粗：

- 新会话上下文压力还是很大
- 容易再次遗忘

拆太细：

- 管理成本过高
- 文档更新负担过重

目标：每个子任务都足够明确、边界清晰、输出具体，且可由一个新会话独立推进。

### 2.5 总控文档必须持续更新

如果总控文档不更新，它会很快失真。

因此总控文档必须包含子任务状态、已产出结果、新结论、阻塞原因、下一步建议。

### 2.6 推荐执行入口

已有总控的后续推进应优先通过 `/control` 进入，而不是绕开总控直接执行。

多个活跃总控并行时，git worktree 由 `git worktree list` 自治管理，命名约定仅供人眼识别（详见总控规范 §3）。worktree 不绑定任务，多激活时通过 `.claude/local/active-control` 文件显式选择。

### 2.7 严格不越界（执行边界）

`/control <key> Tn` → **只动 Tn**，不顺手做 Tn-1 或 Tn+1。

哪怕 Tn-1 看起来"很容易顺便做"也不要做。原因：

- 用户在指定 Tn 时已经做了规划决策，越界会破坏这个决策
- 越界的代码改动很难审查（用户预期里只有 Tn 的 diff）
- 子任务的依赖关系是显式表达的；越界等于隐式跳过了依赖检查

如果发现 Tn 范围定义有问题（应扩大或缩小），**停止施工，向用户报告**，让用户决定是否调整总控。

## 3. 子任务拆分规则

### 3.1 一个子任务只解决一个明确问题

不要在一个子任务里同时混入：

- 需求分析
- 代码修改
- 测试补充
- 文档迁移

如果它们彼此独立，就应拆开。

### 3.2 一个子任务要有清晰输出

每个子任务都必须有可检查输出，例如：

- 新增某份文档
- 修改某个模块说明
- 产出一份测试用例
- 完成一段目录重构

如果说不清输出，那说明任务还不够清晰。

### 3.3 一个子任务的强制阅读应小而准，背景导航宁多勿缺

强制阅读（核心必读）越精准，执行者越快锁定必须消化的东西——超过 3 个通常说明背景没消化成任务。但**背景导航是另一回事**：一行「路径 + 读它获得什么」几乎零成本，宁多勿缺，读不读由执行会话自行判断。要明确告诉新会话：哪些必须先读（准入），哪些是可选背景（导航），并要求它把背景挖够再动手。

### 3.4 并行子任务必须避免写冲突

如果多个子任务可能并行执行，应尽量做到：

- 写不同文件
- 或者写同一文件的不同区域且边界明确

如果写冲突很大，不要并行拆分。

## 3.5 单文件 vs 拆分模式怎么选

| 维度 | 单文件模式 | 拆分模式 |
|------|----------|---------|
| 子任务数量 | 3-7 个 | 8 个以上 |
| 单子任务详情长度 | < 50 行 | > 100 行（带大量强制阅读、设计明细、检查项） |
| 子任务之间共享上下文程度 | 高（背景紧密相关） | 低（每个子任务相对独立） |
| 维护成本 | 一份文件好维护 | 多文件需要同步状态到 README.md |
| 执行时上下文 | 整文件已经不算大 | 从对应 Tn-...md 起步，按需补读，最省 |

**默认用单文件**。除非你确定子任务详情会很长、很多，否则不要拆——拆分有维护成本。

> 决策口诀：**子任务总表 + 子任务详情写完后，整个 README.md 超过 400 行了 → 考虑拆分**。

## 4. 这个思路的常见风险

### 4.1 总控文档过时

如果不回填状态和输出物，总控文档会迅速失真。

### 4.2 子任务拆得太粗

如果一个子任务仍然需要大量历史上下文，它就没有真正解决上下文污染问题。

### 4.3 子任务拆得太碎

如果一个大任务被拆成过多极小子任务，会导致维护总控文档本身的成本变高。

总控文档的目标不是"拆得越细越好"，而是"拆到足以让新会话独立推进"为止。

---

## 5. 什么时候必须做总控文档

当出现以下任一情况时，应该优先考虑先做任务总控文档：

- 任务预计跨多个回合
- 任务预计涉及多个模块
- 任务预计会读很多文件
- 任务预计会拆给多个新会话
- 任务需要严格的状态跟踪和交接

中小任务用计划模式或 `lightweight-design` 即可，不需要总控。

---

## 6. 推荐写法

总控文档应优先使用：

- 目标导向表述
- 结果导向表述
- 明确输入输出
- 明确强制阅读
- 明确状态

避免：

- 大段随想
- 宽泛口号
- 缺少输出定义的子任务
- 把背景全放在聊天里、不写进文档

### 6.1 总目标的好坏写法

好写法（**结果表达**）：

- 建立可持续维护的需求文档体系
- 让新会话能独立接手并推进子任务

差写法（动作表达）：

- 先看代码再写文档
- 先建目录再改 README

### 6.2 输出物的好坏写法

好写法（**明确可交付**）：

- 补齐 `docs/01-需求/{某具体文件}.md`
- 完成某模块 README 的导航结构
- 产出某模块的需求说明初稿

差写法（抽象）：

- 把需求整理好
- 大概搞清楚业务

### 6.3 强制阅读的写法

不要简单列文件名，应说明为什么必须读、读完要获得什么结论：

- `docs/{相关文档}.md`：必须读，用于理解当前模块划分
- `.claude/skills/{相关 skill}/SKILL.md`：必须读，用于确认放置规则与写法
