# 标准研发流程（可选预设）

> 本文件是 `task-control-doc` skill 的**通用流程预设真值源**。描述大多数研发型总控共有的「八阶段动作菜单」以及如何把它实例化成一棵子任务树。
> **本文件项目无关**：只写抽象阶段与抽象槽位，**绝不出现任何具体项目的 skill 名 / 路径 / 域名**。项目特定绑定由「项目研发流程补丁」提供（见 §6 发现协议）。

---

## 1. 这是什么 / 何时用

绝大多数研发型任务（新功能、跨模块重构、带前后端+测试+部署的链路）都走同一条流水线：先调查、再探讨、再设计、再评审、再测试设计、再回写文档、再施工、再交付。把这条流水线固化成预设，用户只需给一句总需求，AI 就能实例化出合理的子任务树，省去每次从零编排。

**定位：正交预设，不是第三种载体。** 研发流程决定「有哪些阶段 / 哪些子任务 / 怎么连依赖」；它**叠加**在单文件或拆分**载体**之上（载体仍按子任务数/详情长度自动选，见 §8）。所以不存在"单文件 vs 拆分 vs 研发流程"三选一——只有「是否套用研发流程预设」× 「单文件 or 拆分载体」两个正交维度。

**何时用**：任务达到总控级（多会话、跨模块、上下文易失忆）且形态属研发流水线。纯文档整理、一次性脚本、局部小改不必套，用计划模式或 `lightweight-design` + `construction-blueprint` 即可。

---

## 2. 第 0 步：明确任务（不占编号）

研发流程的第 0 步是「明确任务」——它**不是子任务、不占 T 编号**。它发生在创建总控的同时：用户给出总目标 / 总内容，AI 确认整体需求后，把它写进总控 `README.md` 头部的「任务背景 / 总目标 / 完成定义 / 范围 / 非范围」。后续八阶段子任务都从这份头部派生。

---

## 3. 八阶段动作菜单（抽象词版）

> 这是**菜单**，不是固定子任务数。每个阶段可实例化成 0 / 1 / N 个子任务（见 §4）。

| 阶段 | 目的 | 典型产出 | 是否需评审 |
|---|---|---|---|
| ① 调查 | 锚定代码真值与需求真值，找出文档与代码/需求的割裂点 | 调查报告（含割裂点清单） | 否 |
| ② 开放探讨 | 多轮敲定产品形态（业务流程）与核心技术（选型/接口/数据/脚手架/复用） | 探讨纪要（可拆产品线/技术线两条） | 否 |
| ③ 轻量设计 | 把探讨结论沉成任务级设计（决策海拔锁死改什么/怎么改） | 轻量设计方案 | 风险触发 |
| ④ 施工蓝图 | 把设计落成代码镜像（逐文件变更清单、施工切片、验收映射） | 施工蓝图 | 风险触发 |
| ⑤ 测试用例设计 | 设计可自动化执行的测试用例（接口/端到端/视觉验收等） | 测试用例 | 风险触发 |
| ⑥ 文档回写 | 把本任务改动的设计 + 连带历史割裂回写正式文档体系（见 §5 两段化） | 正式文档变更 | 否 |
| ⑦ 施工 | 正式改代码（各子系统）+ 测试执行脚本 | 代码 + 测试脚本 | 否 |
| ⑧ 交付 / 发布验证 | 交付物上线/打包/发布并跑自动化测试（具体形态由项目补丁绑定） | 交付记录 + 测试结果 | 否 |

> 末阶段抽象名为「交付 / 发布验证」——不同项目可能是部署、上架、打包、验收，甚至无需此阶段。具体动作由项目补丁绑定。

## 4. 菜单 → 子任务树实例化规则

### 4.1 可伸缩

- **一阶段拆多子任务**：复杂任务里，某阶段可拆成多个并列一级子任务（如调查拆「行业/前沿调查」+「代码与文档调查」；探讨拆「产品需求探讨」+「核心技术探讨」；施工按域/子系统拆多个）。
- **塌缩 / 合并 / 跳过**：简单任务里，相邻阶段可合并（设计+蓝图合一），或整阶段跳过（纯前端改可跳调查的部分动作、跳后端部署）。

### 4.2 拆分决策表（AI 实例化时逐阶段判定）

按五维给每个阶段定"保留独立子任务 / 合并入相邻 / 跳过 / 是否需独立评审"：

| 维度 | 含义 | 偏向「拆细 / 保留 / 独立评审」 | 偏向「合并 / 跳过」 |
|---|---|---|---|
| 复杂度 | 工作量、子系统数 | 大 | 小 |
| 影响层 | 触及的文档/技术层数（需求→测试） | 多层 | 单层 |
| 风险 | 是否命中项目的「死亡线区域」（补丁声明） | 命中 | 不命中 |
| 跨域数 | 触及的业务域数量 | ≥2 域 | 单域 |
| 验证成本 | 需要的测试种类与验收难度 | 高 | 低 |

口诀：**五维多数偏「重」→ 该阶段独立成子任务、必要时独立评审；多数偏「轻」→ 合并入相邻阶段或跳过。**

### 4.3 评审风险触发规则

评审（对抗评审等）**默认塌缩**进对应的设计/蓝图/测试子任务末步（产出→评审→升级用户决策→回补，一个会话走完）。**仅当命中下列任一**，才把评审拆成独立子任务：

- 命中项目「死亡线区域」（补丁声明的高风险区）
- 跨域（≥2 业务域）
- 破坏既有接口契约 / 数据契约

独立评审子任务的「要做的事情」固定四步：① 跑评审 → ② 列出 AI 拿不准的「用户决策点」→ ③ 用户裁决 → ④ 回补被评审产物。报告落 `_shared/T{n}-对抗评审报告.md`（蓝图评审用 `_shared/T{n}-蓝图评审报告.md`）。

### 4.4 线性一级编号

创建期**只写一级 T1 / T2 / T3…**，不预写二级。每个被选中的阶段（或阶段内拆出的多个子任务）顺序占一个一级编号。二级 `Tn.x` 只留给执行中途发现某子任务太大时用 `/control <key> split Tn` 拆。

## 5. 依赖连成 DAG（不机械串链）

**依赖按实际产物连，不按阶段先后机械串。** 每个子任务的「依赖」列指向它**真正需要的前置产物**所在的子任务编号。无依赖关系的子任务天然并行（适合各开 worktree）。

典型满量连法（**满量参考，非默认预填**；实际按 §4 决策表裁剪）：

| 编号 | 阶段 | 依赖 | 说明 |
|---|---|---|---|
| T1 | 调查 | 无 | |
| T2 / T3 | 开放探讨（产品线 / 技术线） | T1 | 两线可并行 |
| T4 | 轻量设计 | T3 | 评审默认塌缩入此 |
| T5 | 施工蓝图 | T4 | 评审默认塌缩入此 |
| (T_r) | 风险触发的独立评审 | 对应产出 | 仅死亡线/跨域/契约破坏时出现 |
| T6 | 测试用例设计 | T5 | |
| T7 | 文档闸门（施工前） | T5 | 见 §5.1 |
| T8 | 施工（可按子系统/域拆多个并行） | T7, T6 | |
| T9 | 文档收尾（施工后） | T8 | 可与验证并行 |
| T10 | 交付 / 发布验证 | T8 | |

**并行点**：T2/T3；按域拆的施工子任务；T9 与 T10 的部分验证。

### 5.1 文档回写两段化（防漂移）

文档回写拆成两段，避免"代码跑在未冻结文档前面"的漂移：

- **文档闸门（施工前）**：把关键的接口契约 / 数据结构 / 架构骨架类文档**先冻结**，作为施工的**前置依赖**。施工据已冻结的真值进行。
- **文档收尾（施工后）**：实现细节回填、面向实现的层、长文档治理等，**可与部分验证并行**。

> 原则：文档是真值、代码据文档施工。契约类文档必须先于施工冻结；只有实现态细节允许施工后回填。

## 6. 阶段 → 槽位映射 + 项目补丁发现协议

八阶段是抽象的；每个阶段「该读什么 skill / 产出落哪 / 用什么验证」是**项目特定**的，由**项目研发流程补丁**填充。本文件只声明抽象槽位，**不写任何项目名**。

抽象槽位（项目补丁负责一一填实）：

| 槽位 | 含义 |
|---|---|
| `{{调查锚点}}` | 调查阶段强制阅读的项目文档体系 / 真值锚定 skill |
| `{{探讨依据}}` | 探讨阶段强制阅读的需求/契约层文档 |
| `{{轻量设计 skill}}` | 轻量设计方法 skill |
| `{{施工蓝图 skill}}` | 施工蓝图方法 skill |
| `{{测试设计 skill}}` | 测试用例规格真值 skill |
| `{{评审 skill}}` | 对抗评审 skill |
| `{{文档回写 skill}}` | 回写正式文档体系的 skill + 长文档治理 |
| `{{施工依据}}` | 施工阶段强制阅读的架构/蓝图 |
| `{{交付 skill}}` | 交付/发布/部署 + 测试执行 skill |
| `{{死亡线区域}}` | 项目高风险区清单（触发独立评审/升级） |

### 6.1 项目补丁发现协议（实例化前 fail-stop）

实例化研发流程前，AI **必须**先定位并加载「当前项目的研发流程补丁」：

1. 在项目根 `.claude/skills/`（及对应运行面 skills 目录）下，查找声明自己是「`task-control-doc` 研发流程补丁」的 skill（其 description / 开头声明含此语义，并提供上表槽位的填充）。
2. **找到** → 加载它，按其槽位对照表把模板里的 `{{槽位}}` 替换成项目真实绑定。
3. **找不到** → **停机询问用户**：当前项目没有研发流程补丁，是否（a）先创建补丁、（b）改用通用拆分模式手工编排。**禁止**用带 `{{槽位}}` 的纯抽象模板直接落盘。

---

## 7. 高频产出物标准命名

**复用 `~/.claude/skills/control/references/总控规范.md` §1.1.1，不另立。** 标准名仅四项：

- `T{n}-轻量设计方案.md`
- `T{n}-施工蓝图.md`
- `T{n}-蓝图评审报告.md`
- `T{n}-对抗评审报告.md`

其余产出（如测试用例、调查报告、探讨纪要）不是 §1.1.1 标准名，作为普通子任务专属资产命名即可（带 `T{n}-` 前缀放 `_shared/`，如 `_shared/T{n}-测试用例.md` / `_shared/T{n}-调查报告.md`）。**不得**为它们私自新立"标准名"而绕过 §1.1.1。

---

## 8. 与单文件 / 拆分载体的关系

研发流程是正交预设；落盘载体仍按现有规则自动选：

- 实例化后**子任务数 ≤ 7 且各详情 < 50 行** → **单文件载体**（全部写进一个 `README.md`）。
- 否则 → **拆分载体**（每子任务一个 `T{n}-*.md`）。
- 边界模糊时问用户。

> 研发流程任务通常阶段多、每包长，**多数落拆分载体**；但小型研发任务（如单域小功能）实例化后可能只有 4-5 个精简子任务，落单文件载体即可——不要因为"套了研发流程"就强制拆分。
