# 标准研发流程（可选预设）

> 本文件是 `task-control-doc` skill 的**通用流程预设真值源**。描述大多数研发型总控共有的「八阶段动作菜单」以及如何把它实例化成一棵子任务树。
> **本文件项目无关**：只写抽象阶段与抽象槽位，**绝不出现任何具体项目的 skill 名 / 路径 / 域名**。项目特定绑定由「项目研发流程补丁」提供（见 §6 发现协议）。

---

## 1. 这是什么 / 何时用

绝大多数研发型任务（新功能、跨模块重构、带前后端+测试+部署的链路）都走同一条流水线：先调查、再探讨、再设计、再设计用例、再冻结规格、再写执行契约、再一口气跑完。把这条流水线固化成预设，任务发起人给出总需求后，AI 就能实例化出合理的子任务树，省去每次从零编排。

### 1.1 两种模式：默认标准模式

| 模式 | 何时 | 流程 |
|---|---|---|
| **标准模式（默认）** | **用户不声明就是它**（只要任务形态属研发流水线） | 本文件的八阶段流水线 |
| 自定义模式 | **用户显式声明**"不套标准流程 / 我自己指定阶段" | 流程按用户指定，本 skill **不强加任何阶段** |

**定位：正交预设，不是第三种载体。** 研发流程决定「有哪些阶段 / 哪些子任务 / 怎么连依赖」；它**叠加**在单文件或拆分**载体**之上（载体仍按子任务数/详情长度自动选，见 §8）。所以不存在"单文件 vs 拆分 vs 研发流程"三选一——只有「模式」×「载体」两个正交维度。**改流程预设时不得破坏这个正交性。**

**何时用**：任务达到总控级（多会话、跨模块、上下文易失忆）且形态属研发流水线。纯文档整理、一次性脚本、局部小改不必套，用计划模式或 `lightweight-design` 即可。

### 1.2 这条流水线在解决什么（改流程前先读）

它是**从「过程管控」切换到「结果管控」**的落地：

| | 过程管控（旧流程的实践形态） | 结果管控（本流程） |
|---|---|---|
| 授权角色在哪 | 几乎每道工序都临时找人审批 | **轻量设计集中裁决重大取舍 + 章程批准 + 候选终审 + 项目治理例外**；不同角色可按职责分离承担，可判定的文档细节不逐条询问 |
| 靠什么保证质量 | 人逐步审查 | **可判定的验证器** + 边界 + 事后逐条追认 |
| 出问题 | 停下来问 | 自愈 + 记飞行日志；只有白名单情况才停 |

> **实测**：过程管控形态下，做完的成果——代码写完、测试过了、文档冻结了——可能长期停在脏工作区、**分支零提交**，卡点**没有一个是工程问题**，全是流程规则。换成本流程后，同类任务能在一次会话内完成提交、部署、测试全绿，**只在真实规格缺陷上停机一次**（停得对），并顺带挖出真 bug。
> 可逆工程问题应在预授权边界内自愈，避免无依据的临时审批；项目声明的业务授权、环境占用、职责分离和强制检查点不得因此省略。

## 2. 第 0 步：明确任务（不占编号）

研发流程的第 0 步是「明确任务」——它**不是子任务、不占 T 编号**。它发生在创建总控的同时：用户给出总目标 / 总内容，AI 确认整体需求后，把它写进总控 `README.md` 头部的「任务背景 / 总目标 / 完成定义 / 范围 / 非范围」。后续八阶段子任务都从这份头部派生。

---

## 3. 八阶段动作菜单（抽象词版）

> 这是**菜单**，不是固定子任务数。每个阶段可实例化成 0 / 1 / N 个子任务（见 §4）。

| 阶段 | 目的 | 典型产出 | 是否需评审 |
|---|---|---|---|
| ① 调查 | 建立文档、代码、数据库与运行证据基线，找出正式规格的缺口、冲突和疑似腐败点 | 调查报告（含证据索引、割裂点清单与初始影响面种子） | 否 |
| ② 开放探讨 | 多轮敲定产品形态（业务流程）与核心技术（选型/接口/数据/脚手架/复用） | 探讨纪要（可拆产品线/技术线两条） | 否 |
| ③ 轻量设计 | 把探讨结论沉成任务最终真值切片：锁死决策、建立 `DEC-x` 授权裁决来源、完成影响面勘察、建立完整 `SD-x` 设计语义索引与验收映射 | 轻量设计方案 + `_shared/用户裁决记录.md`（兼容文件名，如有）+ `design_index_hash` | 风险触发：同对象只开放一次，整改后封闭验收 |
| ④ 测试用例设计 | 先定测试矩阵，再把每条可观察规则写成正式 L7 用例；每条断言有稳定 `AC-x`、`SD-x`、正式规格来源与必要的 `DEC-x` | 正式 L7 用例规格 + `_shared` 冻结指针/摘要 | 风险触发：同对象只开放一次，整改后封闭验收 |
| ⑤ 真值收敛与规格冻结 | 按最终真值切片检查并修订涉及的全部 L1–L7，完成零遗漏物化、业务主题唯一性、语义差异与跨层可满足性检查；任务切片内已知腐败必须清零 | 正式文档变更 + 规格物化覆盖报告（五项冻结闸门全绿 + 评审闭环 PASS 证据） | 否 |
| ⑥ goal 章程 | 继承上游授权，把施工压成执行契约；同时声明治理角色与环境占用策略，用启动服务单分类并提前清算可预见人工协作，但不为环境、命令或测试资产签发准入 | goal 章程 + goal 启动服务单 | 风险触发或项目治理要求 |
| ⑦ goal 执行 | M0 先准备并修复环境、测试资产/runner、夹具、数据与证据工具，再自主完成产品施工、提交、交付/发布、执行冻结测试矩阵并封存证据 | goal 启动检查 + 精确 commit/tree 候选 + 代码/测试资产 + 执行证据清单 + 飞行日志，状态 `CANDIDATE_READY` | 否（内部为 AI 自审 + 检查器） |
| ⑧ 候选终审 | 由全新上下文只读对照冻结正式真值、原子 AC 与强制测试形状，检查精确候选实现、真实断言和执行证据；可逆缺陷退回同一 goal，自上游语义变化起才回退上游 | 候选终审报告 + 退回指针或最终验收封印 | 必须 |

> **⑦ 合并启动准备、产品施工与交付 / 发布验证**：M0 的健康探针只证明执行面可启动，不为每条 AC 提前签发 Ready；测试基础设施和产品代码都在同一 goal loop 内按冻结规格修复。⑧只审核已冻结的精确候选，**不是**恢复「交付发布」或「文档收尾」分段。

> **⑥ 启动服务不恢复旧「执行准备」**：它只把事项分为 `AI_AUTO / PRE_GOAL / CANDIDATE_DEPENDENT / LONG_LATENCY_EXTERNAL`，提前清算与候选无关的授权角色动作，并记录剩余人工窗口及责任角色。服务单无 PASS/FAIL、不冻结命令、不限制 M0 自愈；人工窗口不设通用固定次数。

**相对旧流程的四处变化**（改动理由见 §3.1）：

| 变化 | 说明 |
|---|---|
| **删除「施工蓝图」阶段** | 蓝图 = 勘察（有价值）+ 施工指令书（**全链条唯一无上游、只能靠猜的产物，必然腐烂**）。勘察与验收映射移进③；施工切片移进⑥章程的里程碑；diff 对账改由测试验证器 + 飞行日志承担 |
| **「文档回写」→「真值收敛与规格冻结」** | 七层全是规格层，一次冻完；本任务涉及的存量腐败与本次设计一起收敛，取消"施工前锁一半、施工后回血一半"的两段式 |
| **撤销独立「执行准备」** | 测试资产、runner、环境、数据与证据适配本来就是可逆工程问题；拆成 goal 门票会把不确定性前移并制造重复停机，现并入⑦的 M0 启动检查与后续自愈 |
| **准备、产品施工与交付验证保持同一 goal loop** | 同一自主执行体可修执行基础设施，也可修产品；唯一不变量是测试断言不得弱于冻结规格，修复后按影响面重跑 |

### 3.1 为什么删掉施工蓝图（别再加回来）

实测：一份长施工蓝图**在两处给出相反的施工指令**——前一节说"一步创建"，后一节说"分两步创建"。全链条多份文档里，唯一主张相反口径的就是蓝图的施工指令段；下游工作包照抄了它，施工时炸给用户，让用户去裁决一个**根本不存在的契约冲突**。

根因不是写得不认真：蓝图经过对抗评审 + 专项回灌，回灌把前一处改对了，**漏掉了后一处**。**内容越多、评审越多、回补越多 → 自相矛盾的面积越大。**

> **反诱惑**：不要"给死亡线区域保留蓝图"。反了——**死亡线任务的蓝图最长、评审最多、回补最多 → 漂移面最大**，炸掉的恰恰是最厚的那份。死亡线的正确锁是**冻结契约 + 金标准用例**，不是更厚的蓝图。

## 4. 菜单 → 子任务树实例化规则

### 4.1 可伸缩

- **一阶段拆多子任务**：复杂任务里，某阶段可拆成多个并列一级子任务（如调查拆「行业/前沿调查」+「代码与文档调查」；探讨拆「产品需求探讨」+「核心技术探讨」；施工按域/子系统拆多个）。
- **塌缩 / 合并 / 跳过**：简单任务里，相邻阶段可合并（如设计+用例合一、规格冻结并入设计），或整阶段跳过（纯前端改可跳调查的部分动作）。**⑥章程、⑦goal 执行、⑧候选终审不得互相合并**：章程定义自主边界，goal 生产候选，全新上下文终审独立验收。凡 goal 含产品施工、部署或任一测试面命中，M0 启动检查不得省略。

### 4.2 拆分决策表（AI 实例化时逐阶段判定）

按五维给每个阶段定"保留独立子任务 / 合并入相邻 / 跳过 / 是否需独立评审"：

| 维度 | 含义 | 偏向「拆细 / 保留 / 独立评审」 | 偏向「合并 / 跳过」 |
|---|---|---|---|
| 复杂度 | 工作量、子系统数 | 大 | 小 |
| 影响层 | 触及的文档/技术层数（需求→测试） | 多层 | 单层 |
| 风险 | 是否命中项目的「死亡线区域」（补丁声明） | 命中 | 不命中 |
| 跨域数 | 触及的业务域数量 | ≥2 域 | 单域 |
| 验证成本 | 需要的测试种类与验收难度 | 高 | 低 |

口诀：**五维多数偏「重」→ 该阶段独立成子任务、必要时独立评审；多数偏「轻」→ 合并入相邻阶段或跳过。**

### 4.3 评审风险触发规则

流程有三个**不同对象**可能接受开放式对抗评审——③轻量设计 / ④测试用例 / ⑥goal 章程，各有专属口径卡。**每个对象在同一真值基线下最多开放一次**；评审裁决后的整改统一转 `{{封闭验收 skill}}`，由当前工具一个原生子线程检查、主线程逐条裁决，禁止 R2/R3。它们默认塌缩进对应子任务末步；仅命中下列任一才把“评审 + 整改 + 封闭验收”拆成独立子任务：

- 命中项目「死亡线区域」（补丁声明的高风险区）
- 跨域（≥2 业务域）
- 破坏既有接口契约 / 数据契约

> **默认值是"塌缩"，不许无依据地单向调紧。** 常见漂移：skill 原文写的就是"默认塌缩"，而实践把三次评审做成了三个独立人工检查点——**规则没错，是实践单向漂移**。项目治理正式声明的职责分离与强制检查点不属于漂移；其余发现"skill 说 A、实践做成更严的 B"，以 skill 为准（`control` 规范 §7.2）。
> **风险触发 ≠ 每阶段必评**：未命中风险条件就不运行开放评审；命中后才走一次完整开放评审（双评审 + 当前主线程逐条裁决）以及整改后的封闭验收。

**goal 章程不再每次强制开放式红队**：只有命中上述风险条件或用户显式要求时才评；同一章程对象仍只运行一轮，整改后封闭核对原 A/B/C/D 采纳项，不重新找新攻击点。普通任务依靠冻结规格、M0 启动检查、执行期验证器与全新上下文终审闭环。

独立评审子任务固定五步：① 跑一次开放式评审 → ② 合并列出真实业务决策点 → ③ 业务决策负责人按项目治理裁决并逐项写入 `_shared/用户裁决记录.md#DEC-x`（含实际角色）→ ④ 回补被评审产物 → ⑤ 调 `{{封闭验收 skill}}`，子线程检查、主线程裁决，`PASS` 后关闭。报告落 `_shared/T{n}-对抗评审报告.md`，封闭验收追加在同一报告，不另建 R2/R3。

**评审产出的三桶归置**（口径卡强制，防棘轮）：

| 桶 | 判据 | 去向 | 见用户? |
|---|---|---|---|
| 桶1 设计缺陷 | 现在就能改、也必须现在改 | **一次改好，不留下游闸门**；大的（改变业务结果 / 不可逆架构归属）交业务决策负责人批准，小的由当前主线程按既有真值裁决并直接改 | 仅大的 |
| 桶2 执行期事项 | **此刻处理不了**，只能在 goal 内处理 | 汇总落 `_shared/自愈清单.md` → ⑥章程纳入授权边界，⑦在 M0 或对应施工切片自愈并记日志 | ❌ |
| 桶3 风险登记 | 已知但不行动 | 只记录 | ❌ |

> **桶2 不是"小问题"**——小问题属桶1，当场改掉。桶2 的判据是"**此刻处理不了**"，与问题大小无关。环境、账号、数据、runner、部署通路、测试资产和证据适配统一由 goal 自愈，不再为了提前消除不确定性创建新阶段。
> **反棘轮铁律**：评审产出**禁止**给下游新增闸门 / 审批 / 硬门。**评审结论是信息，不是门禁。**

### 4.4 线性一级编号

创建期**只写一级 T1 / T2 / T3…**，不预写二级。每个被选中的阶段（或阶段内拆出的多个子任务）顺序占一个一级编号。二级 `Tn.x` 只留给执行中途发现某子任务太大时用 `/control <key> split Tn` 拆。

## 5. 依赖连成 DAG（不机械串链）

**依赖按实际产物连，不按阶段先后机械串。** 每个子任务的「依赖」列指向它**真正需要的前置产物**所在的子任务编号。无依赖关系的子任务天然并行（适合各开 worktree）。

典型满量连法（**满量参考，非默认预填**；实际按 §4 决策表裁剪）：

| 编号 | 阶段 | 依赖 | 说明 |
|---|---|---|---|
| T1 | 调查 | 无 | |
| T2 / T3 | 开放探讨（产品线 / 技术线） | T1 | 两线可并行 |
| T4 | 轻量设计（含最终真值切片 + `SD-x` 索引 + 验收映射） | T3 | 评审默认塌缩入此 |
| T5 | 测试用例设计（正式 L7 + `AC-x` + 正式规格来源） | T4 | 评审默认塌缩入此；此时为待最终冻结版本 |
| (T_r) | 风险触发的独立评审 | 对应产出 | 仅死亡线/跨域/契约破坏时出现 |
| T6 | 真值收敛与规格冻结 | T4, T5 | **一次收敛、一次冻完**，见 §5.1；覆盖报告不全绿不得进入章程 |
| T7 | goal 章程 | T6 | 继承冻结真值与用户授权，M0 覆盖全部命中执行面；评审按风险触发 |
| T8 | goal 执行（M0启动检查+产品施工+提交+交付+正式测试+执行证据） | T7 | 自主构建/修复执行基础设施和产品，自主产出 `CANDIDATE_READY` |
| T9 | 候选终审 | T8, T6 | 全新上下文只读审查 T8 冻结的精确 commit/tree；通过后才完成总控 |

**并行点**：T2/T3；goal 的 M0 可按已枚举测试面做有界叶子并行，后续按章程已枚举切片做有界并行（叶子级，禁二级派生）。

> **注意 T5 → T6 这条边**：用例全文**先写入正式 L7**，但与其余规格在 T6 统一最终冻结。写用例天然会暴露设计空洞——"想写断言却发现设计没定义结果"。这个洞必须在 T6 物化前回填，否则冻结的是一份有洞的规格。

### 5.1 真值收敛与规格冻结：一次冻完，没有"施工后回血"

**七层文档全部是规格层，全部先于代码存在。** 判据（`doc-layer-system` §5.0）：

> **把代码全删了，能照文档重做出来吗？** 能 → 那它就是规格。

因此本阶段**一次性冻结全部规格**，作为 goal 执行的**前置依赖**与**法律**。不存在"施工前锁一半、施工后回血一半"：

| | 内容 | 何时 |
|---|---|---|
| **规格（七层）** | 需求 / 交互 / 契约 / 表结构 / 架构骨架与核心链路 / 用例规格 | **本阶段按任务最终真值切片逐层核验、一次冻完**，是 goal 的输入 |
| 代码自由范围 | 函数内部、样式写法、DTO 转换、SQL、标准 CRUD | **不进任何文档**——删了也能照规格重做 |
| 执行产物 | 测试资产/runner、启动检查、正式运行记录、交付记录、飞行日志均在 goal 产出 | **均不进七层** |

> **为什么取消两段化**：实现细节属于**文档未规定的施工自由范围**，但所有影响业务结果、契约、数据、架构边界和可观察行为的设计语义都必须在本阶段进入正式 L1–L7。若轻量设计或用例中存在规范性语义而覆盖报告无法定位其正式落点，说明规格尚未冻结，不能把缺口留给代码解释。

本阶段执行五遍：

1. **物化遍**：逐条读取轻量设计 `SD-x` 和正式 L7 的 `AC-x`，把每条规范性语义写入职责正确的正式层；同时核验每条的 `provenance_refs` 可追到上游正式真值或 `DEC-x`（裁决溯源在本遍产出）。禁止摘要式回写、禁止只写 DP 结论、禁止把轻量设计或 `_shared` 资产当长期真值。
2. **反向覆盖遍**：从最终真值切片逐层检查 L1–L7，每层必须标记「已修订 / 已核验无需改 / 不适用（附证据）」；再验证每个 `SD-x` 有正式规格落点、每个 `AC-x` 有正式规格来源，且 `known_in_scope_debt = []`。
3. **主题唯一性遍**：建立 `TOPIC-x`，为每个业务问题登记正向规则、禁止结果、边界、失败收口与全部正式锚点；打开全部锚点比对，同一主题存在相反结果即冻结失败。
4. **可满足性遍**：逐条证明 L5/L6/L7 要求的状态、快照、预留、时点口径在 L3/L4/域内存在合法输入与承载，或正式证明无需持久化。
5. **语义差异遍**：对比评审前设计、`DEC-x` 与最终正式规格，清零未经授权的业务语义新增/删除/改写；每个任务级 `DEC-x` 都必须进入差异账。覆盖完整不等于唯一、可实现或无漂移，四项必须分别判定。

覆盖报告固定复用 `assets/研发流程模板/规格物化覆盖报告模板.md/.json`。Markdown 供用户快速验收，JSON 是机器门禁输入；必须分别记录 `materialization_pass`、`semantic_uniqueness_pass`、`satisfiability_pass`、`decision_provenance_pass` 与 `semantic_diff_pass`——五遍产出五项布尔（物化遍产出物化与裁决溯源两项，与反向覆盖遍共同支撑 `materialization_pass`）。**五项全真**才可冻结。评审闭环不设布尔：冻结前核对「凡触发过对抗评审的对象，其报告封闭式整改验收终态 = PASS」，以报告为证据。报告只是过程证据，不能承载缺失的业务规格；**闸门审的是报告的结构与追溯，不审规格对错——语义防线是 goal 停机与候选终审**（定义见 `doc-layer-system` §3.4）。

多份 L7 的聚合 `spec_hash` 固定算法：`test_specs` 按 `path` 排序，每项只保留 `path` 与 `sha256:...`，以 UTF-8 JSON（`ensure_ascii=false`、键排序、无多余空白）计算 SHA-256。单份 L7 的自哈希规范由 `test-case-design` 定义，机器检查器会同时复验单份与聚合哈希。

调查阶段得到的文件清单只是**影响面种子**，不是回写白名单。轻量设计必须基于能力、状态、接口、数据、架构和测试链路形成最终真值切片；规格冻结对该切片负责。切片外债务可登记以后修，切片内已知腐败不得带入 goal。

**goal 执行期的文档处置**（授权写在章程里，见 `doc-layer-system` §2.3）：

1. **纯实现自由**：任一合规选择都不改变可观察结果、契约、数据、架构边界与按规格重建 → 只写代码和飞行日志，不进七层。
2. **有界重新冻结**：冻结时无人可合理预见、但影响按规格重建的非业务结果型缺口，且现有正式真值给出唯一方向 → 暂停当前切片，同步补轻量设计 `SD-x`、`TOPIC-x`、职责正式层、对应 `AC-x`、哈希和覆盖报告，五项冻结闸门重跑全绿后继续；禁止只补 L5/L6，禁止重开开放式评审。

### 5.2 goal M0：启动检查，不签发逐 AC 门票

M0 读取上一阶段的 `_shared/T{n}-goal启动服务单.md` 作为当前现场基线，但它不是执行契约或准入证明。会话、路径、命令或工具过期时直接刷新；不得因服务单与现场不同而退回旧准备阶段。

goal 的第一个里程碑固定为 M0。它按单元、接口、DB、Web/admin UI、小程序 UI、视觉、手工等**本任务命中面**各运行一个最小健康探针，确认仓库、工具链、目标环境、账号/凭据位置、数据建立与恢复通路可工作；未命中面写可核 N/A。启动报告只回答“这个执行面能否开始工作”，不得给每条 AC 预演并签发 `READY_*` 状态。

M0 可以在既有授权内新建或修复测试脚本、runner、夹具、数据工具、环境适配器与证据采集器，也可以修正错误命令、路径和依赖。后续执行中再次发现这些资产有缺陷，仍在同一 goal 内修复；不允许退回一个已经删除的前置阶段。唯一硬不变量是：脚本断言集合不得弱于冻结规格，任何修复都必须登记影响面并重跑受影响测试与证据。

M0 新建前先盘点项目正式测试基座与稳定公共 runner，记录稳定路径、来源 commit、当前分支可达性和兼容性探针；可达且兼容就先复用。只存在于兄弟分支的资产标记 `PROPAGATION_REQUIRED`，不得假称继承或擅自合并。这个盘点是复用事实，不签发 PASS/FAIL，也不恢复独立执行准备。

真实动作的权限必须来自轻量设计、获批总控方案或相应权限角色的一次性授权，至少锁定目标环境、精确动作、目标对象、费用上限与副作用范围。M0 只能继承，不能扩大；授权缺口须由环境所有者或发布授权人补齐，不属于“执行环境还没准备好”。

启动检查输出 `_shared/T{n}-goal启动检查.md`，每个命中面一行：环境身份、健康探针、结果、修复、回滚/清理、人工边界。探针失败先自愈；只有 goal-charter §4 白名单（真值矛盾 / 死亡线 / 未预授权动作）或计划内真实人工物理里程碑才停机。凭据定位与重复失败不取得停机权；安全路径穷尽或达到限轮时只交付 `EXECUTION_BLOCKED`，不前拉上游。

### 5.3 候选终审：只读验收精确候选，不重做施工

goal 结束时只能提交 `CANDIDATE_READY`。终审必须锁定 commit/tree SHA，确认工作树干净，复验规格清单与执行证据清单哈希，并打开真实测试落点而不是只看 `AC-x` 字面出现。

- **⑧必须实例化为显式子任务，不可塌缩、不可省略。** goal 交付 `CANDIDATE_READY` 后无人终审是一个结构缺口：候选会悬空无人验收，多个未合并候选还可能在共享环境上互相覆盖。
- **终审 PASS 前，goal 执行子任务不得标「已完成」**：状态保持「进行中」，README 进展记录登记「候选待终审」；候选终审子任务完成前，总控整体同样不得标完成。
- 普通/中风险候选：**默认启动一个全新上下文做独立只读终审**；项目补丁可用 `{{候选终审 skill}}` 覆盖具体实现，但不得复用生产候选的同一上下文，也不得以“槽位未绑定”为由跳过终审。
- 高风险/死亡线候选：对该精确候选使用 `{{评审 skill}}` 代码候选口径，仍遵守同阶段、同对象哈希、同真值基线只开放评审一次。
- 主线逐条裁决意见；终审只写终审报告、README 状态/进展和受控退回指针，禁止修改产品、正式规格、测试资产、runner、冻结件或执行证据。
- 退回路由唯一：产品、测试资产、runner、夹具、环境适配或证据工具缺陷 → **同一 goal**；冻结用例语义或正式规格/业务语义确有缺陷 → **默认热修**：终审报告随附修改方案（决策项 + 上游修改清单 + 失效证据清单 + 恢复点，格式同 goal-charter §4），业务决策负责人按项目治理批准后直接改齐用例/正式层并回同一 goal 补受影响切片，不打回上游子任务；方案论证热修不可靠且获相应批准时，才回退测试用例设计或轻量设计 + 真值收敛与规格冻结子任务重来；缺少外部授权 → 对应环境所有者或发布授权人补权。不得把任何修复留在终审。
- 失效范围按影响面计算：同一 goal 的可逆修复只使受影响测试、证据与候选失效；用例变化才使对应 AC 与下游证据失效；正式规格变化才重建章程及其下游。禁止“一处 runner 小错导致全部上游作废”。历史文件保留供审计，但不得继续充当当前输入。
- 最终只有 `VERIFIED` 计入通过；存在 `BLOCKED/MISSING`、无来源 `WAIVED`、未闭环发现或未通过验证命令时，禁止出具最终验收封印。
- 终审必须核对**真实链路闭合度**结论：逐条过 `env_fidelity=simulated` 与 `BLOCKED` 清单，确认交付记录用人话写明真实链路断在哪、由谁何时接通；缺此结论不得出具封印。
- 终审必须核对**执行资产交接**：本轮新增/修复资产已区分任务临时、领域复用、项目通用；可复用项已晋升稳定路径并提交，且交接写明验证命令、环境前提、消费者和跨分支传播状态。`PROPAGATION_REQUIRED` 可以作为跨任务待办显式存在，但后续任务在来源 commit 可达前不得宣称已继承。

改变业务结果的 → 停机附修改方案（一次批准热修续跑为默认，回炉为例外），不在自愈范围内。

### 5.4 未完成存量总控的兼容升级

本规则生效前已创建、但尚未进入 goal 的标准研发总控，**不批量重写全部历史工作包**，按下一次触达渐进升级：

- 尚未完成的轻量设计 / 用例 / 规格冻结子任务，执行前直接按现行 skill 修订该工作包：补最终真值切片、`SD-x`与 `TOPIC-x`、把用例全文归位正式 L7、把规格冻结改成五遍收敛。
- 尚未进入 goal 的存量任务删除尚未执行的独立执行准备包，或把它标记为“历史输入，不再是门票”；章程补 M0 启动检查、执行基础设施自愈权限与影响面重跑规则后即可继续。
- 尚未进入 goal 的存量任务在下一次触达章程时补 `_shared/T{n}-goal启动服务单.md`：声明治理角色与环境占用策略，清算候选无关的 `PRE_GOAL`，将 AI 可操作项还给 goal，只保留真实候选依赖的人工协作窗口。已取消的独立执行准备任务不复活。
- 旧“规格冻结”已标完成、但缺规格物化覆盖报告时，视为上游完成判定不足；自动把该子任务恢复为待完成并补齐，不需要用户裁决流程细节。
- 旧评审已标完成、但存在多轮 R2/R3、无 `DEC-x` 或无封闭验收时，不重跑开放评审：以最后一份有效裁决报告建立固定整改清单，补授权裁决来源、实际角色与业务语义差异，再走一次 `{{封闭验收 skill}}`。
- goal 章程准入看规格物化覆盖报告是否全绿以及必要用户授权是否明确；不得再要求逐 AC readiness 报告。
- 兼容升级只改尚未执行或需补齐的工作包与状态，不重写已完成任务的历史记录，也不扩张最终真值切片。

`control` 仍遵守单子任务边界：自动修正编排和状态后，下一次只执行被恢复的规格收敛子任务；不得在执行 goal 章程时顺手跨任务补规格冻结子任务。

## 6. 阶段 → 槽位映射 + 项目补丁发现协议

八阶段是抽象的；每个阶段「该读什么 skill / 产出落哪 / 用什么验证」是**项目特定**的，由**项目研发流程补丁**填充。本文件只声明抽象槽位，**不写任何项目名**。

抽象槽位（项目补丁负责一一填实）：

| 槽位 | 含义 |
|---|---|
| `{{调查锚点}}` | 调查阶段强制阅读的项目文档体系 / 真值锚定 skill |
| `{{探讨依据}}` | 探讨阶段强制阅读的需求/契约层文档 |
| `{{轻量设计 skill}}` | 轻量设计方法 skill（含影响面勘察 + 验收映射） |
| `{{测试设计 skill}}` | 测试规范 + 测试用例规格真值 skill，可由项目补丁绑定为多个 skill |
| `{{评审 skill}}` | 对抗评审 skill（须提供设计 / 用例 / 章程三张口径卡） |
| `{{封闭验收 skill}}` | 对抗评审整改后的封闭验收 skill；当前工具原生子线程只读检查，主线程裁决，禁止跨工具与 R2/R3 |
| `{{规格冻结 skill}}` | 把设计写进正式文档体系并冻结的 skill + 长文档治理 |
| `{{goal 章程 skill}}` | goal 章程方法 skill |
| `{{goal 执行绑定}}` | goal 执行阶段的全部绑定，**复合槽位，七类逐项填全**：①goal 章程方法 skill（执行期回读飞行日志/边界语义）②M0 启动检查与测试基础设施自愈 ③交付/发布/部署 skill ④测试执行路由 ⑤项目执行 skill ⑥环境边界/架构规范 skill ⑦**代码合规检查器命令**（可落在对照表的「验证」列，但必须可从本槽位追溯）。漏一项 goal 就不知道怎么启动 / 怎么部署 / 怎么跑测试 / 环境红线在哪 / 拿什么判代码合规 |
| `{{候选终审 skill}}` | 普通/中风险精确候选的独立验收入口；必须展开到测试执行证据协议 + 项目证据规则，核对候选 SHA、原生断言事件、语义证据分布、消费者完整性和飞行日志 |
| `{{死亡线区域}}` | 项目高风险区清单（触发独立评审/升级），**封闭清单，任何人无权新增** |

### 6.1 项目补丁发现协议（实例化前 fail-stop）

实例化研发流程前，AI **必须**先定位并加载「当前项目的研发流程补丁」：

1. 在项目根 `.claude/skills/`（及对应运行面 skills 目录）下，查找声明自己是「`task-control-doc` 研发流程补丁」的 skill（其 description / 开头声明含此语义，并提供上表槽位的填充）。
2. **找到** → 加载它，按其槽位对照表把模板里的 `{{槽位}}` 替换成项目真实绑定。
3. **找不到** → **停机询问用户**：当前项目没有研发流程补丁，是否（a）先创建补丁、（b）改用通用拆分模式手工编排。**禁止**用带 `{{槽位}}` 的纯抽象模板直接落盘。

## 8. 与单文件 / 拆分载体的关系

研发流程是正交预设；落盘载体仍按现有规则自动选：

- 实例化后**子任务数 ≤ 7 且各详情 < 50 行** → **单文件载体**（全部写进一个 `README.md`）。
- 否则 → **拆分载体**（每子任务一个 `T{n}-*.md`）。
- 边界模糊时问用户。

> 研发流程任务通常阶段多、每包长，**多数落拆分载体**；但小型研发任务（如单域小功能）实例化后可能只有 4-5 个精简子任务，落单文件载体即可——不要因为"套了研发流程"就强制拆分。
