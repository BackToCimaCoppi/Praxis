## 子任务背景

- 用户提供的资料：

## 要做的事情

1. 按 `{{调查锚点}}` 锚定本任务触及的代码真值与需求真值
2. 系统性比对，**逐条登记代码 ↔ 文档 / 需求的割裂点**（位置、现状、应然、影响）
3. （可选）行业 / 前沿技术调查，沉淀关键结论
4. 产出调查报告，割裂点清单作为报告的强制章节

## 不做什么

- 不做设计、不下技术选型结论（属探讨/设计阶段）
- 不改任何代码、不改任何正式文档
- 不在本阶段"顺手修"发现的割裂（登记即可，回写阶段统一处理）

## 预期效果

本任务的真值地图清晰：触及哪些层/域、既有真值是什么、哪里割裂——后续阶段有据可依。

## 输出物

- `_shared/T{n}-调查报告.md`：调查结论 + **割裂点清单**（强制章节；若确无割裂，显式写"本任务无连带割裂"）

## 完成判定

- [ ] 调查报告已产出
- [ ] **割裂点清单已列全**（或显式声明无割裂）
- [ ] 父级 `README.md` 子任务总表本行状态改为 `已完成`
- [ ] 父级 `README.md` 进展记录已追加一行

## 风险与注意事项

- 割裂点清单是回写阶段的边界依据，**漏登记 = 回写阶段无据可依**，务必扫全
- 不要把"想改成什么"混进调查（那是设计），调查只记"现状 vs 应然的差"
