# 测试执行路由

本 skill 只回答：冻结用例如何被准备、执行、路由和收口。不要在本层改用例口径；不要写项目凭据或平台专属细节。

## 0. 同一 goal 内的两种模式

| 模式 | 发生时点 | 可以做 | 禁止做 |
|---|---|---|---|
| `bootstrap` M0 启动检查 | goal 首个里程碑 | 实现/修复测试资产、runner、夹具、数据/环境适配与证据工具；每个命中面运行一个最小健康探针 | 改冻结用例语义、扩大用户授权、给逐 AC 提前签发 Ready |
| `verification` 正式验证 | goal 各施工切片内及候选交付前 | 跑冻结矩阵、封存 raw、派生证据状态；发现基础设施缺陷可就地修复并按影响面重跑 | 手填 VERIFIED、削弱断言、把产品现状反写测试 |

两种模式执行前都必须满足：

- 已读取冻结用例规格。
- 已确认 `execution_ref` 或预定锚点。
- 已生成执行面矩阵：单元、接口、DB 预置、DB 终态、Web/admin UI、小程序 UI、视觉、手工；本任务命中面各一行，N/A 有可核理由。
- 已识别项目执行 skill；如果项目没有执行 skill，先报告缺口。

涉及真实动作时必须有上游用户授权锚点，逐项锁定目标环境、精确动作、目标对象、费用上限（含重试储备）与副作用范围。没有独立 readiness 门票；`bootstrap` 的失败先在 goal 内自愈。只有 goal-charter §4 白名单（真值矛盾 / 死亡线 / 未预授权动作，细则以彼处为真值）或计划内真实人工里程碑才交给用户；安全路径穷尽或达到限轮只交付 `EXECUTION_BLOCKED`，不前拉上游。

禁止行为：

- 边执行边修改断言。
- 用“环境不方便”跳过自动化。
- 把手工验证计作自动化覆盖。
- 把 AI 可控浏览器/开发者工具、DOM/data 断言、截图或 VLM 判读降级成手工。
- 失败后只写“测试失败”，不分类。
- 状态账本自证、派生聚合物冒充 raw、从账本反向改 raw、事后补绑候选版本或环境。

### 0.1 证据强度按影响面选择

执行载体的轻重不决定证据重量。先根据冻结规格与执行面矩阵选一种证据轮廓并记录理由，施工中发现影响面扩大时自动升档，禁止为了省事降档：

| 轮廓 | 适用判据 | 最低闭环 |
|---|---|---|
| `direct-native` | 文案、样式、局部只读展示或单点行为；不改接口契约、持久化结构/写链路、状态机/并发/时钟语义，且已有稳定 runner 能直接给出原生结果 | 最终候选 + 目标环境 + run 绑定；AC 逐项直指原生报告、截图或终点实测；失败/错误/跳过/未执行完整可见；不为包装而新造证据框架 |
| `assertion-native` | 新增/变更表、字段、索引、迁移、接口契约、持久化写链路、状态机/并发/时钟规则、跨前后端完整功能、死亡线、高失败代价，或需要新建/实质修改取证工具 | 细粒度逐 AC/证明部件的 raw → envelope → mapping → 账本；所需 fixture/harness、数据清理恢复和终态校验；项目原生检查器全绿 |

`direct-native` 不是口头验收：缺候选/环境/run 绑定、用聚合 PASS 代替原始结果、隐藏失败或无法逐 AC 定位时必须升为 `assertion-native` 或补齐原生观测。`assertion-native` 也不要求每个任务重造生成器；优先复用项目公共 producer/checker，只有实际观测适配缺口才建设新工具。标准总控有正式 L7 和独立冻结索引时默认 `assertion-native`；`plan-goal` 以批准后的 AC 表直接充当索引，是否采用细粒度证据仍只看上述影响面。

涉及真实动作时必须有上游用户授权锚点，逐项锁定目标环境、精确动作、目标对象、费用上限（含重试储备）与副作用范围。没有独立 readiness 门票；`bootstrap` 的失败先在 goal 内自愈。只有 goal-charter §4 白名单（真值矛盾 / 死亡线 / 未预授权动作，细则以彼处为真值）或计划内真实人工里程碑才交给用户；安全路径穷尽或达到限轮只交付 `EXECUTION_BLOCKED`，不前拉上游。

禁止行为：

- 边执行边修改断言。
- 用“环境不方便”跳过自动化。
- 把手工验证计作自动化覆盖。
- 把 AI 可控浏览器/开发者工具、DOM/data 断言、截图或 VLM 判读降级成手工。
- 失败后只写“测试失败”，不分类。
- 状态账本自证、派生聚合物冒充 raw、从账本反向改 raw、事后补绑候选版本或环境。

## 1. 执行流程

### 1.1 `bootstrap` M0 启动检查

1. 读取冻结用例、执行面矩阵、上游授权与项目执行 skill；逐面加载对应参考。
2. 先查项目正式测试基座、稳定 runner/夹具/环境适配与其登记索引，逐项记录 `稳定路径 / 来源 commit / 当前分支是否可达 / 兼容性探针`；可复用且可达的资产先复用，禁止无声重造。资产只存在于兄弟分支时标记 `PROPAGATION_REQUIRED`，不得假称已经继承，也不得擅自合并分支。
3. 每个命中面填写：环境身份/保真度、凭据位置、数据建立/清理/恢复、部署通路、预算、最小健康探针与人工边界；N/A 面填写证据化理由。
4. 实现或修复 `execution_ref`、测试资产、runner、夹具、环境适配与证据工具；错误命令、路径和依赖属于本模式自愈项。
5. 每个命中面只运行一个能区分“执行基础设施坏了”与“可以开始工作”的健康探针。报告状态仅为 `HEALTHY / REPAIRED / BLOCKED_AUTH / MANUAL_BOUNDARY`，不得逐 AC 预演或签发 Ready。
6. 输出 `_shared/T{n}-goal启动检查.md`。这份报告是 goal 的首个运行记录，不是章程准入证明，也不冻结测试资产版本；资产继承清单是复用事实，不是新准入闸。

### 1.2 `verification` 正式验证

1. 复验冻结用例、M0 启动检查、当前测试资产和候选 commit/tree。
2. 按矩阵路由执行测试。发现测试资产/runner/夹具/环境适配/证据工具缺陷时，在同一 goal 内修复；登记影响面，重跑受影响测试和证据。
3. 编号覆盖核对：冻结 `assertion_index` 的每个 `AC-x` 都在测试资产里有字面落点；项目检查器必须通过。
4. 每次运行按 §3.5 单向封存证据，再派生 `VERIFIED / BLOCKED / MISSING / WAIVED`。
5. 运行项目执行证据检查器；失败按 §4 分类并路由，产出执行报告。

## 2. 路由表

| 用例类型 | 路由 |
|---|---|
| 单元测试 | 项目执行 skill 的 unit 参考 |
| 接口测试 | 项目执行 skill 的 api 参考 |
| DB 预置/校验 | 项目执行 skill 的 db 参考 |
| Web UI 自动化 | 项目执行 skill 的 web-ui 参考 |
| 小程序 UI 自动化 | 项目执行 skill 的 mp-ui 参考 |
| 视觉/VLM 验收 | 项目执行 skill 的 visual 参考 |
| 交付/发布验证 | 项目执行 skill 的 release/evidence 参考 |
| 手工验证 | 项目执行 skill 的 evidence 参考；只生成 runbook 与回传要求 |

项目执行 skill 的名称、参考文件布局与命令细节由**项目级补丁**声明（见 `templates/项目级补丁模板/`）。项目一旦提供了自己的测试执行 skill，该项目的全部执行请求统一路由到它，本 skill 不再猜测命令。

## 3. 执行顺序

默认顺序：

1. 静态/单元测试：快速暴露局部缺陷。
2. 数据前置：准备幂等测试数据。
3. 接口测试：验证契约与业务写链路。
4. DB 校验：验证终态、不变量、幂等。
5. Web/小程序 UI 自动化：验证用户路径。
6. 视觉验收：判读布局、图表、canvas 合成图等视觉结果。
7. 交付收口：汇总证据和阻断项。

可以调整顺序，但必须说明原因。例如 UI 用例依赖接口造数完成，接口测试必须先跑。

### 3.1 可复用执行资产的晋升与交接

goal 中新增或修复的执行资产在候选交接前必须分三类：

| 分类 | 典型内容 | 终态 |
|---|---|---|
| 任务临时 | raw、截图、会话状态、一次性恢复文件、内容寻址证据包 | 留在任务证据或本地运行根；不得冒充下次可复用基座 |
| 领域/场景复用 | 正式测试脚本、fixture、领域 harness、稳定 `execution_ref` | 晋升到项目正式测试目录并提交；登记入口、适用范围、环境前提与验证命令 |
| 项目通用 | 公共 runner、环境适配器、证据/清理工具 | 晋升到项目公共稳定路径并提交；登记已验证消费者与兼容边界 |

飞行日志或候选交接必须有“执行资产交接”段，逐项记录：稳定路径、资产分类、引入/修复 commit、验证命令与结果、环境/凭据前提、已知消费者、当前分支可达性、兄弟分支传播状态。没有复用价值时明确写“本轮无可晋升资产”。可复用资产不得只留在任务 `_shared`、本地运行根或未提交工作树；跨分支传播尚未完成可以显式留为 `PROPAGATION_REQUIRED`，但后续任务在 commit 可达前不得宣称继承成功。

这是一项候选交接义务，不是恢复独立执行准备：M0 不因登记不完整停机，当前 goal 仍在授权内自愈；候选终审只核对“本轮实际产生的复用价值是否已晋升并如实说明传播状态”。

### 3.2 批量收集、集中修复与完整核验

本节与 §3.3 是**必须遵守的提速执行纪律，不是可选建议，也不是新增验收门槛**。直接使用项目现有测试命令、原生报告和执行记录；**不为监督执行顺序或并行率新增检测工具、监控适配、机器批次凭证或准备阶段**。效率偏差与质量缺陷按 §3.4 分开处理。

- **收集期间固定输入**：明确本轮范围、候选、工具版本与环境身份；同一执行分支采集期间不热改。普通断言失败或独立证据缺口立即记红，继续其他安全、有效、无依赖的检查；失败阻断交付，不自动中断整批。
- **只停受影响分支**：前置失效、环境污染、清理失败或身份不可信时，不执行依赖后续、不把连锁红当独立缺陷；有效独立分支继续。既有授权、规格裁决与真实人工边界出口不变。
- **必须收齐再修**：必须先收齐当前可完成的安全独立检查，汇总全部已知问题并按 §4 分类、归并根因，再在同一 goal 集中修复；**禁止一遇普通失败就停掉其余独立检查、修一项重启整套**。先定向复测，再完整核验冻结义务。保留原有限轮、时间与预算，不把重新测试当作重置额度。
- **必须利用独立并行**：已授权、输入可隔离且没有真实依赖或资源冲突的施工与检查，有执行槽位就必须并行推进；不得仅因菜单顺序或习惯串行。修复包的派发与合流按 §3.3。
- **长时等待不是全局屏障**：真实跨时钟检查尽早启动、保留等待断点；能保持等待分支候选、工具、环境和数据前提不变时，必须推进其他已就绪的独立工作，不得空等。共享可变输入无法隔离则不并写；修复影响等待事实时按原协议使受影响证据失效并重跑。最终义务不拆出、不用配置或历史事件代签。
- **失败历史与候选集合分清**：历轮原始失败不可变保留于各自运行记录，关联根因、修复和复验；不混进后续最终候选有效集合造成永久卡红，也不删除历史失败或挑偶然绿求通过。最终集合中的失败、未解决缺陷和未执行义务仍按 §3.5 阻断，禁止剪掉同一有效运行中的红项。
- **合流后完整核验**：固定新候选，核验全部冻结验收义务及适用检查器，每项须有符合当前候选/环境要求的有效证据，非法项为零。完整核验不等于每轮重跑所有命令；需新观测的必须重跑，兼容复用仅沿用既有协议和检查器，不自行扩展复用口径。构建兼容不等于旧候选 raw 可搬用；无合法复用依据就重采。轻量任务仍以批准后的 AC 表为集合，不引入中大任务冻结管线。
- **沿用现有记录**：总控用原断点/飞行日志，轻量计划仅在 §9 简记失败、修复、测试结果路径、重跑/复用依据及累计修复—复验次数。恢复先核现存记录与输入，**必须续用仍有效部分，仅按影响面重跑失效部分，不得无故重跑整套**。任务累计次数不因恢复、真实等待或重新测试清零，也不冒称修改平台会话轮数；保留原强读和磁盘复水，不新增报告模板、审批或逐 AC 门票。

### 3.2.1 按当前问题选择下一轮验证

总控 Goal 与 plan-goal 共用本节；这是 §3.2 的执行选择，不新增阶段、门票或交付条件。

| 当前状态 | 下一步 | 不该做什么 |
|---|---|---|
| 新建/修改测试、采集或证据适配资产 | 在既有施工中，用所选正式执行环境的最小真实样本，尽早走通运行→采集→实际消费/比较端；新改取证语义仍按 §3.6 条件核对 | 不等全量采完才试消费端；不把 M0 扩成逐 AC 预演，稳定未改资产不重复加测 |
| 当前批次出现普通失败 | 保持输入，按 §3.2 收齐可完成的安全独立检查，归并根因 | 不一红就修，也不继续环境已污染的依赖分支 |
| 修复未合流、相关已知问题未解决 | 先完成相关修复，再跑失败项及共享根因/消费者的影响面验证；独立包按 §3.3 并行 | 不因一个修复局部变绿就重启昂贵整轮 |
| 相关修复已合流、定向验证成立 | 固定候选，完整核验冻结义务并运行必要完整验证 | 不用局部绿拼最终绿，也不为“完整”机械重复全部命令 |
| 仅汇总/封装损坏，原始事实仍有效 | 按 §3.5 和项目检查器修复消费/装配，复用仍有效原件；工具语义变化仍按 §3.6 | 不为改报告重跑业务；不改 raw、事后绑定或扩大复用口径 |
| 候选/环境/数据前提变化 | 按原证据协议判断失效范围；无合法复用依据就重采 | 不把“业务代码没改”或“构建兼容”当作旧 raw 可用证明 |

- **诊断不等于验收**：根因定位确需集成或完整运行时可以执行，在原记录写明要区分的假设及所需范围；不因仍有已知缺陷禁止有价值的诊断，也不把诊断轮宣称为最终验证。无需等无依赖的长时分支结束才修已收齐的问题组。
- **提前发现不是双跑**：检查已有断言绑定/消费者映射的可用性与正式环境差异；有视觉义务的新改页面/采集路径，在施工中尽早看代表性真实截图，但不能替代冻结的完整视觉义务。复用已有健康探针/定向运行，不另造全套预验收。
- **重复失败先改假设**：同类失败重现，先核对原始失败、上次修复是否命中根因、实际正式环境及全部消费者，再选择可区分假设的最小验证；必要时按 §3.3.1 升级有界诊断。重复本身不新增人工出口、不重置原限轮/预算。

### 3.3 已知失败的有界并行修复

- 主线程在原授权范围内，把本轮已收齐失败按根因和依赖枚举成叶子修复包；枚举时点是派发前，不要求施工前预知每个缺陷。**至少两个独立包且有可用槽位时，必须实际并行，禁止把“可以并行”当成可不执行的建议**；串行须在原记录中简记具体写入冲突、依赖、共享资源或运行时槽位限制。公共根因、重叠写入或强依赖合并负责或分批，不按报错条数派发。
- 每包提供失败原件、冻结要求、允许写入范围、依赖/共享资源及定向验证要求；超范围的新问题交回主线程，不自行扩展调查或改变断言、权限。
- 主线程唯一派发；事前明确本批任务数、并发槽与批次数上限，按可用槽位执行，受原 goal 限轮/时间/预算约束。子代理不得递归、另起 goal 或开放式调查；有界执行的纪律沿用 `deep-research-gate`，不把提示词禁令当物理权限隔离。
- 共享工作树按不重叠写入范围分工，共享文件单一负责人；主线程统一整合与提交。共享开发者工具、账号或数据的操作排队，有可靠隔离才并跑；文件分工不等于环境或运行中读输入已隔离。
- 子代理自测仅用于交回修复，不能把局部绿拼为最终绿；合流后按 §3.2 完整核验并做必要重跑。取证工具实质改动合流后，由主线程按 §3.6 合并派独立核对，完成后才用相关工具批量产证；修复者不递归代派、不自批豁免。
- 修复包及其合流结果沿用既有执行记录，不增加模板章节、审批或每包独立评审。

### 3.3.1 主线程职责、叶子交接与模型策略

总控 Goal 与 plan-goal 的主线程都负责同一套执行闭环；总控的跨任务推进权不因此下放，也不带入轻量任务。

| 角色 | 必须保留/交付的职责 | 不下放的权力 |
|---|---|---|
| 主线程 | 亲读冻结真值与必读；维护当前候选、未完成义务、已知根因、依赖与资源占用；唯一派工、集成提交、核验关键原始证据与全部义务 | 业务/授权裁决、变更范围、最终候选判断与现有独立终审不能由实现者自批 |
| 有界实现/验证叶子 | 完成指定实现、执行资产修复、定向测试、明确日志提取或已知失败的窄范围根因诊断；只消费给定真值与必要直接依赖 | 不补开放背景、不递归、不另起 Goal、不改冻结断言、不接管总控或宣布整体完成 |
| 独立核对/终审叶子 | 保持既有触发条件和只读独立性，只核被指派对象 | 不兼任该对象修复者；普通子代理自测不能取代它 |

- **窄诊断不是补背景调查**：已知失败原件、冻结要求、范围与待区分假设明确后，主线程可派叶子追查该失败的直接依赖；不能把“调查整个模块/项目以补上下文”包装成修复包。范围外发现交回主线程，不自行扩张。
- **交回差量而非倾倒日志**：叶子简报变更及候选身份、实际验证及原件路径、未解决项/反证、受影响消费者和建议下一步；摘要不能替代证据。主线程按风险核对关键原件与所有未完成义务，不必重复叶子所有探索。沿用原日志/断点，不新建报告模板。
- **恢复保留强读**：首次/恢复/压缩后完整执行入口规定的必读，再以现有断点和运行事实恢复当前状态；减少的是额外历史与重复长日志，不得用子代理摘要或短交接替代必读。不为减上下文强迫用户新开会话。

**模型选择**：主线程沿用用户当前会话所选模型，不声称可在执行中自动更换；叶子模型只从当前工具实际可用列表里选择，并在派发时明确记录。疑难诊断可按需提高推理档，不全程双跑；缺少独立上下文能力时不能把主线程自检冒充独立验收。

### 3.4 效率纪律与质量验收分离

- **执行必须提速，终审不考核过程表演**：提前修了一项、可并行却串行、重复测试或无故重造可复用资产等纯效率偏差，在原执行记录/复盘简记并改进后续执行；不得因此退回候选、判 AC 失败、阻断交付、重演整轮流程或额外消耗修复轮数。效率记录不另设完整性门票，缺一条说明不构成质量缺陷。
- **质量与授权底线不变**：漏测、隐藏失败、削弱断言、原生事实缺失、测试结果与最终候选/环境不符、越权动作，仍按既有验收要求处理。拒收必须指向具体未满足的义务或不可信证据，只补验受影响部分；不得把业务并发用例必需的真并发误当作可省的执行调度。原生检查器、独立终审和原限轮/预算保留，纯流程偏差不等于结果失真，结果失真也不得降格成效率问题。
- **撤销工具不迁移业务契约**：历史冻结计划如仍引用本轮已撤销的批次检测工具，下一次触达在原记录注明用户撤销要求，继续用既有原生证据链，不补工具、不补流程票据、不因撤销重跑；不改写历史记录、冻结业务语义、AC 或权限，不干预其他正在执行的任务。真实业务取证工具的必要修复仍按 §3.5—3.6，不能混同于已撤销的流程监督工具。

### 3.5 单向证据协议

`assertion-native` 的证据顺序固定：**raw 运行先发生 → 采集时不可变信封 → AC 映射 → 状态账本**。

`assertion-native` 新候选沿用 `schema_version=2`，但必须声明 `evidence_semantics_version: assertion-native-v1`。缺该标记的旧包只能显式以 legacy 只读模式审计，不能签发新的 `CANDIDATE_READY`。

信封与 raw 必须位于同一内容寻址包，并至少封存：候选 commit/tree、环境身份与保真度、run ID、`framework_test_id`、原生报告路径与 SHA-256、原生结果定位、assertion ID、`proof_part_id`、观测面、observed、expected/判定器、采集时间。自动化 raw 必须来自框架原生报告或真实扫描器输出；wrapper 只允许规范化和装配，禁止生成断言事实。手工/物理边界必须指向采集时产生的原始键、截图或外部响应，不得用事后聚合哈希代替。任何状态都只能从该包重算；禁止逆向改 raw、派生聚合物冒充 raw、事后补绑候选或环境。

**哈希闭合不等于命题成立**：消费侧必须解析上述原始定位，提取实际观测并执行与冻结预期对应的比较，不能只比“报告与信封都写 PASS”。普通 AC 优先直引原生断言，不额外编造包装观测；高风险项沿用 L7 既有证明部件，不再另建观测契约。观测面由 L7 决定：静态扫描可以证明静态约束，不能替代运行、并发或跨时钟事件。比较器规范化必须保留可核的等价比较；不支持的提取/比较留作工具缺口，Goal 内修复并重跑，不改 expected 求绿。

多个 AC 可共享同一个真实测试，但每个 AC 必须满足 L7 的全部证明部件。去除 AC/测试标识、路径、时间戳和哈希后仍相同的观测内容，只有存在 L7 等价组时才能复用；换 assertion ID、test ID 或 observation key 不能把通用观测变成独立证明。套件退出码、文件存在、日志/聚合哈希、源码位置均属代理观测，不能单独签发 `VERIFIED`。

**消费者完整性**：每个已执行测试/套件必须被至少一个 AC 消费，或显式声明 `supporting_only_reason`；任何失败、错误、跳过、已绑定但未执行的测试都阻断候选，辅助套件失败也不例外。多部件 AC 缺任一部件即为 `MISSING`。

候选交付前必须生成观测分布报告：代理观测、标准化重复簇、等价组、孤儿套件、未消费失败/跳过、未执行绑定、多部件缺口均列数量和明细，任一非法项非零不得报 `CANDIDATE_READY`。`MISSING` 证明缺什么，`BLOCKED` 证明物理边界，二者不要求伪造运行成功证据，也绝不计入覆盖。

### 3.6 取证工具条件核对（Goal 内自动工序）

**目的**：采集器、提取器与判断器可能共享执行方的同一误解；在它批量产证或消耗昂贵外部窗口前，让另一上下文核实“事实从哪里来、能证明什么、比较是否执行”。这不是产品预终审，不增加流程阶段、人工审批或逐 AC 准备门票。

**触发与合并**：本轮新建取证工具，或改变原始来源、观测提取、比较关系、证明绑定时触发；同一批相关工具合并一次。已核对的稳定资产兼容复用，以及只改路径、排版、日志且不改变取证语义，不重复触发。后续新增实质变化只核新增影响面，不重审未变部分。

1. 先跑一对有区分度的本地回归：正确事实能通过；在套件成功、状态声明与哈希均正常时，把被消费的业务事实改错，整条证据链应拒绝。负例重新封包以排除“只测出了哈希不符”；打断构建或仅检查提示词文字不能代替这个负例。不默认新增生产故障注入或费用授权。
2. 由主线程在当前工具启动**一个全新上下文原生只读叶子子代理**，禁止递归/外部多模型调用；并行修复包须先合流，修复者不得代派或以自测豁免。输入仅含本批工具及直接依赖的 diff、现有 L7 对应证明义务、原始正反例与验证命令，不喂主线程“已正确”的判断。核对三件事：原始定位真的被读取；观测面/事件能对应既有义务；错值会被真实比较拒绝。重复适配路径按实现族核对，不按 AC 数量复制评审。
3. 子代理只报具体缺口及证据，不修改代码/证据包、不新增业务要求、不逐条签发 AC。主线程按冻结语义逐项处理；工具缺陷在同一 Goal 修，已指出缺口只做定点复验，不重开开放式调查。核对通过不冻结工具，也不替代正式测试和独立候选终审。
4. 在既有飞行日志/资产交接中登记触发原因、工具版本/范围、核对结论、正反例命令与修复影响面即可，不建新登记系统。缺陷未修复前不使用该工具签发受影响证据；其他无依赖工作照常推进。共享工具缺陷影响其全部实际消费者，未受影响证据和上游不作废。

没有可用的原生独立上下文时先修调用方式/等待恢复，不能让同一执行方自称已独立核对；安全路径穷尽后按既有工程阻塞出口交还控制权，**不是新增用户裁决条件**。真实跨时钟用例提早启动并并行等待，不以配置值代替事件，也不因等待自动缩小验收范围。

## 4. 失败分类

失败必须分类：

| 分类 | 含义 | 处置 |
|---|---|---|
| `PRODUCT_BUG` | 产品实现与冻结用例或上游真值不符 | 路由 goal 修产品代码，重跑相关测试 |
| `HARNESS_BUG` | 测试资产、runner、夹具或证据工具错误，但用例口径正确；历史 `TEST_BUG` 等价映射到本类 | goal 内修复，按影响面重跑；不得让小错使全部上游失效 |
| `SPEC_STALE` | 冻结用例或上游正式真值的语义确有缺陷 | 默认热修：附修改方案经业务决策负责人按项目治理批准后直接修订用例/正式层，按语义影响面作废并重跑下游，回同一 goal 续跑；热修不可靠且获相应批准才回退用例设计或设计+规格冻结子任务 |
| `ENV` | 服务、网络、依赖或测试数据环境问题 | goal 内修环境或重建数据后重跑；缺外部授权另分 `AUTHORITY_REQUIRED` |
| `FLAKE` | 时序或异步导致间歇失败 | 修等待/隔离；连续 flake 不得当通过 |
| `MANUAL_REQUIRED` | AI 无法操作真实设备/原生对象/原生授权等物理边界 | 输出物理边界证明、runbook、客观回传要求与写明责任角色的人工里程碑 |
| `AUTHORITY_REQUIRED` | 所需真实动作未获授权或凭据位置未知 | 停在对应环境所有者/发布授权人补权或告知受控位置；不得猜测或偷偷降级为模拟 |

## 6. 与其他 skill 的边界

- 规范矩阵不足：回到 `test-standards`。
- 用例质量不足：回到 `test-case-design`。
- 项目命令和工具细节：进入项目执行 skill。
- 测试暴露产品缺陷：进入项目排障/RCA skill 或主线程修复流程。
- 测试基础设施缺陷：留在同一 goal，修复并按影响面重跑。
