# 证据包制作规范（dispatch 参考文档）

> 本文档是 ask-claude skill 的参考资料，不是独立的 skill。日常简单调用直接用 ask-claude 的内联模板；复杂场景（多文件、多层约束、待决策点）回到本规范深度制包。

---

## 0. RAM 框架

证据包不是「与任务相关的内容集合」，而是「收包方完成特定动作所需的最小充分集合」。

| 要素 | 含义 | 问自己 |
|------|------|--------|
| **R（Reader）收包方** | 谁来读这个包？ | 外部模型？子代理？用户？ |
| **A（Action）动作** | 收包方要做什么？ | 设计 / 评审 / 裁决 / 审计 / 执行 / 回答问题 |
| **M（Minimum）最小集** | 收包方完成 A 所需的最小充分内容 | 由 R+A 联合推导，不由任务关联性推导 |

**核心检验句**（每一项内容必须能完整填入）：

> 「**[R]** 需要 **[这项内容]**，才能 **[A]**，否则会卡在 **[具体卡点]**。」

填不完整 → 删除。不确定 → 默认删除（而不是默认保留）。

---

## 1. 两个关键维度

### 1.1 信息交付方式

决定「包里装的是什么」，分三种：

| 方式 | 含义 | 适用条件 |
|------|------|---------|
| **内嵌模式** | 把内容直接写进包里 | 收包方无法访问文件系统；内容短小；必须确保可见 |
| **引用模式** | 只写文件路径 + 行/方法范围 | 收包方在同一 workspace 内；文件大只需读特定位置 |
| **混合模式** | 关键约束/红线内嵌 + 大文件引用 | 大多数复杂场景的默认选择 |

**引用模式必须附带最小必读清单**：

> 以下是最小必读清单（必读）。如你判断需要更多上下文，可自行阅读仓库其他文件。

这句话只做**准入**（告诉收包方至少要读什么），不再**禁入**——收包方用的是强模型，往往比制包方更清楚还该读什么，是否补读由它自己决定。

### 1.2 输出要求

决定「收包方应该如何行动」，是每个包都必须声明的字段：

| 输出方式 | 含义 | 关键约束 |
|---------|------|---------|
| **直接回复** | 输出结论到 stdout，不改文件 | prompt 末尾必须写「不要改任何文件，不要创建文件」 |
| **写入指定文件** | 产出写到明确路径 | 必须给出精确的文件路径白名单，模糊 = 授权越界 |
| **大范围施工** | 在授权目录/文件范围内自主改动 | 必须给出目录级授权边界，项目红线必须内嵌 |

**必须声明的原因**：不声明输出要求，收包方会用自己的默认行为——通常是「写文件」。如果期望「只回答不动文件」而收包方去改了文件，无法事后纠正。

**注意：放开的只是「读」，不是「写」。** 收包方可以自行决定读哪些文件，但**能写哪些文件**仍由「写入指定文件 / 大范围施工」的授权边界严格限定——写范围模糊 = 授权越界，绝不放松。

## 2. 常见包类型速查

| 场景 | R | A | 交付方式 | 输出要求 |
|------|---|---|---------|---------|
| 设计审查 | 外部模型 | 审查方案完整性，找出遗漏和红线冲突 | 混合（方案内嵌 + 代码引用） | 直接回复 |
| 方案裁决 | 外部模型 | 在多个备选方案中选定最佳并给出理由 | 内嵌（所有方案摘要） | 直接回复 |
| 代码审计 | 外部模型 | 验证实现是否符合规格 | 混合（规格内嵌 + diff 内嵌） | 直接回复 |
| 执行任务 | 外部模型 / 子代理 | 在授权范围内完成改动 | 内嵌（任务和约束全部内嵌） | 写入指定文件 / 大范围施工 |

## 3. 制包流程

### 3.1 关键原则

1. **先声明 R、A、输出要求，再收集内容**。输出要求必须第一步确定，不是最后补充。
2. **每项内容先过 RAM 检验句**。填不完整就不加。
3. **约束类内容一律内嵌原文**，不要引用 CLAUDE.md 路径——收包方不会主动去读。
4. **不确定要不要加 → 默认删除**。如果删掉后验证发现有卡点再补充。
5. **做完后模拟成收包方**，只凭手里的包走一遍：能完成 A 吗？有没有用不到的内容？

### 3.2 制包步骤

```
1. 声明 R + A + 输出要求
2. 模块级广撒网 → 识别哪些模块相关
3. 文件级筛选 → 每个文件过 RAM 检验句
4. 粒度缩减 → 精确到方法/行，不要整个文件
5. 交付方式决定 → 内嵌还是引用？（约束始终内嵌）
6. 自审 → 模拟成 R，能完成 A 吗？
```

步骤 1-5 可跳过或合并（简单任务直接写问模式 prompt 即可），只有复杂任务才走全套。

### 3.3 常见错误

| 错误 | 症状 | 纠正 |
|------|------|------|
| 以相关性为标准扩展 | 包里有 30+ 个文件 | 回到 RAM：每个文件 [R] 做 [A] 时会用到吗？ |
| 整个文件整个放 | 2000 行文件只需要 1 个方法 | 精确到方法名/行范围 |
| 约束区放 CLAUDE.md 路径 | 收包方看到的是路径不是内容 | 摘出适用条款内嵌原文 |
| 不确定时保留 | 包越来越大，关键内容被稀释 | 不确定就删除 |
| 问题太模糊 | 外模回答"差不多"的内容 | 问题必须能被独立回答 |
| 写范围写「相关文件」 | 外模改了不该改的文件 | 写范围精确到文件路径 |
| 直接回复模式缺少不改文件声明 | 外模同时修改了文件 | 末尾显式写「不要改任何文件」 |

## 4. 包的结构格式

复杂场景制包时使用以下结构：

```markdown
## 证据包：[包类型] → [R（收包方）]

**收包方动作**：[一句话，动词开头]
**信息交付方式**：[内嵌 / 引用 / 混合]
**输出要求**：[直接回复 / 写入指定文件：路径 / 大范围施工：目录边界]

---

### 约束区
（从 CLAUDE.md 摘出本次适用的条款，内嵌原文，不是引用路径）

- [适用约束 1]
- [适用约束 2]

---

### 内容区

| 内容 | 交付方式 | 具体范围 | 收包方用它做什么 |
|------|---------|----------|----------------|
| [文件路径/文档名] | 内嵌/引用 | [方法/行范围] | [填检验句后半段] |

> 以上是最小必读清单（必读）；如需要可自行补充阅读仓库其他文件。

---

### 待决策区
（收包方可能遇到的选择点；没有则写"无"）

- [待决策事项]
```

## 5. 包的大小

不用数文件数量，用这个问题：

> **「如果删掉包里任何一项，[R] 完成 [A] 的质量会下降吗？」**
> - 会：保留
> - 不会：删除
> - 不确定：删除

这个问题自动适配任务复杂度——简单任务自然收敛到 2-3 项，复杂任务自然扩展到 15-20 项。

## 6. 与 ask-claude / ask-gpt 的关系

| | dispatch | ask-claude / ask-gpt |
|---|---|---|
| **定位** | 证据包方法论 | 日常调用入口 |
| **何时用** | 复杂场景（多文件、多层约束、待决策点） | 简单场景（问一个问题、派一个任务） |
| **关系** | ask-claude 的 prompt 模板是从 dispatch 的交付方式 + 输出要求演化来的 | ask-claude 不依赖 dispatch，可直接使用 |

**建议**：
- 日常 80% 场景：直接用 ask-claude / ask-gpt 的 §3/§4 模板
- 复杂 20% 场景：回到 dispatch 方法认真制包，再通过 ask-claude 调用
