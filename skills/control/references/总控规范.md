# 总控规范

本文档是 control skill 和 task-control-doc skill 的**唯一规范真值源**（用户级 / 跨项目通用）。

任何与生命周期、归档、目录结构相关的规则只在本文件维护。两个协同 skill 都从这里引用，不再各自重写。

---

## 1. 目录结构

```text
<PROJECT_ROOT>/docs/00-任务总控/
├── README.md                                  # 活跃任务索引（仅入口/导航）
├── {YYYY-MM-DD}-{任务名}/                      # 活跃任务子目录
│   ├── README.md                              # 主总控（拆分 / 单文件统一为 README.md）
│   ├── T1-{子任务名}.md                        # 仅拆分模式存在（脚本硬依赖前缀）
│   ├── T2-{子任务名}.md
│   └── _shared/                               # 唯一过程资产目录（归属由文件名前缀区分）
│       ├── T{n}-{资产名}.md                    # 子任务专属资产
│       ├── T{n}-{资产名}/                      # 子任务多文件资产（图片包等）
│       └── {资产名}.md                         # 任务级共享资产（无前缀）
└── 归档/
    ├── README.md                              # 归档总索引
    └── V{x}/
        ├── README.md                          # 版本归档索引
        └── {YYYY-MM-DD}-{历史任务名}/           # 整体迁移过来（含 _shared/；旧任务可能含历史 _T{n}/）
```

### 1.1 放置规则

- 一个总控任务 = 一个独立子目录，根目录不直接堆放任务文件
- 与该总控强相关的人工执行清单、指南、总结，可放在同任务目录下
- 项目级正式资产（接口测试脚本、手工联调手册、长期测试基座）落到项目自身约定位置（如 `docs/04-...` / `tests/`），**不长期放在总控目录**
- 已完成任务进归档；已删除任务直接删除（不进归档）
- 顶层 `README.md` 只做活跃任务索引，不承载某个任务的细节正文

### 1.1.1 过程资产放置规则（任务执行过程中产生的临时文档）

总控任务执行过程中常产生**仅服务于本任务、不进入项目正式文档体系**的中间文档（设计稿、数据样本、批判稿、清单、原型等）。这类资产**全部放进唯一资产目录 `_shared/`**，归属由**文件名前缀**区分，不再按目录区分：

| 资产归属 | 命名 | 示例 |
|---------|------|------|
| 某子任务专属 / 产出 | `T{n}-{资产名}.md` | `T2-接口清单.md`、`T3-对抗评审报告.md` |
| 二级子任务产出 | `T{n}.{m}-{资产名}.md` | `T6.3-联调记录.md` |
| 多文件资产（图片包、样本集等） | `T{n}-{资产名}/` 子目录 | `T4-页面样图/` |
| 任务级共享（无单一子任务归属：需求真值、对话沉淀、跨子任务定稿） | 无前缀自然中文名 | `需求真值.md` |
| 进入项目正式文档体系的产出 | 项目本地约定位置（如 `docs/0x-.../...md`），不放 `_shared/` | 遵守项目自身命名规则 |

**判定口诀**：这个文件能填进某个 T{n} 的「输出物」字段吗？能 → 带 `T{n}-` 前缀；不能（任务级）→ 无前缀。

**高频资产标准名**（同类资产只许一个名字，不得自创变体）：

| 资产 | 标准名 |
|------|------|
| 轻量设计方案 | `T{n}-轻量设计方案.md` |
| goal 章程 | `T{n}-goal章程.md` |
| goal 飞行决策日志 | `T{n}-goal飞行日志.md` |
| 对抗评审报告 | `T{n}-对抗评审报告.md` |
| 施工自愈清单（任务级，跨子任务累积，无前缀） | `自愈清单.md` |

> `T{n}-施工蓝图.md` / `T{n}-蓝图评审报告.md` 在结果管控流程中**不再产出**（`construction-blueprint` 仅供传统人工逐工序流程可选使用），新任务不得再产出。

**硬约束**：
- 资产目录只有 `_shared/` 一个，以 `_` 开头（脚本只在任务根目录一层 glob `T{n}-*.md` 定位子任务工作包，不进 `_shared/`，因此资产文件带 `T{n}-` 前缀不会与脚本撞车）
- **禁止**在任务根目录平铺资产；**禁止**新建 `_T{n}/` 目录
- 即使只有 1 个资产也建 `_shared/`，规则一致优先于轻量

**资产 ↔ 子任务字段对齐**：
- 所有资产路径必须显式列在对应子任务详情的「输出物」字段（输出物 = 这个子任务交付了什么，不区分正式 / 过程资产），路径统一写 `_shared/...`
- 总控主文件**不**单独维护「资产清单」章节——「输出物」字段已是真值源，不重复登记

**生命周期**：
- 资产随任务目录一起进归档（`归档/V{x}/{任务名}/_shared/...`），归档脚本不裁剪
- 任务被删除时，资产随目录一起删除（不进归档）

### 1.2 命名规则

- **任务子目录**：`{YYYY-MM-DD}-{中文任务名}/`
  - `YYYY-MM-DD` 是任务**创建日**（创建后不变，避免改名）
  - 日期前缀防多 worktree 编号撞车——日级粒度下天然唯一
  - 极端情况（同日创建多任务）：加字母后缀 `2026-05-10b-...` 或加时分 `2026-05-10-1430-...`
- **主总控文档**：`README.md`（无论拆分 / 单文件模式都是这个名字）
- **拆分子任务文件**：`T{n}-{中文子任务名}.md`，`n` 从 1 开始递增，**仅在任务内部唯一**
- **归档版本目录**：用主产品迭代名（`V1` / `V2` / ...）；跨版本任务按主版本归档，覆盖范围写在归档索引里
- **README**：每个能列索引的目录（顶层 / 归档 / 归档/V{x}）放一个 `README.md`，不带前缀

### 1.2.1 二级任务（中途拆分支持）

> 触发场景：执行过程中发现某个一级父任务 Tn 工作量超出预期，需要原地拆为 Tn.1 ~ Tn.N 二级子任务继续推进。

**只允许两级**。`Tn.x` 不能再拆。深层拆分要么开新总控、要么改设计。

**编号格式**：

- 一级：`T1`、`T2`、`T3` …（仅数字）
- 二级：`T1.1`、`T1.2`、`T1.3` …（父编号 + 点 + 数字）

**状态语义**：

| 角色 | 状态列写法 | 派生方式 |
|------|----------|---------|
| 普通叶子任务（Tn 无子） | 用户手填 `待完成` / `进行中` / `已完成` / `阻塞` / `已取消` | 真值源 |
| 二级子任务（Tn.x） | 同上 | 真值源 |
| 父任务（Tn 有子） | 固定占位 `派生` | 脚本从直接子任务聚合：阻塞 > 进行中 > 未启动 > 已完成 |

**依赖语义**：

- 依赖列写一级编号 `T1`：若 T1 是父，自动展开为"所有 T1.* 完成"才算满足；若 T1 是叶子，直接判 T1 状态
- 依赖列写二级编号 `T1.2`：精确依赖该叶子的状态
- 拆分时**不**自动改其他任务对原 Tn 的依赖引用——语义自动扩展为"所有 Tn.* 完成"

**文件布局**（拆分模式下，单文件模式不涉及文件迁移）：

- 原 `T{n}-{子任务名}.md` → 拆分后迁移到 `T{n}/T{n}.md`（保留背景/范围作为父任务说明）
- 二级子任务 → `T{n}/T{n}.{m}-{子任务名}.md`
- 脚本（render / next_subtask / archive / split）通过 `find_subtask_md()` 统一定位文件

**脚本对父任务的处理**：

- `render_control_status.py`：父行状态列渲染为 `<派生值>（派生）`，叶子计数排除父
- `next_subtask.py`：永不推荐父任务；依赖判定时父展开为所有直接子
- `archive_control.py`：归档校验跳过派生父，只看叶子全为 `已完成` / `已取消`
- `split_subtask.py`：用户显式触发；拒绝深层拆、拒绝重复拆、拒绝拆已完成/已取消任务

详细执行流程见 control skill 的 §5.5。

---

### 1.3 单文件 vs 拆分

| 维度 | 单文件 | 拆分 |
|------|------|------|
| 主总控 | `README.md`（含全部子任务详情） | `README.md`（仅含子任务总表 + 进展记录） + `T{n}-...md`（独立子任务工作包） |
| 适用 | 3-7 个子任务、各子任务详情不超过 50 行 | 8+ 个子任务、单子任务详情很长 |

**默认用单文件**。`README.md` 整文件超过 400 行 → 考虑拆分。

## 2. 任务生命周期

### 2.1 创建阶段

1. 在 `<PROJECT_ROOT>/docs/00-任务总控/` 下新建任务目录 `{YYYY-MM-DD}-{任务名}/`
2. 用 `task-control-doc` skill 创建 `README.md`（基于 `assets/任务总控模板.md` 或拆分模板）
3. 在顶层 `README.md` 的「当前活跃任务」表格新增一行
4. 若需要独立 worktree：手动 `git worktree add`，命名遵循 §3.1（不需要在文档里登记）

### 2.2 推进阶段

- 通过 `/control` 进入并执行子任务
- 子任务开始时改 `进行中`，完成时改 `已完成`，遇阻改 `阻塞` 并写明原因
- 在哪个 worktree 写代码由 `git worktree list` 真值决定；命名约定便于人眼识别，但 worktree 不绑定任务，任意 worktree 都可以切换激活总控
- 多激活时通过 `set_active.py` 写入 `.claude/local/active-control` 选择默认总控（详见 §3.4）
- 模型选择由用户在会话开头自行决定（用 `/model` 命令切换）

### 2.3 完成与归档

任务整体完成后，**必须按以下顺序**执行（推荐用 `archive_control.py` 自动完成）：

1. 回填所有子任务状态、输出物和进展记录
2. 从顶层 `README.md` 的「当前活跃任务」删除该任务行
3. 迁移整个任务目录到 `归档/V{x}/{YYYY-MM-DD}-{任务名}/`
4. 在 `归档/README.md` 增加该任务的归档登记
5. 在 `归档/V{x}/README.md` 增加该任务的版本登记
6. 若该任务有专属 git worktree：`git worktree remove` 并删除分支（手动）

### 2.4 删除阶段

任务被明确放弃 / 不做时：

1. 删除整个任务目录
2. 从顶层 `README.md` 移除条目
3. 若有专属 git worktree：手动 `git worktree remove` 并删除分支
4. **不进归档**

## 3. Git Worktree 路径规范

> 仅约束 worktree 的**物理路径和命名**，不维护任何文档绑定。

### 3.1 路径格式

Worktree 必须放在主仓库的**兄弟目录**位置，命名为 `{REPO_NAME}--{任务关键词}`（英文短语，便于人眼识别）。

```text
{PARENT_DIR}/                        # 与主仓库同级父目录
├── {REPO_NAME}/                     # 主仓库
├── {REPO_NAME}--order-refactor/     # ✅ 任务 worktree
└── {REPO_NAME}--admin-dashboard/    # ✅ 任务 worktree
```

**命名约定的作用**：仅为人类可读性建议——从 worktree 路径名可以一眼看出对应任务。**脚本不读 worktree 名字**，多激活时通过 `.claude/local/active-control` 文件显式选择（§3.4）。

### 3.2 禁止位置

| 禁止路径 | 为什么禁止 |
|---------|----------|
| `<PROJECT_ROOT>/.claude/worktrees/xxx` | 嵌套主仓库内部，污染 git status，AI 搜代码时混淆两个分支 |
| `<PROJECT_ROOT>/任何子目录/xxx` | 同上，只要在主仓库目录内部就一律禁止 |
| `~/.claude/worktrees/xxx` | 与项目失去归属关系 |
| `{PARENT_DIR}/{REPO_NAME}-xxx`（单横线） | 命名不符规范，会与普通项目名混淆 |

### 3.3 创建命令模板

```bash
REPO_ROOT=$(git rev-parse --show-toplevel)
PARENT_DIR=$(dirname "$REPO_ROOT")
REPO_NAME=$(basename "$REPO_ROOT")
TASK_KEYWORD="order-refactor"   # 任务英文关键词
WORKTREE_PATH="$PARENT_DIR/$REPO_NAME--$TASK_KEYWORD"

git worktree add "$WORKTREE_PATH" -b "feature/$TASK_KEYWORD"
git worktree list   # 验证：路径应在兄弟目录，而非主仓库内部
```

### 3.4 真值源与激活配置

- **当前 worktree 与分支**：`git worktree list` / `git branch --show-current`
- **任务 ↔ worktree 对应关系**：用户自行管理（命名约定 §3.1 仅供人眼识别，脚本不读）
- **当前 worktree 默认激活总控**：`<PROJECT_ROOT>/.claude/local/active-control`
  - 不进版本控制（`.gitignore` 排除整个 `.claude/local/` 目录）
  - 每个 worktree 物理目录独立，互不影响、永不冲突
  - 仅在多激活总控时生效：唯一总控时此配置无意义
  - 通过 `set_active.py <关键词>` / `--clear` / `--show` 管理
  - 文件格式：单行任务目录精确名（如 `2026-05-10-订单域重构`）
- 不维护任何独立的"工作区映射表"或"工作区绑定.md"文档

## 4. 执行边界（红线）

> 这是 `/control` 执行子任务时的**最高优先级约束**，所有 skill 都必须遵守。

### 4.1 单子任务边界

- 用户指定 `/control <key> Tn` → **只动 Tn**，不要顺手做 Tn-1 或 Tn+1
- 子任务的「输出物」全部产出 → **立刻停止**，回填总控状态，等用户下一步指令
- ✅ 允许：读其他子任务的产出物（依赖关系决定）
- ❌ 禁止：写入其他子任务范围（即使发现"可以顺便做"）

### 4.2 子任务详情即工作包

- 每个子任务详情应该是一个**自包含的工作包**：包含背景、强制阅读（核心必读）、背景导航（可选）、要做什么、不做什么、输出物、完成判定
- 新会话执行时，读「子任务详情 + 强制阅读文件」即可开工——这是**准入下限，不是视野上限**：应主动补读「背景导航」与自行判断需要的背景（其他子任务详情、相关正式文档、代码现状），把背景挖够再动手
- 自主补读**亲自读**（直接读文件 / 检索），不为补背景派子 agent / 起深度调查；执行与写入范围仍严格限于本子任务（§4.1）
- 详见 `task-control-doc` skill 的子任务详情结构
- 工作包必须含结构化「写入范围」：`start_commit`、`allowed_write_paths`、`allowed_cross_task_writes`。允许路径写仓库相对路径或 glob；跨任务例外必须精确到 Markdown 标题（`path::标题`），不得写“按需修改相关文件”

### 4.3 派给外部 agent 时

派 Sonnet/Opus 子线程（Agent 工具）/ 其他 skill 时，必须在 prompt 里注入：

> 你只执行编号 `T<n>` 的子任务，**不要**接管任务调度，**不要**做其他子任务。
> 禁止读取或调用 `~/.claude/skills/control/`、本规范文件。

### 4.4 规则铸造权（防复发核心，优先级等同 §4.1）

**只有用户级文档能铸造规则**——项目级指令文档（`CLAUDE.md` / `AGENTS.md`）与 skill 本身。

| 来源 | 地位 |
|------|------|
| 项目级指令文档 / skill | **规则**，具停机权 |
| 工作包、评审报告、goal 章程、历史总控正文 | **执行建议**，**不具停机权** |

- 工作包里出现的「硬门」「前置门」「必须审批」「死亡线」——**除非能在用户级文档里指出原文出处，否则一律降级为执行建议**
- **死亡线是封闭清单**，以项目级指令文档为准。**任何人无权新增**——包括 AI、评审报告、工作包作者
- 写工作包时**禁止发明新的门禁词汇**。认为"这里必须加一条规则"→ 那是**给用户的建议**，不是你能写进工作包的约束

> **实测教训**：执行链会自己发明「前置硬门」「具名人工审查」这类 skill 原文**从未出现过**的门禁词汇，并被下一代工作包层层继承，累计出现数十次。最终用户被迫花掉一次人工裁决，去撤销一条从来没有任何人类批准过的规则。
> 根因是激励不对称：**漏一条规则 = 事故，多加一条规则 = "严谨"**。棘轮只会往紧的方向转，没有任何机制往回拧。本条就是那个往回拧的机制。

### 4.5 停机白名单（封闭清单）

执行子任务时，**只有下列三种情况可以停下来问用户**：

1. **L2 级契约冲突**：两份**都已冻结**的真值互相矛盾，且裁决会改变业务结果（分级定义见 `doc-layer-system`）
2. **命中项目死亡线清单**的业务规则需要变更（清单以项目级指令文档为准，封闭，见 §4.4）
3. **不可逆 / 外发动作**：删数据、对外发布、生产环境写入、吊销凭据、推送远端等

**冲突批处理，禁止连环打扰用户**：因第 1/2 条触发停机时，立即冻结会受裁决影响的写入，但继续对本任务最终真值切片做**有界、只读**扫描，把同一决策族的冲突、受影响层、可选方案和推荐项一次收齐。随后只向用户提交一份合并决策包；用户一次裁决后批量回补。只有新证据确实形成了不同决策族，才允许再次询问。不可逆/外发动作仍按实际授权点单独处理。合并决策包按 goal-charter §4 修改方案格式扩展：决策项 + 上游修改清单（含正式层与用例）+ 失效证据清单 + 恢复点。一次裁决即一揽子授权：批量回补正式层与用例、按影响面重跑、断点续跑，回补与续跑之间不再逐项确认；打回上游子任务重新执行仅在用户选定回炉档时发生。

> **goal 执行态让位（第 3 条）**：子任务是 goal 执行、且存在**已过红队评审并经用户拍板**的 goal 章程时，章程 §3「允许段」显式预授权的动作（部署、推送、生产写入等）**不触发第 3 条**——章程拍板本身就是用户对这些动作的一次性授权，再停机问一遍等于把已授权的事拿回去重新审批（正是必卡路径）。goal 执行期的停机以**章程 §4 白名单**为准；章程**没**预授权的不可逆动作也不是停机理由，而是章程写漏了——按红队 B 问的处置回炉补章程。

**除此之外一律「先修后报」**——自己修，留痕，继续跑，完成时一并报告。

**操作性阻塞不取得业务停机权**：安全可逆路径已穷尽、工具/环境暂时不可用或 goal 达到既定限轮时，可以交付 `EXECUTION_BLOCKED` 断点并交还控制权，但它只说明“当前运行暂时无法继续”，不得据此要求用户重做业务裁决、不得自动前拉到设计/用例/章程，也不得作废未受影响的候选与证据。失败次数本身永远不是停机或前拉依据；恢复后仍回到同一 goal 的受影响切片。

以下**明确不是**停机理由：

| 不是停机理由 | 正确做法 |
|------|------|
| 发现自己或前人的记录笔误 | 直接改，记一行 |
| 工作包描述与现行项目指令 / skill / 正式规格不一致 | 按 §4.6 自动对齐，继续跑 |
| 测试脚本有 bug | 直接修（脚本是规格的翻译，不是规格本身） |
| 发现真实代码缺陷，且根因已证实、修复路径唯一、可回滚、不改变业务规则/对外契约/数据语义 | 直接修 + 补自动回归 + 记一行 |
| 拿不准用户想要哪个，但两个选择都不改变业务结果 | 选一个，记一行，继续 |

> §4.1 第 5 条「发现子任务范围定义有问题 → 停止施工上报」仍然有效，但它管的是**真的需要改变子任务边界**的情况。**"工作包某句话写得过时了"不是范围问题**，走 §4.6。

### 4.6 过期工作包自动对齐

工作包是**上一代**的产物，上游可能早已更新。过期工作包不取得规格裁决权：

- 工作包描述 vs 项目指令 / 现行 skill / 正式 L1–L7 → 按后者修订工作包，留痕继续，不停机。
- 轻量设计尚未物化时与正式文档不一致 → 这是 T5 的收敛输入，按 `doc-layer-system` 分级；**禁止用“更新”或“已冻结”自动判任何一方赢**。
- T5 规格物化覆盖报告全绿后，正式 L1–L7 是规范真值；轻量设计、测试设计过程稿和工作包都降为留痕/执行投影。
- 两份正式规格互相矛盾且裁决会改变业务结果，才构成 §4.5 第 1 条的 L2 冲突。

未进入 goal 的存量标准研发总控还要执行 `task-control-doc/references/标准研发流程.md` §5.4 兼容升级：缺规格物化覆盖报告时恢复对应上游；尚未执行的独立执行准备包取消或仅作历史输入，并把 M0 启动检查、自愈权限与影响面重跑规则并入 goal，不为这类流程修正打扰用户。

> **实测教训**：某子任务把"工作包过期 vs 上游已冻结"包装成"契约冲突，请裁决"上报——而上游接口契约与前端文档早已冻结、全链条口径一致，根本不存在冲突。用户被迫重复裁决一件早就裁决过的事。
> **冲突铁律防的是真值不明，不是防"真值已明、只是工作包没跟上"。**

### 4.7 提交授权

- **建立总控 = 预授权在其范围内 `git commit`**，不需要每次提交都问用户。**施工成果长期不提交本身就是事故**（实测：施工成果堆在脏工作区数周不提交、分支零提交）
- **推送远端仍需显式授权**——属 §4.5 第 3 条的外发动作，由用户指令或 goal 章程显式给出

### 4.8 写入范围机检

每个子任务在第一次写入前记录当前 `start_commit`，并在工作包声明：

- `allowed_write_paths`：本工作包、正式输出物及本任务明确授权的代码/配置路径。
- `allowed_cross_task_writes`：只有状态回填或流程定义的唯一交接面；Markdown 必须写成 `仓库相对路径::标题`，例如 `README.md::子任务总表`、`T8-goal执行.md::会话启动提示词`。

交付前先形成一个或多个**只属于本子任务**的本地候选提交，再运行 `check_write_scope.py`。检查器逐个读取这些提交自身的 diff，不把 `start_commit` 之后的其他提交或工作树杂项自动算进本任务；因此无关并发变化不构成停机。任一候选提交夹带未允许路径、或跨任务文件在允许标题之外发生变化，检查失败。

`start_commit` 只用于证明候选提交属于该任务启动后的历史并防止拿旧提交冒充，不作为整仓 HEAD/脏文件指纹。目标路径在施工期间出现来源不明的重叠变化时，仍按任务自己的停机规则处理；无关路径变化继续执行。

禁止在失败后扩大 `allowed_write_paths` 以迁就既有 diff。确需扩范围时，先回到子任务边界/上游裁决，更新工作包并记录原因，再产生新的候选提交。

候选终审的跨任务写入只允许：README 的子任务总表/进展记录、被退回工作包的「当前状态」段，以及终审自己的报告/状态。退回指针不授权修改上游正文、产品、正式规格、测试资产、runner、冻结件或执行证据。

### 4.9 长程执行复水

goal 首次启动、`--resume`、新会话或自动上下文压缩后，第一次写入前必须从磁盘重新读取：当前工作包、当前阶段「强制阅读」全部文件、已拍板章程、当前 goal 断点和飞行日志尾部；禁止只依赖聊天历史或压缩摘要。连续未压缩轮次不重复加载整套 skill，里程碑切换时只重读相关章节与断点。

goal 执行工作包必须把 `_shared/T{n}-goal断点.json` 列为输出物。断点只保存 run/里程碑、已完成事实、已失效证据、下一动作、强制阅读路径与读取哈希，不承载业务语义；若意外压缩发生在最近断点之后，先用 Git、运行账本和环境只读检查重建现场，再继续写入。

## 6. 强制阅读优先级（按粒度递增）

`/control` 的强制阅读**严格按粒度递增**，避免铺垫挤占上下文：

| 触发模式 | 必读文件 |
|---------|---------|
| `/control init` | 无（直接调脚本） |
| `/control list` | 顶层 README.md |
| `/control <关键词>` | 上 + 主总控 README 的「任务背景」「子任务总表」（不读完整详情） |
| `/control <关键词> Tn` | 上 + Tn 子任务详情 + Tn「强制阅读」列出的文件 |
| 创建新总控 | 本规范 + task-control-doc skill |
| 归档任务 | 本规范（§2.3 流程）+ 归档目录索引 |

`CLAUDE.md` 由会话级注入，不需要在 control 里再读。

本规范从"每次必读"降为"按需查阅"——只在创建新总控、归档、或对规则有疑问时读。

goal 子任务的“按需”受 §4.9 覆盖：首次启动、恢复、新会话、自动压缩后必须完整复读当前阶段强制阅读；普通连续轮次不机械复读。

## 7. 真值优先级

当本规范与某个 skill 文档冲突时，**以本文件为准**。skill 应该被改回与本文件一致。

git 自身（`git worktree list`、`git branch --show-current`、`git status`）是 worktree 状态的唯一真值源；任何文档**不**镜像它。

### 7.1 文档之间的地位

| 优先级 | 来源 |
|------|------|
| 1 | 用户当场的明确指令（任务级 `_shared/用户裁决记录.md#DEC-x` 是它的持久留痕形式：保存原话或明确选项/日期/来源/适用范围，执行侧与创建侧同等适用；无 `DEC-x` 或上游正式来源，任何文档不得自称「用户已批准」） |
| 2 | 项目级指令文档（`CLAUDE.md` / `AGENTS.md`）与 skill |
| 3 | 正式 L1–L7 当前规格（用户指令须经职责层落盘后才形成长期真值） |
| 4 | 轻量设计 / 测试设计过程稿（T5 前的物化输入，T5 后降为决策留痕） |
| 5 | goal 章程（只统治执行权限与里程碑，不得覆盖 L1–L7） |
| 6 | 工作包描述、评审报告、历史总控正文、代码与运行证据 |

这张表只定义**职责与长期地位**，不是冲突时自动选边的裁决链。正式规格之间、或 T5 物化输入与正式规格之间出现实质分歧，仍按 `doc-layer-system` 分级；代码和数据库实例永远不能凭“更真实/更新”取得规格裁决权。

### 7.2 默认值不得单向调紧

发现「skill 写的是 A，实践做成了更严的 B」时——**以 skill 为准，把实践改回 A**。想把 A 变成 B，必须由用户拍板并改 skill 本身。

> **实测教训**：skill 原文明写「评审**默认塌缩**进设计 / 测试子任务末步，仅命中死亡线 / 跨域 / 契约破坏才独立」，而实践把评审做成了三个独立子任务，每个都要用户出面。**规则没错，是实践单向漂移**——且漂移之后没有任何机制把它拉回来。
> 这条对**放松**同样适用：AI 无权单方面移动用户拍板过的常数（阈值、上限、条数），**松紧皆然**。觉得定得不合理 → 报实测数据给用户裁决，不要自行调整。
