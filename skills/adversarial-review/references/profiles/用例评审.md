# 口径卡：测试用例评审

> 用法：`adversarial-review` §3.2 打包时把**本文件全文**内嵌进「本次评审口径」槽位。评审者与裁判都只认这个范围。

## 为什么这层评审关键

**在本方法论里，用例是「施工规格」而不是「验收资产」。** goal 的完成判定就锚在冻结用例的 `spec_hash` 上——**用例写虚了，没有第二道网**：

- 规格说「应该失败」→ 脚本怎么写都算"符合" → goal 全绿 → 活儿没干成
- 规格写死「返回 400 / 错误码 40001 / retryable=false」→ 想蒙混就得改规格 → 而规格已冻结、改了留痕

**这一层松一寸，后面全线失守。**

## 评什么

**只评一件事：测试强度是否达到金标准。** 判据源 = 项目/用户级测试规范 skill（`test-standards` §2 高风险清单 + §5 交付阻断条件 + §4 最低断言深度）。

具体看：

| 面 | 不合格 | 合格 |
|---|---|---|
| 断言深度 | 「接口返回成功」「有记录」「页面能打开」 | 核心字段值、字段关系、错误码、状态变化、DB 终态、唯一约束、幂等重跑结果 |
| 可对账 | 「应该失败」 | 「返回 400 / 错误码 40001 / retryable=false」 |
| 编号 | 断言是一段散文 | 每条断言有**稳定编号** AC-x，且标注它验证哪个决策点 DP-x |
| 覆盖 | 只测 happy path | 正常 + 边界 + 异常 + 回归；死亡线区域的金标准用例必须在 |
| 矩阵 | 跳过某测试面没说理由 | 每个未命中的测试面都写清"本次为什么不命中" |

## 不评什么（硬约束）

| 不评 | 为什么 |
|---|---|
| **设计选得对不对** | 设计已在上游冻结、已过它自己的评审。在这里翻案 = 让用户为同一件事裁决第二次 |
| **需求该不该这样** | 同上，更上游 |
| 实现怎么写 | 不是本层的事 |

## ⚠️ 必须放行的例外（这条最容易搞错）

**「设计没说」≠「设计选错了」。这两个必须分开处理：**

| 情况 | 判定 | 处置 |
|---|---|---|
| 「设计**选错了**，应该选另一个方案」 | ❌ **驳回**——这是翻案，设计已冻结 | 不改 |
| 「设计**没说**——我想写断言，但设计里根本没定义这种情况下的结果」 | ✅ **必须暴露**——这是缺陷，不是测试层可代答的问题 | 若正式真值能唯一推出，回填设计；若需选择新的业务结果，形成用户裁决 `DEC-x` 后再回填 |

**为什么必须留这个口子**：写用例天然会暴露设计空洞——**想写断言却发现设计没定义结果，这本身就是设计有洞的证据**，而且是最可靠的一种证据。把这条也堵死，等于关掉了唯一能自动发现设计空洞的通道，那些洞会一路漏到施工时炸给用户。

**为什么它不是翻案**：设计没说 = 用户从来没就这件事拍过板 = 不存在"重开已决策"。

## 硬约束

- **严重度预算**：阻断级最多 3 条，每条过【停线测试】三问
- **反棘轮**：禁止建议给下游加闸门 / 审批 / 前置门
- 多数问题由当前主线程裁决并整改；**只有"设计没说且补法会改变业务结果"才升级用户**
- **测试不得铸造业务语义**：AC 只能验证上游正式规格；不得因为“这样更好测”新增状态分支、错误码、时点口径或数据语义
- **只开放一次**：同一对象/基线只做一次开放式评审；回补后走 `closed-remediation-review`，禁止 R2/R3

## 三桶归置（本口径的具体化）

| 桶 | 在用例评审里长什么样 | 处置 |
|---|---|---|
| 桶1 | 断言太弱 / 漏了边界 / 缺编号 / 「设计没说」的洞 | **现在改**：改用例；洞按正式真值或 `DEC-x` 回填设计，不能由测试层选答案 |
| 桶2 | 测试执行资产的最终文件锚点需在施工时依据真实脚手架确定 | 进 `_shared/自愈清单.md`；不得把错误码、业务结果等契约语义下放施工 |
| 桶3 | 已知不测的面（如需真机） | 登记 N/A + 原因 |
