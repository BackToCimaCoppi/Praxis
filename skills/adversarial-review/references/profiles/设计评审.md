# 口径卡：轻量设计评审

> 用法：`adversarial-review` §3 打包时把**本文件全文**内嵌进「本次评审口径」槽位。评审者与裁决的主线程都只认这个范围。

## 评什么

**重大设计问题**——只有两类配叫"重大"：

1. **会改变业务结果**：用户看到的行为、数据的语义、对外契约的含义会变
2. **不可逆的架构归属**：域边界、表归属、模块划分这类"一旦定了就拆不动"的决策

## 不评什么

| 不评 | 为什么 |
|---|---|
| 逐文件怎么改、函数怎么写 | 设计是**决策海拔**，不下沉到文件级。切片是 goal 章程阶段的事 |
| 代码风格、命名、注释 | 有检查器和 code review，不该占用对抗评审的火力 |
| 【已决策·不得重开】区里的上游决策 | 已拍过板。指出"它与本设计新内容矛盾"可以（那是新问题）；说"这个决策选错了"不可以 |
| 实现细节该不该写进文档 | 实现细节属**代码自由范围**，本来就不进文档 |

## 硬约束

- **严重度预算**：阻断级最多 3 条，每条过【停线测试】三问
- **小问题一次改好，不留下游闸门**：当前主线程裁决后直接改掉，不要"记录下来待施工时注意"——那就是硬门的种子
- **决策表只含上游冻结件**：本次设计的决策**正在被拍板，是被评对象**，不进"不得重开"区
- **反棘轮**：禁止建议给下游加闸门 / 审批 / 前置门
- **业务决策来源**：评审只能指出缺口和候选，不能替用户选。凡“用户已批准”必须引用 `_shared/用户裁决记录.md#DEC-x`；没有来源只能升级用户，不能写进“不得重开”区
- **只开放一次**：同一对象/基线只做一次开放式评审；回补后走 `closed-remediation-review`，禁止 R2/R3

## 三桶归置（本口径的具体化）

| 桶 | 在设计评审里长什么样 | 处置 |
|---|---|---|
| 桶1 设计缺陷 | 设计本身错了 / 漏了一个会改变业务结果的分支 | **现在改**。大的（改业务结果 / 不可逆归属）先形成 `DEC-x` 再回补；小的、唯一确定且不改变业务结果的由主线程直接改 |
| 桶2 施工自愈项 | "这个依赖的版本要到施工时才知道"、"这个文件路径得看代码现状" | 进 `_shared/自愈清单.md`，**不改设计文档** |
| 桶3 风险登记 | 已知的技术债、将来可能要重构的地方 | 只记录 |

> **桶2 的判据是「此刻处理不了」，不是「这问题小」。** 小问题属桶1，当场改掉。

## 该重点看的地方

- **决策点是否锁死到唯一选择**：每个决策点必须说清"选了什么 / 放弃了什么 / 为什么"。含糊 = 施工时 AI 自己选 = 设计没起作用
- **影响面勘察是不是真读了代码**：勘察写的应该是「读到什么」（这个消费方现在怎么用它、改了会怎样），不是「列了什么」（罗列一堆文件名）
- **验收映射是否闭合**：每个决策点 DP-x 都能连到一条验收条件 AC-x。连不上的决策点 = 没人验 = 施工时可以偷偷不做
- **决策溯源是否真实**：每个改变业务结果、死亡线或不可逆归属的 DP-x，是否有上游正式真值或 `DEC-x`；评审建议不得充当来源
