# 证据包制作规范（RAM + 冻结核心 / 开放发现）

> 本文档是 `adversarial-review` skill 的参考资料，复杂场景（多文件、多层约束、待决策点）制包时使用；简单场景直接内联即可，不必套全套流程。

---

## 0. RAM 框架

证据包不是「收包方唯一允许看到的内容集合」，而是「收包方开始特定动作所需的最小充分核心」。它负责冻结对象、真值与边界，同时给出调查起点；授权项目根内的独立发现不计入包体，也不得被最小集裁掉。

| 要素 | 含义 | 问自己 |
|------|------|--------|
| **R（Reader）收包方** | 谁来读这个包？ | 外部模型？子代理？用户？ |
| **A（Action）动作** | 收包方要做什么？ | 设计 / 评审 / 裁决 / 审计 / 执行 / 回答问题 |
| **M（Minimum）最小集** | 收包方开始 A 所需的最小充分内嵌/引用核心 | 由 R+A 联合推导，不由任务关联性推导 |

> **读得宽，评得窄**：读取范围默认覆盖授权项目根，评审范围始终锁定冻结对象、冻结真值和本次口径。开放发现不是授权重开已决策项，也不是授权重设计整个项目。

**核心检验句**（每一项内容必须能完整填入）：

> 「**[R]** 需要 **[这项内容]**，才能 **[A]**，否则会卡在 **[具体卡点]**。」

填不完整 → 不内嵌。不确定 → **按承载形式分流**（不再一律删除）：

| 内容类型 | 不确定时的处理 | 理由 |
|---------|--------------|------|
| **内嵌正文**（占收包方上下文的实体内容） | 降级为引用，不占正文 | 内嵌位从紧，防关键内容被稀释 |
| **引用条目**（一行路径 + 一句"读它获得什么"） | **默认保留** | 一行引用几乎零成本，删掉才是真丢信息；读不读由收包方自行判断 |
| **约束 / 红线** | 与"不确定"无关：适用即必须内嵌原文 | 防漏底线，永不放松 |

> **历史注（为什么改）**：旧版规则是「不确定 → 默认删除」，为弱收包方（上下文易污染、不会自主取舍）设计。现收包方能自主检索、判断和取舍——**制包方不再替收包方裁剪调查视野，只负责钉死动作、真值、权限边界和红线**。实践证明：喂太少导致收包方背景不足做出错误判断的代价，远大于多给几行导航。

## 1. 两个关键维度

### 1.1 信息交付方式

决定「包里装的是什么」，分三种：

| 方式 | 含义 | 适用条件 |
|------|------|---------|
| **内嵌模式** | 把内容直接写进包里 | 收包方无法访问文件系统；内容短小；必须确保可见 |
| **引用模式** | 只写文件路径 + 行/方法范围 | 收包方在同一 workspace 内；文件大只需读特定位置 |
| **混合模式** | 关键约束/红线内嵌 + 大文件引用 | 大多数复杂场景的默认选择 |

**引用模式必须附带冻结核心与起始导航**：

> 以下是冻结核心与起始导航（必读），不是调查上限。开工后必须在授权项目根内亲自完成一次独立勘察，不得只凭本清单作答。

这句话只做**准入**（告诉收包方至少要读什么），不做**封顶**。独立勘察是开工义务，不是可选许可；制包方不得用穷举文件白名单代替收包方的发现过程。

**唯一硬限制（扇出焊死）**：自主补读 = **亲自读**（直接用读文件 / 检索工具），**禁止为"补背景"派子 agent / 起深度调查**——读文件是加法（线性、吃缓存），派 agent 是乘法（每个 agent 从零建上下文）；收包方自身是叶子，不得扇出（同 `deep-research-gate` 铁律 2）。若觉得背景缺口大到需要专门调查 → 说明包本身没制好，向制包方/用户报告，不自己扩编。

### 1.2 读取边界与动作边界

开放的只是授权项目内的**只读发现**，不是所有工具与外部系统。证据包必须声明：

- **项目根**：默认取被评审项目的 Git 根；不是为缩小上下文而取对象所在子目录。非 Git 项目才使用用户明确授权的项目根。
- **允许读取**：与冻结对象有关的正式规格、代码、生产者/消费者、测试源码、配置结构、迁移、运行手册，以及只读的 Git 状态、历史、差异与检索结果。
- **禁止读取**：本地环境文件（如 `.env`、`.env.local`、`.env.*.local`；已跟踪且不含真实凭据的 example/template 可读）、私钥、密钥库、凭据/令牌存储、认证缓存、其他评审者输出，以及主线程为裁决准备的预期答案或草稿。路径命中但内容是否敏感不明时，先不读并登记信息缺口。
- **禁止动作**：写入或创建文件、执行测试/构建/迁移/服务、运行有副作用的命令、联网、Web 搜索、MCP、访问数据库/云资源/其他外部系统、派生子 agent。

评审者可以用只读文件工具和无副作用的本地检索完成调查。确需越出上述边界时，只能登记 `INFO-GAP`（信息缺口）并说明缺什么、为何影响结论；不得自行扩权，也不得用猜测补洞。

### 1.3 输出要求

决定「收包方应该如何行动」，是每个包都必须声明的字段：

| 输出方式 | 含义 | 关键约束 |
|---------|------|---------|
| **直接回复** | 输出结论到 stdout，不改文件 | prompt 末尾必须写「不要改任何文件，不要创建文件」 |
| **写入指定文件** | 产出写到明确路径 | 必须给出精确的文件路径白名单，模糊 = 授权越界 |
| **大范围施工** | 在授权目录/文件范围内自主改动 | 必须给出目录级授权边界，项目红线必须内嵌 |

**必须声明的原因**：不声明输出要求，收包方会用自己的默认行为——通常是「写文件」。如果期望「只回答不动文件」而收包方去改了文件，无法事后纠正。

**注意：放开的只是「读」，不是「写」。** 收包方可以自行决定读哪些文件，但**能写哪些文件**仍由「写入指定文件 / 大范围施工」的授权边界严格限定——写范围模糊 = 授权越界，绝不放松。

## 2. 常见包类型速查

| 场景 | R | A | 交付方式 | 输出要求 |
|------|---|---|---------|---------|
| 设计审查 | 外部模型 | 审查方案完整性，找出遗漏和红线冲突 | 混合（方案内嵌 + 代码引用） | 直接回复 |
| 方案裁决 | 外部模型 | 在多个备选方案中选定最佳并给出理由 | 内嵌（所有方案摘要） | 直接回复 |
| 代码审计 | 外部模型 | 验证实现是否符合规格 | 混合（规格内嵌 + diff 内嵌） | 直接回复 |
| 执行任务 | 外部模型 / 子代理 | 在授权范围内完成改动 | 内嵌（任务和约束全部内嵌） | 写入指定文件 / 大范围施工 |

## 3. 制包流程

### 3.1 关键原则

1. **先声明 R、A、输出要求，再收集内容**。输出要求必须第一步确定，不是最后补充。
2. **每项内容先过 RAM 检验句**。填不完整就不加。
3. **本次直接适用且跨通道必须同义的红线内嵌原文**。运行时可能自动加载 AGENTS.md / CLAUDE.md，但不能假设各通道加载结果完全相同；也不要把整份全局规则重复塞进证据包。
4. **不确定要不要加 → 降级为引用，而不是删除**（见 §0 分流表）。一行「路径 + 读它获得什么」几乎零成本，只有确认无关才删；内嵌位仍从紧。
5. **做完后模拟成收包方**：凭冻结核心能否准确开工，凭项目根能否继续独立发现，敏感信息与动作边界是否清楚？
6. **把证据包自身当作待核验声明**：评审者必须检查清单是否遗漏冲突真值、关键消费者或失效材料；发现遗漏时按证据包缺口报告，不能假定制包方天然完整。

### 3.2 制包步骤

```
1. 声明 R + A + 输出要求
2. 模块级广撒网 → 识别起始模块与跨模块影响方向
3. 文件级筛选 → 每个内嵌/引用项过 RAM 检验句
4. 粒度缩减 → 精确到方法/行，不要整个文件
5. 交付方式决定 → 内嵌还是引用？（约束始终内嵌）
6. 声明项目根、禁止读取项、禁止动作与 INFO-GAP 规则
7. 自审 → 模拟成 R，能准确开工且能自主发现吗？
```

步骤 1-5 可跳过或合并（简单任务直接写 prompt 即可），只有复杂任务才走全套。

### 3.3 常见错误

| 错误 | 症状 | 纠正 |
|------|------|------|
| 以相关性为标准扩展内嵌正文 | 包里塞入大量文件全文 | 回到 RAM：保留必要冻结核心，其余变成起始导航或交给项目内自主发现 |
| 整个大文件全文放入 | 2000 行文件只需要 1 个范围 | 同一工作区可访问时优先路径 + 哈希 + 精确范围；短小、临时或不可访问内容才内嵌 |
| 约束区放规则文件路径 | 收包方看到的是路径不是内容 | 摘出适用条款内嵌原文 |
| 不确定时全文内嵌 | 包越来越大，关键内容被稀释 | 不确定降级为引用（一行路径），内嵌位只留确定项 |
| 替收包方裁剪视野 | 收包方背景不足，做出错误判断 | 冻结核心只做准入；项目根内独立勘察是强制动作，不以清单封顶 |
| 只说“可自行补读” | 收包方直接基于种子材料作答 | 强制先勘察，再输出调查账与发现；未做到视为评审角色失败 |
| 用文件白名单充当读取边界 | 跨文件影响面被人为截断 | 默认读取边界取项目根，仅按敏感信息和用户授权收窄 |
| 问题太模糊 | 外模回答"差不多"的内容 | 问题必须能被独立回答 |
| 写范围写「相关文件」 | 外模改了不该改的文件 | 写范围精确到文件路径 |
| 直接回复模式缺少不改文件声明 | 外模同时修改了文件 | 末尾显式写「不要改任何文件」 |

## 4. 包的结构格式

复杂场景制包时使用以下结构：

```markdown
## 证据包：[包类型] → [R（收包方）]

**收包方动作**：[一句话，动词开头]
**信息交付方式**：[内嵌 / 引用 / 混合]
**输出要求**：[直接回复 / 写入指定文件：路径 / 大范围施工：目录边界]
**授权项目根**：[绝对路径；默认 Git 根]
**禁止读取**：[敏感信息、其他评审输出、主线程预期答案]
**禁止动作**：[写入、执行、联网、外部系统、派生 agent]

---

### 约束区
（从运行侧规则文件摘出本次适用的条款，内嵌原文，不是引用路径；Codex 侧通常取 AGENTS.md，Claude 侧通常取 CLAUDE.md）

- [适用约束 1]
- [适用约束 2]

---

### 内容区

| 内容 | 交付方式 | 具体范围 | 收包方用它做什么 |
|------|---------|----------|----------------|
| [文件路径/文档名] | 内嵌/引用 | [方法/行范围] | [填检验句后半段] |

> 以上是冻结核心与起始导航（必读），不是调查上限。开工后必须在授权项目根内亲自完成一次独立勘察，不得只凭本清单作答。

---

### 起始导航区（推荐，不设上限）
（收包方可能用到的延伸背景：一行「路径 + 读它获得什么」。这是种子，不是穷举；**亲自读，不派 agent**。简单任务可省略。）

- [路径]：[价值一句话]

---

### 待决策区
（收包方可能遇到的选择点；没有则写"无"）

- [待决策事项]

---

### 强制独立勘察与调查账

先核对冻结对象与真值，再独立检索同一概念、业务标识、状态、错误码及上下游影响；按任务相关性覆盖生产者、消费者、正式规格、测试、配置/迁移/运行手册。只有继续检索已不再改变本次口径内结论时才收口，不以已读文件数作为停止条件。

输出一份精简调查账：

- 冻结核心已读项；
- 自主发现的关键文件与检索主题；
- 已做的反证/负向检查和实际覆盖边界；
- 未能访问、主动排除或仍缺失的信息（`INFO-GAP`）。

调查账不要求罗列每个读过的文件，但必须足以区分“独立调查后无问题”和“只读了证据包后无问题”。
```

## 5. 包的大小

不用数文件数量，用这个问题：

这里只约束**内嵌正文与起始导航的体积**，不约束授权项目根内的发现范围。判断包内项目时问：

> **「如果删掉包里任何一项，[R] 准确开始 [A] 的质量会下降吗？」**
> - 会：保留
> - 不会：删除
> - 不确定：降级为引用（一行路径 + 一句价值），读不读由收包方自行决定

这个问题让冻结核心随任务复杂度自然伸缩；不得把“包应精简”推导成“评审者只能看少量文件”。
